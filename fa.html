1.1 Node.js HTTP · Express · آداپتورهای لبه (Edge)

زیر کاپوت اکسپرس

فراخوانی express() یک تابع جاوااسکریپتی معمولی با ساختار (req, res) => void بازمی‌گرداند. سرور HTTP نود این تابع را به ازای هر درخواست صدا می‌زند. اکسپرس همچنین متدهایی چون app.use() و app.get() را به آن ضمیمه می‌کند تا این تابع را پیکربندی نماید.

در دنیای واقعی

ماژول http.Server نود مانند یک ساختمان اداری است که درب ورودی را باز می‌کند. تابع app(req, res) در اکسپرس همان متصدی پذیرشی است که به هر مراجعه‌کننده خوش‌آمد گفته و او را به بخش مربوطه هدایت می‌کند.

نحوه اجرای اکسپرس در Cloudflare Workers

سرویس PhysioCoach AI با استفاده از وب استانداردهای API fetch(request, env, ctx) درون Cloudflare Workers اجرا می‌شود. یک پل ارتباطی بسیار کوچک شیء Request وب را به یک فراخوانی سوکت نود برای اکسپرس تبدیل می‌کند.

import { httpServerHandler } from 'cloudflare:node';
import { createServer } from 'node:http';
import { createApp } from './app';
import type { WorkerBindings } from './env';

const app = createApp();
const server = createServer(app);
const nodeHandler = httpServerHandler(server as unknown as Parameters<typeof httpServerHandler>[0]);

export default {
  async fetch(request: Request, env: WorkerBindings, ctx: ExecutionContext): Promise<Response> {
    // Inject Cloudflare per-request environment bindings (Hyperdrive DB, secrets) into Express
    app.locals.workerEnv = env;
    return (nodeHandler as { fetch: (req: Request, env: unknown, ctx: unknown) => Promise<Response> }).fetch(
      request,
      env,
      ctx,
    );
  },
};
  • 1createServer(app) تابع اکسپرس را مستقیماً به سرور HTTP نود تحویل می‌دهد.
  • 2httpServerHandler رویداد fetch کلودفلر را به سرور نود پل می‌زند.
  • 3app.locals.workerEnv = env سکرت‌ها و اتصالات دیتابیس Hyperdrive را در اختیار اکسپرس قرار می‌دهد.

تفاوت بین app.locals، res.locals و الصاق ویژگی‌ها به req چیست؟

طول عمر app.locals برابر با کل پروسه یا ایزوله سرور است. از آن برای پیکربندی‌های سراسری یا اتصالات محیطی (Environment Bindings) استفاده کنید.

هشدار شرایط رقابتی (Race Condition): در یک سرور نود با درخواست‌های هم‌زمان، تغییر دادن مقادیر app.locals به ازای هر درخواست، منجر به تداخل داده در درخواست‌های هم‌پوشان می‌شود. وضعیت‌های مختص به هر درخواست را همیشه روی req یا res.locals قرار دهید.

طول عمر req و res.locals فقط به اندازه یک درخواست HTTP است. به محض پایان پاسخ‌دهی، حافظه آن‌ها توسط زباله‌روب (Garbage Collector) آزاد می‌شود. قرار دادن req.user یا req.traceId روی شیء req تضمین می‌کند که داده‌های کاربر الف هرگز به درخواست هم‌زمان کاربر ب درز نکند.

export function createApp(): TestableExpressApp {
  const app = express();

  app.use(cors());          // 1. Fast OPTIONS preflight
  app.use(express.json());  // 2. Parse JSON stream into req.body

  // 3. Distributed Trace ID (before auth so 401s still get a traceId!)
  app.use((req, res, next) => {
    req.traceId = req.header('x-request-id') || crypto.randomUUID();
    res.setHeader('x-request-id', req.traceId);
    next();
  });

  // 4. Global Authentication gate
  app.use(authMiddleware);

  // 5. Backward-compatible URL aliasing middleware
  app.use('/api/v1', (req, _res, next) => {
    const aliases: Record<string, string> = {
      '/profiles': '/profile',
      '/workout-plans/active': '/workout-plans/current',
      '/auth/google/exchange': '/auth/oauth/exchange',
      '/exercises': '/exercise-catalog/exercises',
    };
    const queryIndex = req.url.indexOf('?');
    const path = queryIndex >= 0 ? req.url.slice(0, queryIndex) : req.url;
    const query = queryIndex >= 0 ? req.url.slice(queryIndex) : '';
    const target = aliases[path];
    if (target) req.url = `${target}${query}`;
    next();
  });

  // 6. Feature Routers mounted under /api/v1
  app.use('/api/v1', healthRouter);
  app.use('/api/v1', authRouter);
  // ... profilesRouter, assessmentsRouter, workoutPlansRouter, workoutSessionsRouter

  // 7. Central Error Funnel (MUST BE LAST)
  app.use(errorHandler);
  return testableApp;
}

مقایسه Express 4 و Express 5

پروژه PhysioCoach AI روی "express": "^5.0.0" اجرا می‌شود. اکسپرس ۵ بررسی می‌کند که آیا یک هندلر Promise برمی‌گرداند یا خیر و رد شدن پرامیس‌ها (Rejections) را به صورت خودکار به next(err) ارسال می‌کند.

در دنیای واقعی

اکسپرس ۵ مثل بستن تور نجات زیر پای بندباز است. در اکسپرس ۴، اگر یک هندلر async بدون تور نجات خودش سقوط می‌کرد، مستقیماً به زمین می‌خورد و سرور از کار می‌افتاد.

وقتی یک دستور await دچار خطا می‌شود چه اتفاقی می‌افتد؟

اکسپرس ۴ قبل از پیدایش async/await در جاوااسکریپت ساخته شده بود. اکسپرس ۵ ذاتاً پرامیس‌ها (Thenables) را درک می‌کند.

پاک‌سازی تضمینی اتصالات دیتابیس با بلوک finally

سرویس PhysioCoach AI اکسپرس ۵ را با یک آداپتور سفارشی روتر ترکیب کرده تا اطمینان حاصل کند اتصالات دیتابیس همواره بسته می‌شوند، حتی اگر در مسیر خطایی رخ دهد.

register(path, async (req, res, next) => {
  const context = createRouteContext(req, res);
  try {
    const response = await handler(context);
    await sendWebResponse(res, response);
  } catch (error) {
    next(error); // Forward any thrown error or rejected promise to errorHandler
  } finally {
    await context.closeDb?.();

هدایت خودکار پرامیس‌ها

هر تابع async (req, res) که خطایی پرتاب کند یا رد شود، به طور خودکار هندلر خطای ۴ آرگومانی را فعال می‌کند.

وایلدکارت‌های نام‌دار و امنیت ReDoS

کاراکترهای وایلدکارت باید نام‌گذاری شوند، مثل /*splat به جای * خالی. قوانین سخت‌گیرانه‌تر مسیرها همچنین حملات ReDoS (رجکس‌هایی که روی ورودی مخرب معلق می‌مانند) را مسدود می‌سازد.

متد req.query به صورت Getter فقط‌خواندنی است

به صورت پیش‌فرض از پارسر ساده‌تری استفاده می‌کند. این تغییر اشیای تودرتوی مخرب که قصد آلودگی پروتوتایپ (Prototype Pollution) دارند را مسدود می‌سازد.

پاسخ مصاحبه

چرا ارتقا از Express 4 به Express 5 یک دستاورد معماری مهم به شمار می‌رود؟

۱. انتشار بومی خطاهای ناهمگام (Native Async Error Propagation): اکسپرس ۴ پرامیس‌های بازگردانده شده از هندلرهای async را نادیده می‌گرفت. بدون try / catch یا پکیج express-async-errors، پرامیس‌های رد شده سرور نود را متوقف یا درخواست را معلق می‌کردند. اکسپرس ۵ پرامیس‌ها (Thenables) را دریافت کرده و به شکل خودکار next(err) را صدا می‌زند.

۲. تطبیق امن‌تر مسیرها (Hardened Route Matching): وایلدکارت‌های ستاره خالی * اکنون باید نام داشته باشند (مانند /*splat). الگوهای رجکس مسیرها نیز برای جلوگیری از حملات منع سرویس با عبارات باقاعده (ReDoS) مستحکم شده‌اند.

۳. گتر امن‌تر برای req.query: پارامترهای کوئری به طور پیش‌فرض فقط‌خواندنی هستند و از یک پارسر مسطح استفاده می‌کنند که از نفوذ اشیای تودرتو و آلودگی پروتوتایپ جلوگیری می‌نماید.

توکن رفرش مات (Opaque)

function timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean {
  if (a.length !== b.length) {
    return false;
  }

  let diff = 0;
  for (let i = 0; i < a.length; i += 1) {
    diff |= a[i]! ^ b[i]!; // Bitwise XOR every single byte without short-circuiting!
  }

  return diff === 0;
}
  • 1عبارت a[i]! ^ b[i]! تنها زمانی مقدار 0 می‌دهد که هر دو بایت کاملاً یکسان باشند.
  • 2دستور diff |= ... هرگونه عدم تطابق را در طول کل آرایه انباشته کرده و در انتها عبارت diff === 0 را ارزیابی می‌کند.

ستون ۴: چرخش توکن رفرش، شناسایی استفاده مجدد و مقایسه اتمیک (CAS)

بر اساس استاندارد RFC 6819 و توصیه‌های امنیتی OAuth 2.0، با هر بار رفرش، توکن قدیمی باطل شده و توکن جدیدی صادر می‌شود. تلاش برای استفاده مجدد از یک توکن قدیمی و چرخیده‌شده، منجر به ابطال فوری کل نشست خواهد شد.

چرخش توکن رفرش و ردیابی سرقت (src/auth/sessions.ts)

  1. 1

    لاگین توکن رفرش R1 را صادر می‌کند

    هش SHA-256 آن در auth_sessions و auth_refresh_token_history ذخیره می‌شود.

  2. 2

    کلاینت با R1 درخواست رفرش می‌دهد ← سرور توکن R2 را صادر می‌کند

    سرور R1 را باطل می‌کند (آن را به previousRefreshTokenHash منتقل می‌نماید) و R2 را به عنوان توکن فعال قرار می‌دهد.

  3. 3

    مهاجم (یا کلاینت قربانی پس از سرقت) دوباره از توکن R1 استفاده می‌کند

    سرور متوجه می‌شود که R1 توکن فعال فعلی نیست و تاریخچه auth_refresh_token_history را جستجو می‌کند.

  4. 4

    سرور متوجه می‌شود R1 متعلق به سشن S بوده و کل سشن S را باطل می‌کند

    بلافاصله مقدار revokedAt = now را تنظیم می‌کند تا نه سارق و نه نشست قدیمی دیگر نتوانند توکنی رفرش کنند.

// Optimistic Concurrency Control (CAS - Compare-And-Swap in SQL)
const updated = await db
  .update(authSessions)
  .set({
    refreshTokenHash: nextHash,
    previousRefreshTokenHash: presentedHash,
    previousRefreshRotatedAt: nowIso,
    idleExpiresAt: nextIdle.toISOString(),
  })
  .where(
    and(
      eq(authSessions.id, session.id),
      eq(authSessions.refreshTokenHash, presentedHash), // MUST still hold the current hash!
      isNull(authSessions.revokedAt),
    ),
  )
  .returning({ id: authSessions.id });

if (updated.length === 0) {
  // Another concurrent request already rotated this token! Revoke the session.
  await revokeSession(db, session.id, nowIso);
  throw new AuthError('token_invalid', 'Refresh token is not valid.');
}

  • 2اگر مقدار updated.length === 0 باشد، به این معنی است که درخواست دیگری قبلاً توکن را چرخانده است؛ بنابراین نشست بی‌درنگ باطل می‌شود.

دو درخواست رفرش در دقیقاً همان میلی‌ثانیه یکسان

شرط SQL دستور می‌دهد eq(authSessions.refreshTokenHash, presentedHash). درخواست دوم می‌بیند که updated.length === 0 است، بلافاصله تابع revokeSession(db, session.id, nowIso) را صدا می‌زند و خطای token_invalid پرتاب می‌کند.

پاسخ مصاحبه

چرا از ماژول بومی bcrypt و عملگر === برای هش پسورد اجتناب می‌کنیم، و چرا در صورت پیدا نشدن کاربر باز هم با DUMMY_PASSWORD_HASH اعتبارسنجی را اجرا می‌کنیم؟

۱. سازگاری با لبه شبکه (Edge): افزونه‌های نیتیو C++ نظیر bcrypt در محیط‌های ایزوله Cloudflare Workers کار نمی‌کنند و ترد‌پول نود را مسدود می‌نمایند. ما از Web Crypto (crypto.subtle) با PBKDF2-SHA256 و ۵۰,۰۰۰ دور تکرار به همراه نمک ۱۶ بایتی استفاده می‌کنیم (pbkdf2$50000$<base64-salt>$<base64-hash>).

۲. عملیات بیتی با زمان ثابت (timingSafeEqual): عملگر متداول === در اولین بایت مغایر خارج می‌شود و راه را برای حملات زمان‌بندی (Timing Attacks) باز می‌گذارد. تابع timingSafeEqual با محاسبه diff |= a[i]! ^ b[i]! تمام بایت‌ها را در زمان پردازشی کاملاً یکنواخت مقایسه می‌کند.

۳. جلوگیری از سرشماری کاربران (User Enumeration): الگوریتم PBKDF2 حدود ۳۰ تا ۵۰ میلی‌ثانیه زمان می‌برد، در حالی که خروج زودهنگام تنها ۲ میلی‌ثانیه طول می‌کشد. اجرای verifyPassword در برابر DUMMY_PASSWORD_HASH (~۴۵ میلی‌ثانیه) و بازگرداندن پیام یکسان Invalid email or password. امکان حدس وجود یا عدم وجود یک حساب کاربری را از بین می‌برد.

پاسخ مصاحبه

چرا یک توکن JWT ۳۰ روزه صادر نمی‌کنیم، و سازوکار چرخش و ردیابی استفاده مجدد چگونه جلوی سرقت توکن رفرش را می‌گیرد؟

۱. توکن‌های دوگانه و ذخیره‌سازی هش‌شده: توکن‌های JWT بدون وضعیت را نمی‌توان تا قبل از سررسید باطل کرد. ما یک توکن دسترسی ۱۵ دقیقه‌ای با HS256 (بررسی در زیر ۱ میلی‌ثانیه) را با یک توکن رفرش ۳۲ بایتی جفت می‌کنیم که فقط هش SHA-256 آن (refreshTokenHash) در auth_sessions نگهداری می‌شود. حتی اگر نسخه پشتیبان دیتابیس به سرقت برود، نفوذگران تنها به هش‌ها دسترسی خواهند داشت و امکان سوءاستفاده از نشست کاربران را نخواهند داشت.

۲. چرخش و ردیابی استفاده مجدد (RFC 6819): با هر بار استفاده از R1، این توکن باطل شده و توکن R2 صادر می‌شود. اگر فرد دیگری دوباره از R1 استفاده کند، سرور وجود آن را در auth_refresh_token_history ردیابی کرده و کل نشست را بلافاصله لغو می‌کند (revokedAt = now).

۳. مقایسه و جایگزینی اتمیک (CAS) و پنجره انقضای دوگانه: اجرای اتمیک Compare-And-Swap در SQL (eq(authSessions.refreshTokenHash, presentedHash)) در برابر رفرش‌های هم‌زمان از نشست محافظت می‌کند. به علاوه، هر نشست از یک انقضای شناور idleExpiresAt به همراه یک سقف سخت و قطعی absoluteExpiresAt بهره می‌برد.

چرا در فایل src/db/client.ts دو گزینه prepare: false و fetch_types: false تنظیم شده‌اند؟

۱. prepare: false (غیرفعال‌سازی عبارات آماده نام‌دار): مدیریت‌کننده‌های استخر اتصال مانند Cloudflare Hyperdrive و PgBouncer در حالت استخر تراکنش (Transaction Pooling Mode) کار می‌کنند. ممکن است تراکنش شماره ۱ روی اتصال بک‌اند پستگرس #42 اجرا شود، در حالی که تراکنش شماره ۲ روی اتصال بک‌اند #19 قرار گیرد. عبارات آماده نام‌دار در پستگرس به یک اتصال فیزیکی خاص TCP وابسته هستند. فرض کنید کتابخانه postgres.js دستور آماده s1 را روی اتصال #42 ایجاد کند و در ادامه کوئری بعدی را روی اتصال #19 بفرستد. در این لحظه پستگرس با خطای ERROR: prepared statement "s1" does not exist متوقف می‌شود. قرار دادن prepare: false اجرای ساده/بدون‌نام پروتکل را فعال می‌کند تا مدیریت استخر در سطح تراکنش بدون مشکل عمل کند.

۲. fetch_types: false (درون‌نگری در زمان اتصال سرد): درایور postgres.js به طور پیش‌فرض هنگام اتصال، کوئری SELECT oid, typname FROM pg_type... را اجرا می‌کند تا انواع داده‌های سفارشی پستگرس را پیش از اجرای نخستین کوئری شما شناسایی کند. در محیط سرورلس Worker، این کوئری اضافی تعداد رفت‌وبرگشت‌ها به دیتابیس را در نخستین اتصال دو برابر می‌کند. خاموش کردن fetch_types تاخیر اتصال سرد دیتابیس را به نصف می‌رساند.

1.9 میان‌افزار خطا · استاندارد RFC 7807 · مهار هشدارهای لاگ

مدیریت متمرکز خطا

اکسپرس یک میان‌افزار مدیریت خطا را با بررسی شرط fn.length === 4 در زمان اجرا شناسایی می‌کند. هر شکستی در سیستم باید از مسیر یک قرارداد یکپارچه Problem Details بر پایه RFC 7807 به بیرون هدایت شود.

در دنیای واقعی

در یک بیمارستان، تمامی بخش‌ها از یک فرم گزارش حادثه یکسان استفاده می‌کنند. حادثه در پذیرش رخ داده باشد، در آزمایشگاه یا در داروخانه، هر پزشکی می‌تواند ظرف چند ثانیه گزارش را بخواند و متوجه ماجرا شود.

دام شرط زمان اجرای fn.length === 4

در اکسپرس، یک میان‌افزار مدیریت خطا صرفاً با داشتن دقیقاً ۴ آرگومان شناسایی می‌شود: (error, req, res, next).

دام پروداکشن · اکسپرس مقدار fn.length === 4 را چک می‌کند

حذف _next مقدار را به fn.length === 3 تغییر داده و هندلر خطای شما بی‌پاسخ نادیده گرفته می‌شود

حتی اگر داخل تابع مدیریت خطا نیازی به فراخوانی next نداشته باشید، حتماً باید پارامتر چهارم _next را در ساختار (error, req, res, _next) نگه دارید. اگر بنویسید (error, req, res)، ویژگی fn.length برابر 3 می‌شود و اکسپرس آن را یک میان‌افزار عادی در نظر می‌گیرد و هنگام وقوع خطا اصلاً آن را اجرا نمی‌کند.

۳ آرگومان: (error, req, res)

مقدار fn.length تابع در جاوااسکریپت 3 است. اکسپرس آن را به عنوان یک میان‌افزار معمولی ثبت می‌کند.

→ هنگام صدا زدن next(err) کاملاً نادیده گرفته شده و اجرا نمی‌شود

۴ آرگومان: (error, req, res, _next)

مقدار fn.length تابع برابر 4 است. عبارت void _next; لینتر را راضی نگه داشته و پارامتر چهارم را حفظ می‌کند.

→ تمامی خطاهای پرتاب‌شده در کل برنامه را با موفقیت دریافت و مدیریت می‌کند

استاندارد RFC 7807 / RFC 9457 (application/problem+json)

در فایل src/middleware/error.ts، سامانه PhysioCoach AI خروجی‌های خطای سلیقه‌ای و نامنظم را با ساختار استاندارد RFC 7807 Problem Details برای APIهای HTTP جایگزین می‌کند.

ساختارهای ناسازگار و متناقض خطا در مسیرها

یک اندپوینت شیء { error: "bad" } بازمی‌گرداند در حالی که دیگری { msg: "failed", code: 12 } می‌دهد.

→ فرانت‌اند ناچار است برای هر اندپوینت لاجیک مجزایی برای خواندن خطا پیاده‌سازی کند

یک قرارداد یکتا بر پایه RFC 7807

هر خطایی هدر Content-Type: application/problem+json را به همراه فیلدهای type، title، detail، instance، traceId و auditLogId برمی‌گرداند.

→ یک ساختار کاملاً پیش‌بینی‌پذیر برای کلاینت‌ها و سیستم‌های لاگینگ

export const errorHandler: ErrorRequestHandler = (error: unknown, req, res, _next) => {
  void _next;
  const candidate: HttpError =
    error instanceof Error ? error : new Error('Unexpected API error.');
  const status = resolveStatusCode(error, candidate);
  const traceId = req.traceId || crypto.randomUUID();
  const auditLogId = candidate.auditLogId || req.auditLogId || null;

  if (status >= 500) {
    console.error('request.failed', { traceId, auditLogId, error: candidate.message });
  }

  res
    .status(status)
    .type('application/problem+json')
    .json({
      type: `https://physiocoach.devbench.ir/problems/${status}`,
      title: STATUS_TITLES[status] || 'Request Failed',
      detail: candidate.message || 'Unexpected API error.',
      instance: req.originalUrl,
      traceId,
      auditLogId,
      ...(error instanceof ZodError ? { errors: error.issues } : {}),
    });
};

  • 2شرط if (status >= 500) فقط کرش‌ها و خطاهای سمت سرور را لاگ می‌کند و اشتباهات موردانتظار کلاینت با کدهای 4xx را ثبت نمی‌کند.
  • 3هدر پاسخ را روی application/problem+json قرار داده و مقادیر traceId، auditLogId و آرایه اختیاری errors ناشی از Zod را ضمیمه می‌نماید.

منبع خطا در resolveStatusCode() کد وضعیت HTTP هشدار در console.error؟
ZodError 400 Bad Request خیر (اشتباه در ورودی کلاینت)

1.10 پراکسی‌های معکوس · هدر Retry-After · مدیریت حافظه مقید

محدودسازی نرخ درخواست پشت پراکسی

پشت شبکه کلودفلر، آی‌پی سوکت TCP همان آی‌پی پراکسی است. سیستم محدودکننده نرخ درخواست باید هدر معتبر لبه شبکه را بخواند و حافظه خود را بدون نیاز به تایمرهای سراسری پاک‌سازی کند.

در دنیای واقعی

نگهبان یک باشگاه شبانه تعداد دفعات ورود را بر اساس کارت شناسایی اختصاصی هر فرد (cf-connecting-ip) می‌شمارد، نه بر اساس پلاک تاکسی مشترکی (req.socket.remoteAddress) که همه را جلوی درب پیاده کرده است.

چرا هدر cf-connecting-ip بر x-forwarded-for اولویت دارد

function getClientKey(c: ExpressRouteContext): string {
  const cfConnectingIp = c.req.header('cf-connecting-ip');
  if (cfConnectingIp) {
    return cfConnectingIp;
  }

  const forwardedFor = c.req.header('x-forwarded-for');
  if (forwardedFor) {
    return forwardedFor.split(',')[0]?.trim() || 'unknown';
  }

  const realIp = c.req.header('x-real-ip');
  return realIp?.trim() || 'unknown';
}

۱. آیا Node.js تک‌رشته‌ای (Single-threaded) است؟

کدهای جاوااسکریپت شما روی یک رشته منفرد (حلقه رویداد یا V8 Event Loop) اجرا می‌شوند. یک حلقه سنگین محاسباتی یا تابع همگام JSON.parse حجیم، تمامی کاربران هم‌زمان را مسدود می‌کند.

۶. چرا برای Refresh Token به جای PBKDF2 یا bcrypt از هش SHA-256 استفاده می‌شود؟

گذرواژه‌ها آنتروپی پایینی دارند: انسان‌ها معمولاً رمزهای ساده و قابل حدس انتخاب می‌کنند، بنابراین نیازمند یک الگوریتم هش کند (مانند PBKDF2 یا Argon2) هستند تا جلوی حملات حدس آفلاین (Brute-force) گرفته شود.

توکن‌های تجدید آنتروپی بسیار بالایی دارند: این توکن‌ها شامل ۳۲ بایت (۲۵۶ بیت) داده تصادفی رمزنگاری‌شده قوی (crypto.getRandomValues) هستند. با داشتن 2^256 حالت ممکن، حدس زدن آن‌ها از نظر ریاضی غیرممکن است. یک تابع هش سریع رمزنگاری مثل SHA-256 توکن را در صورت نشت احتمالی دیتابیس کاملاً ایمن نگه می‌دارد، بدون اینکه در هر بار تمدید توکن منابع باارزش پردازنده را هدر دهد.

2.3 تزریق وابستگی · طول عمر · اسکوپ‌ها

طول عمر سرویس‌ها در Dependency Injection

یک سرویس با طول عمر طولانی، هرگز نباید مستقیماً به یک سرویس با طول عمر کوتاه‌تر وابسته باشد.

در دنیای واقعی

یک سرویس Scoped شبیه به کتاب مرجع سالن مطالعه است که قرار است پس از پایان هر نوبت مطالعه تحویل داده شود. وابستگی اسیرشده (Captive Dependency) مثل این است که یکی از ساکنان دائمی کتابخانه، آن کتاب را بردارد و برای همیشه در اتاق اختصاصی خود قفل کند.

مقایسه طول عمرهای Transient، Scoped و Singleton در طول دو درخواست HTTP

طول عمر زمان ساخت نمونه مثال واقعی در net-angular
Transient در هر بار که درخواست داده شود. هلپرهای سبک و بدون وضعیت (در صورت استفاده از Scoped به‌ندرت نیاز می‌شود).
Scoped یک‌بار به ازای هر درخواست HTTP (یا اسکوپ دستی). AppDbContext، ApplicationService، EmbeddingIndex.
Singleton فقط یک‌بار برای کل طول حیات اپلیکیشن. NpgsqlDataSource، RunQueue، DecisionThresholds.

دام وابستگی اسیرشده (Captive Dependency)

دام پروداکشن

به دام افتادن AppDbContext درون یک Singleton

دو درخواست یا تسک پس‌زمینه همزمان، موجودیت‌های ردیابی‌شده یکدیگر را دستکاری کرده و خطای InvalidOperationException: A second operation was started on this context instance را پرتاب می‌کنند.

پاسخ مصاحبه

چه فاجعه‌ای رخ می‌دهد اگر یک سرویس Scoped (مانند AppDbContext) را درون یک سرویس Singleton (مانند RunWorker : BackgroundService) تزریق کنید؟

تبدیل به یک Captive Dependency (وابستگی اسیرشده) می‌شود. سرویس Scoped برای همیشه درون شیء Singleton گیر می‌افتد و عملاً رفتاری مشابه یک شیء Singleton پیدا می‌کند.

کلاس DbContext به هیچ عنوان Thread-Safe نیست و موجودیت‌های ردیابی‌شده را در حافظه کَش می‌کند. دو درخواست یا جاب پس‌زمینه همزمان، وضعیت داده‌های یکدیگر را مخدوش کرده و خطای زمان اجرای InvalidOperationException: A second operation was started on this context instance رخ می‌دهد.

راهکار رفع مشکل: در کلاس Singleton به جای کانتکست، اینترفیس IServiceScopeFactory را تزریق کنید، به ازای هر جاب با متد scopeFactory.CreateScope() یک اسکوپ مستقل دستی بسازید، و AppDbContext را از آن اسکوپ فراخوانی کنید.

نحوه ساخت اسکوپ تمیز به ازای هر جاب در RunWorker.cs

using var scope = scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
  • 1کلاس RunWorker یک Singleton است (BackgroundService)، بنابراین به جای AppDbContext، اینترفیس IServiceScopeFactory را تزریق می‌کند.
  • 2دستور using var scope یک AppDbContext تازه مختص به همان جاب می‌سازد و به محض اتمام کار، آن را Dispose می‌کند.

نکته کلیدی · اسکوپ مجزا برای ثبت خطا در RunWorker.cs (سطرهای ۴۹ تا ۵۹)

هنگامی که یک جاب پس‌زمینه با خطا مواجه می‌شود، کانتکست اصلی AppDbContext ممکن است حاوی وضعیت‌های خراب در ردیاب تغییرات باشد (مثل موجودیتی نامعتبر که در انتظار ثبت در دیتابیس مانده است). بلوک catch یک اسکوپ خطای کاملاً جدید می‌سازد (using var errorScope = scopeFactory.CreateScope()) تا وضعیت failedRun.Status = "failed" را بدون هیچ تداخل و خطایی در دیتابیس ذخیره کند.

مزایا و معایب انتخاب Channel<T> در برابر Hangfire یا RabbitMQ چیست؟

صف Channel<T> در حافظه رم اجرا می‌شود. چنانچه پروسه در حین وجود جاب در کانال کرش کند یا ری‌استارت شود، دلیگیت موجود در حافظه از بین خواهد رفت.

راهکار پروژه net-angular برای جبران این موضوع: از آنجا که پیش از قرار دادن در صف، یک ردیف با وضعیت queued یا running در PostgreSQL ثبت می‌شود، می‌توان هنگام بالا آمدن سرور ردیف‌های معلق و قدیمی را شناسایی کرده و آن‌ها را دوباره اجرا نمود.

چه زمانی باید سیستم را ارتقا داد؟ در زمان مهاجرت به کلاسترهای چند سروره (Multi-Node) یا زمانی که به تضمین قطعی تحویل پیام در ری‌استارت‌ها بدون نوشتن کدهای دستی بازیابی نیاز دارید. در آن شرایط، از صف‌های مبتنی بر دیتابیس مثل Hangfire یا Quartz، یا بروکرهای پیام مثل RabbitMQ یا Azure Service Bus استفاده کنید و بروکر را با الگوی Transactional Outbox (ذخیره پیام خروجی در همان تراکنش دیتابیس پیش از انتشار) همراه سازید.

۱. تفاوت IQueryable<T> و IEnumerable<T>

اینترفیس IQueryable<T> یک درخت عبارت (Expression Tree) می‌سازد (Expression<Func<T, bool>>) که EF Core آن را به دستورات SQL برای اجرا روی سرور پایگاه داده ترجمه می‌کند.

اینترفیس IEnumerable<T> دلیگیت‌ها (Func<T, bool>) را درون حافظه C# اجرا می‌کند. تبدیل داده‌ها به IEnumerable قبل از اعمال فیلتر باعث می‌شود تمام داده‌های جدول از طریق شبکه به داخل RAM دانلود شوند.

پاسخ مصاحبه · ۲ از ۸

۲. سازوکار زیرین async / await

دستور async ترد جدیدی ایجاد نمی‌کند. کامپایلر C# متد شما را به یک ماشین وضعیت (IAsyncStateMachine) بازنویسی می‌کند.

در زمان انتظار برای عملیات I/O شبکه یا دیسک (نظیر پاسخ پستگرس یا OpenRouter)، ترد جاری به تردپول دات‌نت بازمی‌گردد تا به سایر درخواست‌های HTTP سرویس دهد. همواره نوع خروجی متدها را Task یا Task<T> تعریف کنید.

  1. 1

    آغاز I/O و رسیدن به await

    ماشین وضعیت IAsyncStateMachine متغیرهای محلی جاری را ثبت کرده و یک ادامه (Continuation) رزرو می‌کند.

  2. 2

    بازگشت ترد به استخر تردهای دات‌نت (Thread Pool)

    صفر ترد حین پردازش درخواست در پستگرس یا OpenRouter مسدود می‌ماند.

  3. 3

    اتمام I/O ← ادامه کار ماشین وضعیت

    یکی از تردهای استخر، وضعیت بعدی را برداشته و شیء بازگشتی Task<T> را تکمیل می‌کند.

دام ۱: استفاده از .Result یا .Wait()

گرسنگی تردپول (Thread-pool Starvation) و بن‌بست (Deadlock)

مسدود کردن همگام یک ترد در انتظار پایان تسک ناهمگام، سبب قفل همگام روی ناهمگام (Sync-over-async) شده و استخر تردها را فلج می‌کند.

دام ۲: استفاده از async void

کرش کردن کل پروسه با پرتاب استثنا

کدهای فراخواننده نمی‌توانند روی async void از دستور await استفاده کنند یا خطاهای آن را مهار نمایند. همیشه Task یا Task<T> بازگردانید.

پاسخ مصاحبه · ۳ از ۸

۳. مقایسه ValueTask<T> در برابر Task<T>

کلاس Task<T> یک نوع مرجع (Reference type) است که روی هیپ حافظه تخصیص می‌یابد مگر اینکه کش شده باشد. در حالی که ValueTask<T> یک struct (نوع مقداری) است.

از ValueTask<T> در مسیرهای پرحرارت و پرفراخوانی (Hot Paths) که نتیجه معمولاً به صورت همگام در دسترس است (مثلاً در ۹۹٪ موارد از کش درون حافظه خوانده می‌شود) استفاده کنید. هرگز روی یک ValueTask<T> بیش از یک‌بار await نزنید.

۴. جمع‌آوری زباله (GC) و نسل‌های حافظه در دات‌نت

دات‌نت هیپ مدیریت‌شده را به Gen 0، Gen 1، Gen 2 و هیپ اشیای بزرگ (LOH) تقسیم می‌کند. نسل ۰ اشیای کوتاه‌عمر مانند DTOهای درخواست‌های HTTP را نگه می‌دارد، نسل ۱ به عنوان بافر عمل می‌کند، و نسل ۲ اشیای با طول‌عمر طولانی مانند Singletonها را در خود جای می‌دهد. بخش LOH اشیای با حجم >= 85,000 بایت مثل آرایه‌های بسیار بزرگ یا رشته‌های حجیم را ذخیره می‌کند.

عملیات GC روی نسل ۰ زیر یک میلی‌ثانیه طول می‌کشد، در حالی که پاکسازی LOH و نسل ۲ بسیار سنگین و پرهزینه است. از تخصیص مکرر رشته‌ها و آرایه‌های بزرگ درون حلقه‌ها خودداری کنید و به جای آن از ArrayPool<T>، Span<T> یا استریمینگ بهره ببرید.

رندرینگ و وضعیت (State)

یک کامپوننت ری‌اکت یک نمونه زنده از یک کلاس نیست؛ بلکه یک فراخوانی تابع خالص است که props و state فعلی را به رابط کاربری (UI) تبدیل می‌کند.

فرمول بنیادین

UI = f(props, state)

با هر بار تغییر state، ری‌اکت تابع شما را از بالا تا پایین مجدداً اجرا می‌کند.

تصویر دنیای واقعی

یک کامپوننت ری‌اکت شبیه باجه عکاسی فوری است؛ با هر تغییر، عکسی کاملاً جدید چاپ می‌کند، نه اینکه روی عکس قبلی با خودکار نقاشی بکشد.

یک فراخوانی تابع، نه یک نمونه کلاس

متغیرهای محلی تعریف‌شده با const یا let در هر بار رندر از نو ساخته می‌شوند. هندلرهای رویداد، مقادیر props و state مربوط به همان رندر به‌خصوص را در حافظه کلوژر خود نگه‌می‌دارند (Capture می‌کنند).

عادت انگولار: نمونه کلاس

انگولار یک بار new MyComponent() را صدا می‌زند، متغیر this.someProperty را در طول زمان جهش می‌دهد (Mutate می‌کند)، و هنگام انتشار سیگنال‌ها یا رویدادهای زون، تمپلیت را بررسی می‌نماید.

وضعیت (State) تغییرناپذیر است و با Object.is مقایسه می‌شود

ری‌اکت تغییر وضعیت را با مقایسه رفرنس‌های قدیمی و جدید از طریق Object.is(oldState, newState) تشخیص می‌دهد.

دام پروداکشن · عادت آسیب‌رسان در انگولار

toasts.push(newItem); setToasts(toasts)

رفرنس آرایه تغییر نکرده است، بنابراین Object.is(oldArray, newArray) === true خواهد بود. ری‌اکت می‌پندارد چیزی تغییر نکرده و از رندر مجدد صرف‌نظر می‌کند.

const [toasts, setToasts] = useState<ToastItem[]>([]);

  const id = nextId.current++;
  setToasts((current) => [...current, { id, message, tone }]);

مقادیر مشتق‌شده: محاسبه مستقیم در حین رندر

هنگامی که مقداری از props یا state به دست می‌آید، آن را مستقیماً درون بدنه تابع محاسبه کنید. آن را در useState یا useEffect قرار ندهید.

عادت انگولار: computed()

شیوه ری‌اکت: یک const ساده

تابع کامپوننت شما از قبل با هر رندر دوباره اجرا می‌شود. یک متغیر ساده const بسیار پرسرعت است و به هیچ رپری نیاز ندارد.

قانون رندر خالص (Pure Render Rule)

ری‌اکت و کامپایلر ری‌اکت می‌توانند کامپوننت شما را چندین بار فراخوانی کرده یا خروجی آن را کش کنند. رندر حتماً باید خالص باقی بماند.

متغیرهای بیرونی را تغییر ندهید

در زمان رندر، هرگز متغیرهای خارج از تابع کامپوننت را تغییر (Mutate) ندهید.

توابع ناخالص را در رندر صدا نزنید

هرگز توابعی مانند Date.now()، new Date() یا Math.random() را حین رندر یا در ردیوسر وضعیت فراخوانی نکنید.

کارهای ناخالص را به هندلرها بسپارید

هندلرهای رویداد نظیر submit بخشی از مرحله رندر نیستند؛ آن‌ها می‌توانند با خیال راحت new Date() را فراخوانی کرده و مقدار حاصل را به داخل بفرستند.

چرا کپی کردن props درون state در هوک useEffect یک آنتی‌پترن مخرب است، و سه رویکرد اصولی برای مدیریت داده‌های حاصل از props کدامند؟

علت آسیب: فراخوانی setState(prop) درون useEffect باعث می‌شود ری‌اکت ابتدا یک چرخه کامل رندر و ترسیم (Paint) را با وضعیت قدیمی به پایان برساند، و سپس بلافاصله یک رندر دوم را آغاز کند که منجر به افت عملکرد و پرش بصری می‌شود.

۱. محاسبه حین رندر: اگر مقدار از props یا state محاسبه می‌شود، آن را به‌عنوان یک متغیر ساده درون بدنه تابع محاسبه کنید (مانند hasFilters در IssueFilters).

۲. ریست کردن کل state با کلید key: هر زمان که یک شناسه یا شماره نسخه تغییر کرد و شما یک نقطه شروع کاملاً پاک می‌خواهید، یک key جدید بفرستید. کامپوننت IssueForm از key={issue.updatedAt.toISOString()} استفاده می‌کند.

۳. اصلاح state خاص در حین رندر: برای به‌روزرسانی تنها برخی فیلدها ضمن حفظ فوکوس درون SearchBox، کامپوننت را در حالت مونت نگه دارید. setState را مستقیماً حین رندر درون شرط if (prop !== prevProp) صدا بزنید.

با فعال بودن کامپایلر جدید ری‌اکت (React Compiler)، آیا هنوز هم باید نگران تغییرناپذیری (Immutability) یا رندر خالص باشیم؟

بله، حتی بسیار جدی‌تر از گذشته. کامپایلر ری‌اکت مقادیر و بلوک‌های JSX را بر مبنای برابری رفرنس‌ها (Object.is) به‌صورت خودکار مموایز می‌کند و این فرض قطعی را دارد که تابع رندر شما کاملاً بدون ساید افکت است.

هرگز یک آرایه را در محل تغییر ندهید و توابع ناخالص مانند new Date() را حین رندر صدا نزنید. در غیر این صورت، کامپایلر ممکن است از محاسبه مجدد یک بلوک صرف‌نظر کرده و رابط کاربری کهنه و غلط روی صفحه باقی بماند.

افکت‌ها و سیستم‌های خارجی

یک افکت تنها و تنها برای همگام‌سازی با یک سیستم خارجی است؛ مانند لیسنرهای DOM، تایمرها، اتصالات وب‌سوکت یا ویجت‌های غیر ری‌اکتی.

تصویر دنیای واقعی

هوک useEffect درست مثل تبدیل دوشاخه برق در سفر است. شما فقط در مرز اتصال میان دستگاه خود و پریز برق بیگانه روی دیوار به آن احتیاج پیدا می‌کنید.

اشتراک در رویدادهای DOM با useEffectEvent

فراخواننده‌ها یک تابع ناشناس (Arrow Function) مانند useHotkey("/", (e) => { ... }) ارسال می‌کنند که در هر بار رندر رفرنس جدیدی ایجاد می‌کند. هوک useEffectEvent (در ری‌اکت ۱۹.۲+) همیشه آخرین نسخه handler را بدون لزوم ثبت مجدد لیسنر DOM می‌خواند.

export function useHotkey(
  key: string,
  handler: (event: KeyboardEvent) => void,
) {
  const onKey = useEffectEvent(handler);

  useEffect(() => {
    function listener(event: KeyboardEvent) {
      if (event.key !== key || event.metaKey || event.ctrlKey || event.altKey)
        return;
      if (isTyping(event.target)) return;
      onKey(event);
    }
    document.addEventListener("keydown", listener);
    return () => document.removeEventListener("keydown", listener);
  }, [key]);
}
  • 1useEffectEvent(handler) همیشه جدیدترین نسخه handler را صدا می‌زند در حالی که نیازی نیست handler درون آرایه وابستگی‌های [key] قرار گیرد.
  • 2بازگرداندن () => document.removeEventListener(...) لیسنر را در زمان آنمونت یا تغییر key به‌خوبی پاکسازی می‌کند.
  1. 1

    اجرای Setup در زمان مونت

    ری‌اکت متد document.addEventListener("keydown", listener) را فراخوانی می‌کند.

  2. 2

    بررسی پاکسازی در Strict Mode (فقط در محیط توسعه)

    ری‌اکت بلافاصله آنمونت شدن را شبیه‌سازی کرده و removeEventListener را اجرا می‌کند تا پاکسازی‌های جاافتاده را کشف کند.

  3. 3

الگوی Latest-Ref برای تایمرها

هنگامی که یک setTimeout به‌جای useEffect درون یک هندلر رویداد استارت می‌خورد، آخرین نسخه کالبک را درون یک جعبه useRef نگهداری کنید.

export function useDebouncedCallback<Args extends unknown[]>(
  fn: (...args: Args) => void,
  delayMs: number,
) {
  const latest = useRef(fn);
  const timer = useRef<ReturnType<typeof setTimeout> | undefined>(undefined);

  useEffect(() => {
    latest.current = fn;
  });

  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback(
    (...args: Args) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => latest.current(...args), delayMs);
    },
    [delayMs],
  );
}
  • 1latest.current = fn درون یک افکت پس از هر کامیت به‌روزرسانی می‌شود.
  • 2هنگامی که تایمر پس از delayMs (برای مثال ۳۰۰ میلی‌ثانیه) فعال می‌شود، تابع latest.current(...args) را با جدیدترین مقادیر props و state فراخوانی می‌کند.

چرا useRef؟

{ current: value } یک ظرف تغییرپذیر است که در طول رندرهای مختلف زنده می‌ماند، بدون آنکه تغییر فیلد .current رندر مجددی ایجاد نماید.

چرا از useEffectEvent استفاده نمی‌کنیم؟

توابع حاصل از Effect Event را فقط می‌توان از درون خود useEffect صدا زد. در اینجا تایمر درون یک هندلر رویداد فراخواننده (onChange) شروع می‌شود.

چرا مقدار latest.current را در حین رندر نمی‌نویسیم؟

موتور همروند (Concurrent) ری‌اکت ممکن است رندری را آغاز کرده و آن را نیمه‌کاره رها کند یا با ترتیبی نامنتظره رندر نماید. تغییر دادن یک Ref حین رندر، خلوص آن را نقض می‌کند.

مقادیر ایمن مرورگر در زمان هایدریشن با useSyncExternalStore

سرور تاریخ‌ها را بر مبنای UTC قالب‌بندی می‌کند در حالی که مرورگر از منطقه زمانی کاربر (مثلاً +04:00) بهره می‌برد. فراخوانی مستقیم date.toLocaleString() حین رندر باعث می‌شود سرور ساعت 14:00 UTC و مرورگر ساعت 18:00 را تولید کند که منجر به خطای عدم تطابق هایدریشن (Hydration Mismatch) در ری‌اکت می‌گردد. هوک useSyncExternalStore تضمین می‌کند HTML اولیه سرور و گذر نخست هایدریشن کلاینت کاملاً یکسان باشند و سپس به زمان محلی تبدیل شوند.

const subscribe = () => () => {};

export function LocalTime({ date }: { date: Date }) {
  const text = useSyncExternalStore(
    subscribe,
    () => formatLocalDateTime(date), // 2nd arg: Client snapshot (after hydration)
    () => formatDateTime(date),      // 3rd arg: Server & hydration snapshot (UTC)
  );
  return <time dateTime={date.toISOString()}>{text}</time>;
}
  • 1آرگومان سوم (formatDateTime) روی سرور و در گذر ابتدایی هایدریشن کلاینت فراخوانی می‌شود.
  • 2درست پس از تکمیل موفقیت‌آمیز هایدریشن، ری‌اکت به سراغ آرگومان دوم (formatLocalDateTime) می‌رود.

الگوی قدیمی useState("") + useEffect

روی سرور یک رشته خالی "" رندر می‌کند که باعث برچسب‌های زمانی خالی در HTML اولیه SSR و جابه‌جایی چیدمان صفحه (Layout Shift) پس از بارگذاری می‌شود.

هوک مدرن useSyncExternalStore

یک برچسب زمانی واقعی بر پایه UTC در HTML سرور می‌سازد، بدون کمترین عدم تطابقی هایدریت می‌شود، و درجا به منطقه زمانی محلی ارتقا پیدا می‌کند.

این یک رفتار کاملاً عمدی و طراحی‌شده توسط <StrictMode> ری‌اکت است. ری‌اکت در محیط توسعه آنمونت و مونت مجدد هر کامپوننت را شبیه‌سازی می‌کند (setup → cleanup → setup) تا راستی‌آزمایی کند که تابع پاکسازی (Cleanup) شما کلیه آثار فاز setup را پاک می‌کند.

ترکیب کامپوننت‌ها و الگوی دونات (Donut Pattern)

تصویر دنیای واقعی

یک کامپوننت کلاینت شبیه یک قاب عکس مجهز به پیچ تنظیم روشنایی است. کامپوننت سرور مثل عکس چاپ‌شده‌ای است که درون این قاب قرار می‌گیرد.

مرز سرور/کلاینت و الگوی دونات

در ساختار App Router در Next.js، همه کامپوننت‌ها به‌طور پیش‌فرض کامپوننت سرور (Server Component) هستند مگر آنکه فایل با راهنمای "use client" آغاز شود. کامپوننت‌های سرور منحصراً روی سرور اجرا می‌شوند، می‌توانند مستقیماً کوئری‌های دیتابیس را await کنند، و حجم خروجی آن‌ها برابر با 0 KB JS برای مرورگر است.

قاعده ۱ · ایمپورت‌ها به کد کلاینت تبدیل می‌شوند

هر ماژولی که مستقیماً توسط یک فایل دارای "use client" ایمپورت شود، درون باندل کلاینت جاوااسکریپت بسته‌بندی خواهد شد.

قاعده ۲ · راه نجات با الگوی دونات

معماری Context در ری‌اکت ۱۹: دور نگه داشتن وضعیت‌های متغیر از کانتکست‌های فراگیر

ToastContext فقط تابع پایدار toast را در اختیار می‌گذارد، نه آرایه متغیر toasts را.

const ToastContext = createContext<ShowToast | null>(null);

export function useToast(): ShowToast {
  const toast = use(ToastContext);
  if (!toast) throw new Error("useToast must be used inside <ToastProvider>.");
  return toast;
}
  • 1ToastContext حاوی تایپ ShowToast (یک کالبک پایدار) است، نه آرایه ToastItem[].
  • 2دستور use(ToastContext) این کانتکست را با بهره‌گیری از هوک مدرن use() در ری‌اکت ۱۹ می‌خواند.

رندر کردن <ToastContext.Provider value={toast}> و خواندن با useContext(ToastContext)، که قابلیت فراخوانی درون بلاک‌های if را نداشت.

رندر مستقیم <ToastContext value={toast}> و خواندن با use(ToastContext)، که می‌تواند به‌صورت شرطی پس از returnهای زودهنگام یا درون بلاک‌های if صدا زده شود.

هوک useId و علت شکست شناسه‌های ثابت DOM در Next.js 16

نسخه ۱۶ فریم‌ورک Next.js از کامپوننت جدید <Activity> ری‌اکت استفاده می‌کند تا مسیرهای قبلی را به‌صورت پنهان در DOM نگه دارد. اگر هر دو مسیر /issues/new و /issues/1/edit ویژگی ثابت id="title" را رندر کنند، کلیک کردن روی لیبل در صفحه ویرایش باعث پرش فوکوس به فیلد ورودی پنهان‌شده در صفحه ایجاد ایشیو می‌شود.

export function useFieldId() {

قابلیت‌های همروند و فرم‌ها در ری‌اکت ۱۹

ری‌اکت ۱۹ کدهای تکراری مدیریت دستی isLoading و منطق بازگشت (Rollback) را با چهار هوک هماهنگ برای ترنزیشن‌ها، رابط کاربری خوش‌بینانه و فرم‌ها جایگزین کرده است.

تصویر دنیای واقعی

گارسونی که بلافاصله روی برگه سفارش میز شما می‌نویسد «در حال آماده‌سازی»، و اگر آشپزخانه اعلام کند موجودی تمام شده، آن را فوراً پاک می‌کند.

چهار هوک هماهنگ در ری‌اکت ۱۹

سه هوک از بسته اصلی react و یک هوک از بسته react-dom ارائه می‌شوند.

عادت انگولار یا نسخه‌های قدیمی ری‌اکت

مدیریت دستی متغیرهای isLoading، error، و ذخیره متغیر prevValue همراه با کدهای بازگشت در بلوک‌های try / catch با هر تغییر وضعیت.

شیوه مدرن ری‌اکت ۱۹

هماهنگ‌سازی جهش‌های ناهمگام با استفاده از useTransition، useOptimistic، useActionState و useFormStatus.

useTransition · از پکیج react

اجرای یک به‌روزرسانی وضعیت یا اکشن ناهمگام در پس‌زمینه بدون مسدود ساختن ورودی کاربر؛ ردیابی وضعیت pending. مثال‌ها: StatusControl، SearchBox.

useOptimistic · از پکیج react

نمایش بی‌درنگ حالت جدید رابط کاربری در حین در جریان بودن ترنزیشن یا اکشن ناهمگام؛ بازگشت خودکار در صورت لغو یا خطا. مثال‌ها: StatusControl، CommentThread.

useActionState · از پکیج react

متصل ساختن یک <form> به امضای (prevState, formData) => nextState، با ردیابی آخرین FormState و وضعیت isPending. مثال‌ها: IssueForm، CommentThread.

useFormStatus · از پکیج react-dom

خواندن مقادیر { pending, data } فرم دربرگیرنده (<form>) از درون یک کامپوننت فرزند. مثال: SubmitButton.

هماهنگی میان useTransition و useOptimistic

دام پروداکشن

فراخوانی useFormStatus() در همان کامپوننتی که <form> را رندر می‌کند همواره برابر با false است

هوکی که در سطحی بالاتر از <form> صدا زده شود، هیچ فرم والدی برای خواندن اطلاعات ندارد. همیشه useFormStatus() را درون یک کامپوننت فرزند که داخل <form>...</form> قرار می‌گیرد فراخوانی نمایید.

export function SubmitButton({ children, pendingLabel, ...props }) {
  const { pending } = useFormStatus();
  return (
    <Button type="submit" disabled={pending || props.disabled} aria-disabled={pending} {...props}>
      {pending && pendingLabel ? pendingLabel : children}
    </Button>
  );
}
  • 1هوک useFormStatus() وضعیت { pending } را از تگ دربرگیرنده <form> دریافت می‌کند.
  • 2در زمان اجرای اکشن فرم، دکمه خودش را غیرفعال کرده و برچسب pendingLabel را جایگزین می‌نماید.

تفاوت بین یک به‌روزرسانی عادی وضعیت با وضعیتی که درون startTransition قرار می‌گیرد چیست؟

فوری در برابر غیرفوری: آپدیت‌های عادی وضعیت (مانند تایپ کردن در یک ورودی <input>) فوری (Urgent) و همگام هستند؛ آن‌ها رابط کاربری را تا زمان پایان رندر مسدود می‌کنند.

ترنزیشن‌های قابل وقفه (Interruptible): قرار دادن یک آپدیت (یا ناوبری روتر Next.js) درون startTransition آن را به‌عنوان عملیاتی غیرفوری و قابل وقفه نشانه‌گذاری می‌کند. در حین در جریان بودن یک ترنزیشن، ری‌اکت رابط کاربری فعلی را روی صفحه کاملاً تعاملی نگه می‌دارد به‌جای اینکه یک صفحه خالی یا لودر نشان دهد. چنانچه کاربر مجدداً کلیدی را فشار دهد، ری‌اکت رندر ناتمام قبلی را متوقف کرده و رندر جدید را در اولویت می‌گذارد.

useOptimistic(passthroughState) هرگز وضعیت را به‌طور دائمی جهش (Mutate) نمی‌دهد.

مقدار موقت خوش‌بینانه تنها تا زمانی وجود دارد که اکشن ناهمگام یا startTransition به‌طور فعال در جریان (Pending) باشد. لحظه‌ای که ترنزیشن به سرانجام برسد، ری‌اکت لایه خوش‌بینانه را کنار گذاشته و به مقدار معتبر و قطعی passthroughState که از سرور آمده رجوع می‌کند.

اپ روتر، استریمینگ و مرزهای خطا

نکست ۱۶ یک پوسته بیرونی استاتیک را در زمان بیلد پیش‌رندر می‌کند و حفره‌های دینامیک در زمان درخواست را از طریق <Suspense> استریم می‌نماید.

در دنیای واقعی

یک رستوران بلافاصله برای شما نان و آب می‌آورد، در حالی که غذای اصلی هنوز در آشپزخانه در حال پختن است.

پارامترهای ناهمگام (Async Params)، searchParams و cacheComponents

در نکست ۱۵ و ۱۶ به بعد، مقادیر params و searchParams مسیر از نوع Promise هستند. شما نباید params.projectKey را به صورت همگام بخوانید؛ بلکه باید params را درون یک مرز <Suspense> با await دریافت کنید.

نکته کلیدی

مقادیر params و searchParams از جنس Promise هستند. کامپوننت ProjectPage همگام باقی می‌ماند و این Promiseهای هنوز حل‌نشده را به <ProjectContent> درون <Suspense> پاس می‌دهد.

export default function ProjectPage({
  params,
  searchParams,
}: PageProps<"/projects/[projectKey]">) {
  return (
    <main className="flex flex-col gap-6">
      <Suspense fallback={<ProjectPageSkeleton />}>
        <ProjectContent params={params} searchParams={searchParams} />
      </Suspense>
    </main>
  );
}

  • 2هر پردازشی در زمان درخواست (مانند خواندن params، searchParams، headers()، cookies() یا کوئری‌های کش‌نشده دیتابیس) باید درون یک مرز <Suspense> قرار گیرد.

3.6 DAL · "use cache" · React.cache · updateTag

لایه DAL و سیستم کشینگ

داده‌های خام اشتراکی بین تمام کاربران را با "use cache" کش کنید، و سطح دسترسی هر کاربر را بیرون از کش محاسبه نمایید.

در دنیای واقعی

رستوران برای تمام مهمانان یک منوی مشترک چاپ می‌کند، اما پیشخدمت حساسیت‌های غذایی هر مهمان را به شکل اختصاصی بررسی می‌نماید.

الگوی لایه دسترسی داده (DAL)

هر کوئری و میوتیشن در مسیر src/features/*/ (سند معماری docs/adr/0009-data-access-layer.md) سه قانون سخت‌گیرانه را اعمال می‌کند.

هرگز db را در UI ایمپورت نکنید

کامپوننت‌های ری‌اکت هرگز نباید db یا اسکیمای Drizzle را مستقیماً ایمپورت کنند.

actor: Actor پارامتر نخست است

هر کوئری و میوتیشن شیء فاعل عملیات (actor: Actor) را به عنوان اولین آرگومان دریافت می‌کند.

بازگرداندن DTO به همراه viewerCan

کوئری‌ها یک DTO تمیز حاوی viewerCan: { edit, delete } که توسط توابع خالص در permissions.ts محاسبه شده برمی‌گردانند.

نحوه کارکرد "use cache" در نکست ۱۶.۴ (و چرا actor بیرون می‌ماند)

در یک تابع دارای "use cache"، فریم‌ورک Next.js کلید کش را به صورت خودکار از روی آرگومان‌های سریالایز شده تابع (projectKey، issueNumber) می‌سازد.

export async function getIssue(
  actor: Actor,
  projectKey: string,
  issueNumber: number,
): Promise<IssueDetail | null> {
  const row = await cachedIssue(projectKey.toUpperCase(), issueNumber);
  if (!row) return null;

  // viewerCan depends on WHO is asking, so it is computed here, outside the
  // cache. The cached part is the same for everyone.
  const { reporterId, assigneeId, ...issue } = row;
  return {
    ...issue,
    viewerCan: {
      edit: can.editIssue(actor, { reporterId, assigneeId }),
      delete: can.deleteIssue(actor, { reporterId }),
    },
  };
}

تفاوت بین React.cache و "use cache" در نکست را توضیح دهید، و بگویید چه زمانی از هر دوی آن‌ها با هم استفاده می‌کنید.

React.cache (تک‌درخواستی): خروجی تابع را صرفاً در طول درخت رندر یک درخواست منفرد کش می‌کند (Memoization). اگر Layout، Page و یک کامپوننت فرزند همگی تابع getCurrentUser() را فراخوانی کنند، کوئری نشست دیتابیس برای آن درخواست فقط یک بار اجرا می‌شود.

"use cache" (چنددرخواستی): نتایج را در کش سرتاسری نکست که میان درخواست‌ها و کاربران به اشتراک گذاشته شده ذخیره می‌کند و با cacheLife و cacheTag کنترل می‌شود.

استفاده همزمان از هر دو: دایرکتیو "use cache" نمی‌تواند کوکی‌های مختص یک درخواست (cookies()) را بخواند. بنابراین ما هویت کاربر را بیرون با React.cache (getCurrentUser) می‌خوانیم و تنها آرگومان‌های مستقل از هویت کاربر را به توابع "use cache" ارسال می‌کنیم.

تفاوت بین updateTag(tag) و revalidateTag(tag, "max") در نکست ۱۶ چیست؟

updateTag(tag): فقط درون یک اکشن سرور قابل فراخوانی است. مدخل کش را بلافاصله باطل می‌کند تا خواندن بعدی در همان چرخه منتظر داده‌های تازه بماند (الگوی read-your-own-writes).

revalidateTag(tag, "max"): در Route Handlerها یا وبهوک‌ها استفاده می‌شود و مدل stale-while-revalidate را اجرا می‌کند (داده‌های قدیمی را تحویل می‌دهد در حالی که در پس‌زمینه داده تازه واکشی می‌شود).

export async function updateIssueAction(
  issueId: string,
  _prev: FormState,
  formData: FormData,
): Promise<FormState> {
  // 1. Authenticate the caller (never trust that the button was hidden in UI)
  const user = await requireUser();

  // 2. Validate form data with Zod
  const values = formValues(formData);
  const parsed = EditIssueInput.safeParse(values);
  if (!parsed.success) return invalid(values, parsed.error);

  // 3. Authorize & mutate inside the DAL (checks can.editIssue)
  let issue;
  try {
    issue = await updateIssue(user, issueId, parsed.data);
  } catch (error) {
    return failed(values, error);
  }

  // 4. Expire affected cache tags
  invalidate.issueChanged(issue);

  // 5. Redirect OUTSIDE try/catch!
  redirect(`/projects/${issue.projectKey}/issues/${issue.number}` as Route);
}

دام پروداکشن ۱ · آرگومان‌های متصل (Bound) ورودی غیرقابل اعتماد هستند

عبارت updateIssueAction.bind(null, issue.id) در فیلدهای پنهان HTML فرم سریالایز می‌شود

مهاجم می‌تواند آن فیلد پنهان را در ابزار DevTools مرورگر دستکاری کرده و فرم را ارسال کند. همواره آرگومان‌های بایند شده را با Zod اعتبارسنجی کنید (Id.safeParse(projectId)) و سطح دسترسی را درون تابع تغییر داده دیتابیس بررسی نمایید.

دام پروداکشن ۲ · تابع redirect() یک خطای NEXT_REDIRECT پرتاب می‌کند

قرار دادن redirect() درون try { ... } catch (err) { return failed(...) } فرایند ریدایرکت را بلعیده و مختل می‌کند

توابع redirect() و notFound() یک خطای کنترلی داخلی پرتاب می‌کنند تا ری‌اکت فوراً رندر را متوقف کند. قرار دادن آن‌ها درون یک بلوک catch این استثنا را مهار کرده و ذخیره‌سازی موفق را به یک پیام خطا برای کاربر تبدیل می‌کند.

عادت دنیای انگولار · درون try / catch

در انگولار، متد this.router.navigate(...) یک Promise معمولی بازمی‌گرداند. اما در نکست، صدا زدن redirect() درون try/catch باعث به دام افتادن NEXT_REDIRECT شده و تابع return failed(values, error) را اجرا می‌کند.

تابع redirect() خطای NEXT_REDIRECT پرتاب می‌کند: در نکست، redirect() مقداری بازنمی‌گرداند؛ بلکه یک استثنای کنترلی داخلی به نام NEXT_REDIRECT پرتاب می‌کند. فریم‌ورک این استثنا را در سطوح بالاتر دریافت می‌کند تا هدر ریدایرکت 303 را ارسال کند یا ناوبری روتر کلاینت را استریم نماید.

راهکار حل مشکل: قرار دادن redirect() درون try/catch مانع از رسیدن این استثنا به نکست می‌شود. یا redirect() را بعد از بلوک try/catch قرار دهید، یا درون catch تابع unstable_rethrow(err) را صدا بزنید.

آیا دستور myAction.bind(null, secretId) مقدار secretId را روی سرور مخفی نگه می‌دارد؟

خیر. نکست آرگومان‌های بایند شده را در فیلدهای مخفی فرم به کلاینت می‌فرستد تا مرورگر هنگام ثبت فرم بتواند آن‌ها را بازگرداند.

هرگز داده‌های محرمانه را به .bind() پاس ندهید، و شناسه یا مقادیر بایند شده را همیشه روی سرور دقیقاً همانند فیلدهای ورودی FormData اعتبارسنجی و بررسی مجوز کنید.

دفاع لایه‌ای (Defense-in-Depth) در ۳ لایه

فرایند احراز هویت و بررسی سطح دسترسی در سه لایه هم‌مرکز روی سرور اجرا می‌شود.

۱. src/proxy.ts · بررسی وجود کوکی (بدون دیتابیس)
۲. صفحات و اکشن‌ها · requireUser / requireAdmin (نشست دیتابیس با React.cache)
۳. لایه DAL · فایل‌های queries.ts / mutations.ts + permissions.ts (بررسی can.editIssue قبل از SQL)

۱. src/proxy.ts

در نسخه‌های پیش از نکست ۱۶ با نام middleware.ts شناخته می‌شد. یک بررسی سریع و خوش‌بینانه که صرفاً وجود کوکی نشست را بررسی کرده (getSessionCookie(request)) و کاربران ناشناس را ریدایرکت می‌کند. اینجا هیچ تماسی با دیتابیس برقرار نمی‌شود.

۲. صفحه و اکشن (session.ts)

توابع requireUser و requireAdmin توکن سشن را در برابر جدول sessions در پستگرس اعتبارسنجی می‌کنند؛ این فرآیند با React.cache برای هر درخواست فقط یک بار اجرا می‌شود.

۳. لایه DAL (permissions.ts)

ماژول‌های queries.ts و mutations.ts نقش و مالکیت را دقیقا پیش از اجرای کوئری SQL بررسی می‌کنند (can.editIssue(actor, row)).

هرم تست ۴ لایه‌ای (بدون شبیه‌سازی یا ماک دیتابیس)

به جای شبیه‌سازی کوئری‌های SQL، تست‌های یکپارچگی (Integration) مایگریشن‌های واقعی Drizzle را روی دیتابیس PGlite درون‌حافظه‌ای (پستگرس کامپایل‌شده به WASM؛ سند docs/adr/0010-integration-tests-pglite.md) اجرا می‌کنند. تست‌های E2E با پلی‌رایت نیز در برابر بیلد پروداکشن پروژه اجرا می‌شوند (docs/adr/0006-testing-strategy.md).

۴. تست سرتاسری Playwright E2E · دستور next build && next start
۳. یکپارچگی دیتابیس و اکشن‌ها · PGlite درون حافظه (*.int.test.ts)
۲. هوک‌ها و کامپوننت‌های کلاینت · Testing Library (*.test.tsx)
۱. یونیت تست · توابع خالص، Zod و پارسرهای URL (*.test.ts)

۱. تست‌های واحد (*.test.ts)

توابع خالص، اسکیمای Zod و پارسرهای پارامترهای سرچ در URL: فایل‌های permissions.test.ts و search-params.test.ts.

۲. هوک‌ها و کامپوننت‌های کلاینت (*.test.tsx)

ابزار Testing Library به همراه userEvent و تایمرهای ساختگی: فایل‌های comment-thread.test.tsx و use-debounced-callback.test.tsx.

۳. یکپارچگی دیتابیس و اکشن‌ها (*.int.test.ts)

مایگریشن‌ها و کوئری‌های واقعی SQL در Drizzle را روی PGlite درون حافظه (پستگرس تحت WASM، بدون هیچ SQL ساختگی) اجرا می‌کند. تست issues/actions.int.test.ts فراخوانی‌های دقیق updateTag() و مقاصد redirect() را بررسی می‌کند.

۴. تست‌های E2E پلی‌رایت (e2e/)

در برابر خروجی واقعی بیلد پروداکشن next build && next start اجرا می‌شود تا کامپوننت‌های سرور، استریمینگ، کشینگ، و نگهداری DOM در <Activity> ری‌اکت را بیازماید.

پرسش‌های مصاحبه سطح سنیور

پاسخ مصاحبه · پرسش ۱

یک معمار سیستم با پس‌زمینه انگولار پیشنهاد می‌دهد بررسی سشن کاربر در فایل src/app/(app)/layout.tsx انجام شود تا صفحات منفرد نیازی به بررسی نداشته باشند. پاسخ شما در جلسه بازبینی معماری چیست؟

این طرح را رد کنید. در App Router نکست، Layoutها هنگام ناوبری سمت کلاینت بین مسیرهای فرزند مجدداً اجرا نمی‌شوند. همچنین صفحات مستقل از Layoutها استریم می‌شوند و اکشن‌های سرور نیز به طور کامل Layoutها را دور می‌زنند.

جایگاه اصلی احراز هویت: بررسی‌ها در Layout صرفاً برای نمایش رابط کاربری کاربر (مانند آواتار در نوبار) کاربرد دارند. احراز هویت و کنترل دسترسی واقعی باید در فراخوانی‌های دسترسی به داده در تک‌تک صفحات و درون تمام اکشن‌های سرور انجام گیرد.

پاسخ مصاحبه · پرسش ۲

چرا نمی‌توان یک کامپوننت سرور async را که از <Suspense> و "use cache" استفاده می‌کند در محیط Vitest + Testing Library یونیت تست کرد؟

فقدان ران‌تایم سرور در JSDOM: تابع render() در Testing Library در یک محیط شبه‌کلاینت JSDOM اجرا می‌شود. این محیط فاقد سریالایزر استریم RSC نکست، ران‌تایم "use cache"، و کانتکست درخواست سرور (headers() و cookies()) است.

بهترین تفکیک استراتژی تست: کوئری‌های داده و اکشن‌های سرور را مستقیماً در تست‌های یکپارچگی سریع با PGlite درون‌حافظه‌ای تست کنید. سپس صفحات کامپوننت سرور async را به صورت سرتاسری (E2E) با Playwright در برابر بیلد پروداکشن بیازمایید.

«علت» را توضیح دهید، نه فقط «چیستی» را.
