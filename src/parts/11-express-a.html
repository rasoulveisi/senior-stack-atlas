1.1 Node.js HTTP · Express · Edge Adapters

Under the hood

Calling express() returns a plain JavaScript function with the signature (req, res) => void. Node's HTTP server calls that function on every request. Express also attaches methods such as app.use() and app.get() to configure that function.

Real-world picture

Node's http.Server is an office building that opens the front door. Express app(req, res) is the one receptionist who greets every visitor and directs them inside.

How Cloudflare Workers runs Express

PhysioCoach AI runs inside Cloudflare Workers using the Web Standard fetch(request, env, ctx) API. A tiny bridge turns the Web Request into a Node socket call for Express.

import { httpServerHandler } from 'cloudflare:node';
import { createServer } from 'node:http';
import { createApp } from './app';
import type { WorkerBindings } from './env';

const app = createApp();
const server = createServer(app);
const nodeHandler = httpServerHandler(server as unknown as Parameters<typeof httpServerHandler>[0]);

export default {
  async fetch(request: Request, env: WorkerBindings, ctx: ExecutionContext): Promise<Response> {
    // Inject Cloudflare per-request environment bindings (Hyperdrive DB, secrets) into Express
    app.locals.workerEnv = env;
    return (nodeHandler as { fetch: (req: Request, env: unknown, ctx: unknown) => Promise<Response> }).fetch(
      request,
      env,
      ctx,
    );
  },
};
  • 1createServer(app) passes the Express function directly to Node's HTTP server.
  • 2httpServerHandler bridges Cloudflare's fetch event to that Node server.
  • 3app.locals.workerEnv = env hands Cloudflare secrets and Hyperdrive DB bindings to Express.

Why app.ts and index.ts are separate

src/app.ts builds the Express instance via createApp(). src/index.ts attaches it to the network runtime.

No EADDRINUSE in tests

Each parallel test calls createApp() without binding port 8787.

Edge runtime ready

src/index.ts wraps the app in Cloudflare Workers fetch().

Docker & Node portability

The exact same app runs on a Linux container via app.listen(8787).

What happens to a POST body stream

When a client sends a POST request with JSON, the body is not ready right away.

  1. 1

    Raw bytes arrive in chunks over a TCP stream

    Node wraps this readable stream in an http.IncomingMessage object (req).

  2. 2

    req.body does not exist yet

    Reading a network stream is asynchronous and takes time until a body parser reads the chunks.

  3. 3

    Express upgrades the JavaScript prototypes

    Express uses Object.setPrototypeOf to attach express.request and express.response, adding req.header(), res.status(), and res.json().

Interview answer

What is the difference between app.locals, res.locals, and attaching properties to req?

app.locals lives for the whole process or isolate lifetime. Use it for global configuration or environment bindings.

Race-condition warning: In a concurrent multi-request Node server, mutating app.locals per request causes race conditions across overlapping requests. Always put per-request state on req or res.locals.

req and res.locals live for one HTTP request only. When the response finishes, they are garbage-collected. Putting req.user or req.traceId on req guarantees User A's data never leaks into User B's concurrent request.

Process / Isolate Lifetime

app.locals

Shared across all requests. Mutating it per request in Node risks race conditions.

One HTTP Request Lifetime

req & res.locals

Isolated per visitor and garbage-collected right after the response ends.

1.2 Pipeline · Order · Fail-Closed Security

Order is architecture

Express has one mental model: an ordered array of functions. When a request arrives, Express starts at index 0 and runs each function in order.

Real-world picture

Middleware is an airport security line. Each desk checks one thing. A desk can wave you to the next desk, send you home, or call security.

A normal request walks stations 1 to 6 and ends with a response. Station 7 runs only when something calls next(err) or throws.

Three allowed moves — and what breaks

Every middleware receives (req, res, next) and must do exactly one of three things.

1. Call next()

Pass control to the next middleware function in line.

2. Send a response

Call res.json(), res.send(), or res.end() to finish the request.

3. Call next(error)

Or throw inside an async function in Express 5 to jump straight to errorHandler.

Trap

Forget next() and send no response

The client hangs forever until the load balancer times out with 504 Gateway Timeout.

Trap

Call next() after res.json()

The next middleware sends a second response. Node crashes with Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client. Always return res.json(...)!

Pipeline assembly in code

export function createApp(): TestableExpressApp {
  const app = express();

  app.use(cors());          // 1. Fast OPTIONS preflight
  app.use(express.json());  // 2. Parse JSON stream into req.body

  // 3. Distributed Trace ID (before auth so 401s still get a traceId!)
  app.use((req, res, next) => {
    req.traceId = req.header('x-request-id') || crypto.randomUUID();
    res.setHeader('x-request-id', req.traceId);
    next();
  });

  // 4. Global Authentication gate
  app.use(authMiddleware);

  // 5. Backward-compatible URL aliasing middleware
  app.use('/api/v1', (req, _res, next) => {
    const aliases: Record<string, string> = {
      '/profiles': '/profile',
      '/workout-plans/active': '/workout-plans/current',
      '/auth/google/exchange': '/auth/oauth/exchange',
      '/exercises': '/exercise-catalog/exercises',
    };
    const queryIndex = req.url.indexOf('?');
    const path = queryIndex >= 0 ? req.url.slice(0, queryIndex) : req.url;
    const query = queryIndex >= 0 ? req.url.slice(queryIndex) : '';
    const target = aliases[path];
    if (target) req.url = `${target}${query}`;
    next();
  });

  // 6. Feature Routers mounted under /api/v1
  app.use('/api/v1', healthRouter);
  app.use('/api/v1', authRouter);
  // ... profilesRouter, assessmentsRouter, workoutPlansRouter, workoutSessionsRouter

  // 7. Central Error Funnel (MUST BE LAST)
  app.use(errorHandler);
  return testableApp;
}
  • 1Trace ID runs at step 3 before authMiddleware at step 4.
  • 2Step 5 rewrites legacy paths in memory while preserving query strings.
  • 3errorHandler is registered last so it catches errors from every step above.

Look closely at steps 3, 5, and 6

Key idea

Put Trace ID middleware before authMiddleware. When an expired JWT triggers 401 Unauthorized and jumps to errorHandler, the response and server log still carry x-request-id.

Value inside authRouter /auth/login /api/v1/auth/login

Interview answer

Why use a global authMiddleware with a public-path allowlist instead of adding authMiddleware to individual routes?

Fail-closed security (Secure by Default). Every new endpoint is protected automatically.

With 40+ endpoints across 10 routers, adding router.post('/secret', authMiddleware, handler) by hand is risky. Someone will eventually forget one route and expose private data.

Mounting authMiddleware globally in src/app.ts with an explicit PUBLIC_PATHS allowlist in src/middleware/auth.ts removes that risk.

1.3 Express 5 · Async Errors · Routing

Express 4 vs 5

PhysioCoach AI runs on "express": "^5.0.0". Express 5 checks if a handler returns a Promise and automatically forwards rejections to next(err).

Real-world picture

Express 5 stretches a safety net under a trapeze artist. In Express 4, an async handler that threw without its own net fell straight to the floor.

What happens when an await throws

Express 4 was built before async/await existed in JavaScript. Express 5 natively understands Promises ("thenables").

Express 4

Calls handlers synchronously. If an await rejects and you forgot try / catch or express-async-errors, nobody catches the rejected Promise.

→ unhandled rejection crashes Node or hangs the request

Express 5

Router internals check if the handler returns a Promise. When the Promise rejects, Express catches it and calls next(err) for you.

→ 4-argument errorHandler returns clean JSON

Guaranteed DB cleanup with finally

PhysioCoach AI pairs Express 5 with a custom router adapter so database connections always close, even when a route throws.

register(path, async (req, res, next) => {
  const context = createRouteContext(req, res);
  try {
    const response = await handler(context);
    await sendWebResponse(res, response);
  } catch (error) {
    next(error); // Forward any thrown error or rejected promise to errorHandler
  } finally {
    await context.closeDb?.();
  }
});
  • 1catch (error) passes any sync or async failure straight to next(error).
  • 2finally runs await context.closeDb?.() after both success and error paths.

Three breaking changes in Express 5

Auto-forwarded Promises

Any async (req, res) function that throws or rejects automatically triggers the 4-argument error handler.

Named wildcards & ReDoS safety

Wildcards must be named, like /*splat instead of bare *. Tighter path rules also block ReDoS (a regex that takes forever on evil input).

req.query is a read-only getter

Uses a simpler query parser by default. It blocks deep prototype-polluting nested objects unless configured.

Interview answer

Why is upgrading from Express 4 to Express 5 a major architectural milestone?

1. Native async error propagation: Express 4 ignored Promises from async handlers. Without try / catch or express-async-errors, rejections crashed Node or hung the request. Express 5 catches returned Promises ("thenables") and calls next(err) automatically.

2. Hardened route matching: Bare * wildcards must now be named (such as /*splat). Path regex patterns were also tightened to prevent Regular Expression Denial of Service (ReDoS) attacks.

3. Safer req.query getter: req.query is read-only by default and uses a flat parser that blocks prototype-polluting nested objects.

1.4 TypeScript · Declaration Merging · Context Adapter

Type-safe request context

Never write (req as any).user. Use TypeScript declaration merging and a context adapter that forces every route to return a Web Response.

Real-world picture

Lazy database creation works like a motion-sensor room light. The light switches on only when the first person walks in, and stays on for everyone else in that visit.

Solution 1: Declaration merging instead of any

By default, TypeScript complains: Property 'user' does not exist on type 'Request'. Declaration merging fixes this cleanly across the entire project.

Casting (req as any).user

Silences the compiler by turning off type checking. Typos and missing checks slip into production.

→ destroys type safety across the codebase

declare global merging

Extends Express.Request in one place. Every route gets strict types and IDE autocomplete.

→ req.user, req.traceId, req.authSessionId are 100% typed

declare global {
  namespace Express {
    interface Request {
      user?: AuthenticatedUser;
      authSessionId?: string;
      traceId?: string;
      auditLogId?: string;
    }
  }
}
  • 1TypeScript merges this Request interface with @types/express automatically.
  • 2Properties are marked optional (?) because they are attached by middleware along the pipeline.

Solution 2: The context adapter pattern (createExpressRouter)

Instead of passing raw (req, res, next) into every route, src/routes/express-adapter.ts passes an ExpressRouteContext (c). The adapter builds standard Web responses with Response.json(body, { status }).

Raw res.json(body)

res.json() returns res, not a control-flow exit. Forgetting return lets code below it run and send headers twice.

→ accidental double-send at runtime

return c.json({ ok: true }, 200)

Handlers must return a Web Response object. TypeScript checks at compile time that every branch returns a response.

→ impossible to forget return or double-send

Lazy per-request database creation with ??=

Nullish coalescing assignment (db ??= getDb(bindings)) creates a DB client only when a route queries the database. Later calls in the same request reuse that single instance.

if (key === 'db') {
  db ??= getDb(bindings);
  return db;
}
  • 1??= assigns getDb(bindings) only when db is null or undefined.
  • 2Every later call in the same request gets the existing db instance immediately.

Interview answer

How do you pass per-request state in Express with TypeScript without using any, and why wrap Router() in an adapter?

1. TypeScript Declaration Merging: In src/middleware/auth.ts, declare global extends Express.Request with user, authSessionId, traceId, and auditLogId.

2. Compile-time return enforcement: Raw res.json() does not exit the function, making double-send bugs easy. Our ExpressRouteContext adapter requires every branch to return c.json(...) (a Web Response).

3. Lazy per-request DI: c.get('db') runs db ??= getDb(bindings). It creates one DB client only when needed, reuses it across the request, and closes it in finally.

1.5 Zero-Trust · Zod · Mass Assignment

Zero-trust validation

TypeScript types disappear at compile time. Incoming req.body, req.query, and req.params are unknown until a runtime Zod schema validates them.

Real-world picture

Zod at the HTTP boundary is passport control at a border. Writing as RegisterPayload is waving everyone through without checking their bags.

The HTTP border gate

Never write const body = req.body as RegisterPayload. A client can send objects or arrays instead of strings, plus "isAdmin": true, and runtime code will trust it.

export const workoutSessionCreateSchema = z
  .object({
    workoutPlanId: z.string().min(1),
    dayIndex: z.number().int().min(0),
    scheduledDate: z.string().min(1),
  })
  .strict(); // <-- Notice .strict()!
  • 1Every field enforces exact types and bounds (.min(1), .int().min(0)).
  • 2.strict() rejects the whole request if any extra key is present.

Why .strict() blocks Mass Assignment

Mass Assignment (Over-posting) happens when an attacker guesses internal database column names like role: "admin" or verified: true and sneaks them into a JSON payload.

Default z.object({ ... })

Silently strips unknown keys like role: "admin" and lets the request proceed without warning.

→ silent stripping hides over-posting attempts

z.object({ ... }).strict()

If the client sends role: "admin" or verified: true, Zod rejects the entire payload right at the door.

→ immediate 400 Bad Request

.parse() vs .safeParse() in parseJsonPayload

User input mistakes are routine, not unexpected crashes. PhysioCoach AI uses a discriminated union helper instead of throwing exceptions.

Method schema.parse(input) schema.safeParse(input)
On invalid input Throws a ZodError exception Returns { success: false, error }
Control flow Jumps to catch block via stack unwind Fast, explicit if (!parsed.success) branch 
const parsed = await parseJsonPayload(c, loginSchema);
if (!parsed.success) return parsed.response;
// Below this line, TypeScript knows `parsed.data` matches `loginSchema`!
  • 1parseJsonPayload handles malformed JSON or empty bodies without throwing.
  • 2Checking if (!parsed.success) narrows parsed.data to the exact Zod schema type.

Interview answer

Why is req.body as Payload unsafe, and why combine Zod .strict() with .safeParse()?

1. Zero-Trust boundary: TypeScript types vanish at compile time. An attacker can send {"email": {"$gt": ""}, "password": ["array_instead_of_string"], "isAdmin": true}. Treat req.body, req.query, and req.params as unknown until verified at runtime.

2. Preventing Mass Assignment with .strict(): Default Zod strips extra keys silently. .strict() rejects any request containing unknown fields like role: "admin" or verified: true with 400 Bad Request.

3. Explicit control flow with .safeParse(): Wrapped in parseJsonPayload(c, schema), .safeParse() returns a discriminated union instead of throwing exceptions on expected user validation errors.

1.6 Web Crypto · Dual Tokens · Reuse Detection

Senior-grade authentication

Anyone can say "I use JWT and bcrypt." Senior authentication closes four real attack vectors: timing side-channels, user enumeration, database leaks, and refresh token theft.

Real-world picture

Refresh tokens work like hotel key cards. The front desk gives you a new card each day and cancels yesterday's card. If someone swipes yesterday's card again, security locks the room right away.

The 4 security pillars in src/auth/ and src/routes/auth.ts

Pillar 1 · Web Crypto PBKDF2 & Constant-Time XOR

crypto.subtle PBKDF2-SHA256 (50,000 iterations) + timingSafeEqual byte XOR.

Pillar 2 · Anti-Enumeration Dummy Hash

Runs PBKDF2 against DUMMY_PASSWORD_HASH when an email does not exist so login always takes ~45 ms.

Pillar 3 · Dual-Token Architecture

15-minute stateless HS256 JWT + 32-byte refresh token stored only as a SHA-256 hash in auth_sessions.

Pillar 4 · Rotation, CAS & Reuse Detection

Every refresh rotates the token via atomic SQL Compare-And-Swap; reusing an old token revokes the session.

Pillar 1: Web Crypto PBKDF2-SHA256 & constant-time comparison

Native C++ bcrypt addons cannot run in serverless edge isolates like Cloudflare Workers and can block the Node thread pool. src/auth/password.ts uses standard crypto.subtle PBKDF2-SHA256 in a self-describing format:

Self-describing password hash format

pbkdf2 $ 50000 $ <base64-salt> $ <base64-hash>

function timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean {
  if (a.length !== b.length) {
    return false;
  }

  let diff = 0;
  for (let i = 0; i < a.length; i += 1) {
    diff |= a[i]! ^ b[i]!; // Bitwise XOR every single byte without short-circuiting!
  }

  return diff === 0;
}
  • 1a[i]! ^ b[i]! evaluates to 0 only when both bytes match.
  • 2diff |= ... accumulates any mismatch across the full array before returning diff === 0.

Pillar 2: Stopping user enumeration with DUMMY_PASSWORD_HASH

50,000 PBKDF2 iterations take ~30–50 ms of CPU time. If login returns 401 in 2 ms when user is null, attackers can test 100,000 emails. They can spot registered accounts by response time alone.

const DUMMY_PASSWORD_HASH =
  'pbkdf2$50000$AAAAAAAAAAAAAAAAAAAAAA==$2ffAJAWDOjK7twSNwuk4ViIEALV8TIAHNuZwB+zAsDo=';

const user = await getUserByEmail(db, normalizeEmail(parsed.data.email));
if (!user) {
  await verifyPassword(parsed.data.password, DUMMY_PASSWORD_HASH);
  return authRouteError(c, new AuthError('invalid_credentials', 'Invalid email or password.'));
}
  • 1When !user, the server still runs full 50,000-iteration PBKDF2 verification against DUMMY_PASSWORD_HASH.
  • 2The error code invalid_credentials and message Invalid email or password. match a wrong-password failure.

Pillar 3: Dual-token architecture

Stateless JWTs cannot be revoked before expiry without hitting a database on every request. PhysioCoach AI pairs a short-lived JWT access token with a hashed refresh token in PostgreSQL. If a database backup leaks, attackers get only SHA-256 hashes and cannot impersonate users.

Pillar 4: Refresh token rotation, reuse detection & atomic CAS

Following RFC 6819 / OAuth 2.0 Security Best Current Practice, every refresh invalidates the old token and issues a new one. Reusing a rotated token revokes the entire session.

Refresh Token Rotation & Theft Detection (src/auth/sessions.ts)

  1. 1

    Login issues Refresh Token R1

    Its SHA-256 hash is saved in auth_sessions and auth_refresh_token_history.

  2. 2

    Client refreshes with R1 → Server issues R2

    Server invalidates R1 (moves it to previousRefreshTokenHash) and sets R2 as active.

  3. 3

    Attacker (or client after theft) tries to use R1 again

    Server sees R1 is not the active token and checks auth_refresh_token_history.

  4. 4

    Server finds R1 belongs to Session S and revokes Session S

    Sets revokedAt = now immediately so neither thief nor old session can refresh again.

// Optimistic Concurrency Control (CAS - Compare-And-Swap in SQL)
const updated = await db
  .update(authSessions)
  .set({
    refreshTokenHash: nextHash,
    previousRefreshTokenHash: presentedHash,
    previousRefreshRotatedAt: nowIso,
    idleExpiresAt: nextIdle.toISOString(),
  })
  .where(
    and(
      eq(authSessions.id, session.id),
      eq(authSessions.refreshTokenHash, presentedHash), // MUST still hold the current hash!
      isNull(authSessions.revokedAt),
    ),
  )
  .returning({ id: authSessions.id });

if (updated.length === 0) {
  // Another concurrent request already rotated this token! Revoke the session.
  await revokeSession(db, session.id, nowIso);
  throw new AuthError('token_invalid', 'Refresh token is not valid.');
}
  • 1The WHERE clause requires refreshTokenHash === presentedHash and revokedAt IS NULL in one atomic SQL statement.
  • 2If updated.length === 0, another request already rotated the token, so the session is revoked immediately.

Trap · Concurrent Refresh Race

Two refreshes in the exact same millisecond

The SQL WHERE clause requires eq(authSessions.refreshTokenHash, presentedHash). The second request sees updated.length === 0, calls revokeSession(db, session.id, nowIso), and throws token_invalid.

Dual Expiry Windows

idleExpiresAt vs absoluteExpiresAt

idleExpiresAt Slides forward on every refresh
absoluteExpiresAt Hard cap → forces clean re-login

Interview answer

Why avoid native bcrypt and === on password hashes, and why verify against DUMMY_PASSWORD_HASH when a user is missing?

1. Edge compatibility: Native C++ bcrypt addons cannot run in Cloudflare Workers isolates and can block Node's thread pool. We use Web Crypto (crypto.subtle) PBKDF2-SHA256 with 50,000 iterations and a 16-byte salt (pbkdf2$50000$<base64-salt>$<base64-hash>).

2. Constant-time XOR (timingSafeEqual): Standard === exits at the first wrong byte, enabling Timing Attacks. timingSafeEqual XORs every byte (diff |= a[i]! ^ b[i]!) in constant CPU time.

3. Stopping User Enumeration: PBKDF2 takes ~30–50 ms, while an early 401 takes 2 ms. Running verifyPassword against DUMMY_PASSWORD_HASH (~45 ms) and returning Invalid email or password. hides whether an email exists.

Interview answer

Why not issue a 30-day JWT, and how do Refresh Token Rotation and Reuse Detection stop token theft?

1. Dual tokens & hashed storage: Stateless JWTs cannot be revoked before expiry. We pair a 15-minute HS256 JWT (<1 ms check) with a 32-byte refresh token stored only as a SHA-256 hash (refreshTokenHash) in auth_sessions. If a database backup leaks, attackers get only SHA-256 hashes and cannot impersonate users.

2. Rotation & Reuse Detection (RFC 6819): Refreshing with R1 invalidates R1 and issues R2. If anyone uses R1 again, the server spots R1 in auth_refresh_token_history and revokes the session (revokedAt = now).

3. Atomic CAS & Dual Expiry: SQL Compare-And-Swap (eq(authSessions.refreshTokenHash, presentedHash)) revokes the session on concurrent refreshes. Every session also enforces both sliding idleExpiresAt and a hard absoluteExpiresAt cap.
