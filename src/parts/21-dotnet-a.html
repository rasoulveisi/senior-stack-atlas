Why no generic repository (IRepository<T>)?

Key idea

EF Core's DbContext is already a Unit of Work (tracks changes for one save), and DbSet<T> is already a Repository.

Bad outcome 1: Hide IQueryable<T>

Twenty special interface methods

You cannot write custom .Select(...) projections, ILike filters, or pgvector cosine distance queries without bloating the interface.

Bad outcome 2: Expose IQueryable<T>

Leaky, pointless wrapper

Returning IQueryable<T> from your repository leaks EF Core to callers anyway and adds zero value.

Why no AutoMapper or MediatR?

AutoMapper & MediatR

Hidden mapping rules can crash at runtime when someone renames a property. Calling await _mediator.Send(new CreateApplicationCommand(...)) hides the target handler.

→ F12 jumps to a generic interface, not your code

Explicit mapper & direct service call

Writing new ApplicationDto(...) in ApplicationMapper.cs takes two minutes and is checked by the compiler. Endpoints call await service.CreateAsync(req, ct) directly.

→ F12 jumps straight to the implementation and shows every usage

Interview answer

How do you explain choosing Vertical Slices over Clean Architecture?

Team size and domain complexity decide the architecture. Clean Architecture with MediatR fits 50 developers working on complex decoupled pipelines.

Vertical slices fit most product APIs because each feature keeps its endpoint, DTOs, and service logic together in one folder.

Say it like a senior

"I choose architecture based on team size and domain complexity. Full Clean Architecture with MediatR is helpful when 50 developers work on complex decoupled pipelines. For most product APIs and microservices, Vertical Slices pair Minimal APIs with direct DbContext access and pure static Domain classes. This setup cuts boilerplate by 60% while keeping business rules 100% testable."

2.2 C# · .NET 10 · Clean Habits

Modern C# essentials

Five C# habits make net-angular compact, thread-safe, and fast under load.

Real-world picture

Passing a CancellationToken is telling the kitchen to stop cooking the moment the guest walks out of the restaurant.

Five habits interviewers look for

1. Primary constructors

Declare injected services right on the class header in ApplicationService.

2. Immutable records

Use public record for DTOs and value objects like EligibilityResult.

3. Pure static domain rules

FitScoring.cs and EligibilityRules.cs never touch DB, HTTP, or the clock.

4. Compiled regexes

static readonly regexes with RegexOptions.Compiled | RegexOptions.CultureInvariant.

5. CancellationToken everywhere

Forward ct from ApplicationEndpoints.cs to EF Core and HttpClient.

1. Primary constructors

public class ApplicationService(
    AppDbContext db,
    IDbContextFactory<AppDbContext> dbFactory,
    AnalysisService analysisService)
  • 1Dependencies sit right in the ApplicationService class declaration.
  • 2No private readonly fields and no 20-line constructor boilerplate.

Old 20-line constructor

Every dependency is typed three times: as a private readonly field, a constructor parameter, and an assignment line.

→ 20 lines of noise before business logic starts

Primary constructor

One header declares db, dbFactory, and analysisService for the whole class.

→ clean, compact header

2 & 3. Immutable records and pure static domain rules

Mutable classes & impure domain

Standard classes compare memory addresses on a == b and allow accidental mutation. Domain methods that call the database or clock need mocks to test.

→ fragile equality and slow, stateful tests

public record & pure static functions

EligibilityResult gives value equality (a == b compares fields) and safe with copies in EligibilityRules.MergeJev. FitScoring.cs and EligibilityRules.cs take strings and numbers in and return records out.

→ thread-safe, zero-allocation friendly, instant to test

4. Compiled regular expressions

Trap

new Regex(...) inside a loop or request handler

It recompiles the regex state machine on every call and allocates heavy memory on the Large Object Heap (LOH). The LOH is a special memory zone for large objects that is expensive to garbage-collect.

Per-call new Regex(...)

Parses the pattern and rebuilds the state machine every time a request or loop iteration runs.

→ CPU spikes + Large Object Heap pressure

static readonly in FitScoring.cs

Declared once with RegexOptions.Compiled | RegexOptions.CultureInvariant.

→ compiled once, reused across all requests

5. CancellationToken propagation

Every async method in ApplicationEndpoints.cs accepts CancellationToken ct from ASP.NET Core and passes it down to database and HTTP calls. Cancelling the in-flight SQL query or AI request saves CPU and database connections.

Interview answer

What modern C# habits do you use in production .NET 10 services?

Primary constructors and immutable records. Classes like ApplicationService avoid field boilerplate. Meanwhile, public record DTOs like EligibilityResult give value-based equality (a == b) and safe with updates (EligibilityRules.MergeJev).

Pure static domain rules, compiled regexes, and CancellationToken. 2.3 Dependency Injection · Lifetimes · Scopes

DI lifetimes

A long-lived service must never hold a shorter-lived service directly.

Real-world picture

A Scoped service is a library desk book meant to be returned after one visit. A captive dependency is one permanent resident locking that book in their room forever.

Transient, Scoped, and Singleton across two HTTP requests

Lifetime When it is created Real example in net-angular
Transient Every time you ask for it. Lightweight stateless helpers (rarely needed when using Scoped).
Scoped Once per HTTP request (or manual scope). AppDbContext, ApplicationService, EmbeddingIndex.
Singleton Once for the entire lifetime of the app. NpgsqlDataSource, RunQueue, DecisionThresholds.

The Captive Dependency trap

Trap

Captive AppDbContext inside a Singleton

Two concurrent requests or background tasks corrupt each other's tracked entities and throw InvalidOperationException: A second operation was started on this context instance.

Interview answer

What happens if you inject a Scoped service (like AppDbContext) into a Singleton service (like RunWorker : BackgroundService)?

It becomes a Captive Dependency. The Scoped service is trapped inside the Singleton forever and effectively becomes a Singleton.

DbContext is not thread-safe and caches tracked entities in memory. Two concurrent requests or background tasks will corrupt each other's state and throw InvalidOperationException: A second operation was started on this context instance.

The fix: Inject IServiceScopeFactory into the Singleton, create a manual scope per job with scopeFactory.CreateScope(), and resolve AppDbContext from that scope.

How RunWorker.cs resolves a clean scope per job

using var scope = scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
  • 1RunWorker is a Singleton (BackgroundService), so it injects IServiceScopeFactory instead of AppDbContext.
  • 2using var scope creates a fresh AppDbContext for one job and disposes it when the job finishes.

Key idea · Fresh error scope in RunWorker.cs (lines 49–59)

When a background job fails, the original AppDbContext may hold broken change-tracking state (such as a failed entity waiting to be inserted). The catch block creates a fresh error scope (using var errorScope = scopeFactory.CreateScope()) to cleanly save failedRun.Status = "failed".

2. Parallel queries with IDbContextFactory<AppDbContext>

Trap

One DbContext allows only one active operation

Running Task.WhenAll(db.Applications.ToListAsync(), db.Analyses.ToListAsync()) on the same AppDbContext crashes immediately because a single context instance cannot run concurrent queries.

private async Task<T> Query<T>(Func<AppDbContext, Task<T>> query)
{
    await using var context = await dbFactory.CreateDbContextAsync();
    return await query(context);
}
  • 1dbFactory.CreateDbContextAsync() spins up a lightweight context for a single query.
  • 2await using disposes the context and returns its connection to the pool as soon as the query finishes.

3. AsNoTracking() and global snake_case conventions

Tracked queries for read-only JSON

By default, EF Core takes a memory snapshot of every returned row to watch for updates that never happen on a GET endpoint.

→ wasted memory and CPU time

.AsNoTracking() in ApplicationService.cs

Every read query uses .AsNoTracking() so EF Core skips change-tracking snapshots when returning JSON to Angular.

→ lower memory usage and faster serialization

Manual [Column("created_at")] attributes

Littering every entity property with column attributes is noisy and easy to forget on new fields.

→ noisy entities and naming bugs

7-line loop in OnModelCreating (AppDbContext.cs)

One global model configuration loop converts every C# PascalCase property to PostgreSQL snake_case automatically.

→ clean C# entities, standard Postgres columns

Interview answer

How do you optimize EF Core against a remote cloud PostgreSQL database?

1. Warm the connection pool at startup. Configure NpgsqlDataSource with MinPoolSize = 8 and KeepAlive = 30 seconds. At startup, call WarmPoolAsync(dataSource) with Task.WhenAll so the first user avoids the 2–3 second cold TCP/TLS handshake.

2. Run independent reads in parallel with IDbContextFactory<AppDbContext>. A single DbContext allows only one active operation. Creating lightweight contexts per query turns six 40 ms sequential queries (240 ms) into one ~40 ms parallel batch.

3. Use .AsNoTracking() and global model conventions. Skip change-tracking snapshots on read-only queries and map PascalCase to snake_case in a 7-line OnModelCreating loop.

2.5 System.Threading.Channels · BackgroundService · Async Queue

Background jobs with Channel<T>

Queue long scans in memory with zero extra infrastructure while tracking status in PostgreSQL.

Real-world picture

Channel<T> is the order-ticket rail in a restaurant kitchen. The waiter clips the ticket on the rail and returns to the table; the cook pulls tickets one by one.

Trap

A 3-minute scan cannot block the HTTP request

When a user clicks "Start Scan" to crawl 50 company job boards, waiting synchronously inside the HTTP handler causes the request to time out.

Producer/consumer sequence across five lanes

Instead of adding RabbitMQ or Kafka for a single-node app, net-angular pairs System.Threading.Channels with a PostgreSQL runs table.

Two-class design: RunQueue.cs and RunWorker.cs

  1. 1

    RunQueue saves the database row first, then pushes to the channel

    RunQueue wraps Channel<QueuedRunItem>. When EnqueueAsync runs, it saves a Status = "queued" row in the runs table and pushes the work into the channel.

  2. 2

    RunWorker streams jobs with ReadAllAsync(stoppingToken)

    RunWorker inherits from BackgroundService and loops over await foreach (var item in queue.Reader.ReadAllAsync(stoppingToken)). It sleeps with zero CPU usage when the queue is empty and wakes up the instant an item arrives.

Choosing the right queue architecture

Question Channel<T> + runs table Hangfire / Quartz RabbitMQ / Service Bus + Outbox
Where data lives In-memory delegate + Postgres runs row Database tables Message broker + transactional outbox table
Survives restart? In-memory delegate lost; retry stale queued/running rows on startup Yes, automatic Yes, guaranteed delivery
Multi-node cluster? Single node only Yes, via DB locks Yes, built for distributed nodes

Interview answer

What is the trade-off of Channel<T> vs. Hangfire or RabbitMQ?

Channel<T> lives in memory. If the process crashes or restarts while a job is in the channel, that in-memory delegate is lost.

How net-angular mitigates it: Because we write a queued or running row to Postgres first, we can detect stale runs on startup and retry them.

When to step up: Move beyond Channel<T> in a multi-node cluster or when you need guaranteed delivery across restarts without custom recovery code. Use a database-backed queue like Hangfire or Quartz, or a message broker like RabbitMQ or Azure Service Bus. Pair the broker with the Transactional Outbox pattern by saving the outgoing message in the same database transaction before publishing.
