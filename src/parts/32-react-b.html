3.5 Async Params · cacheComponents · Suspense · Error Boundaries

App Router, streaming and error boundaries

Next.js 16 prerenders a static outer shell at build time and streams dynamic request holes through <Suspense>.

Real-world picture

A restaurant brings bread and water to your table at once while the main dish cooks in the kitchen.

Async params, searchParams and cacheComponents

In Next.js 15 and 16+, route params and searchParams are Promises. You do not read params.projectKey synchronously; you await params inside a <Suspense> boundary.

Key idea

params and searchParams are Promises. ProjectPage stays synchronous and passes the un-awaited Promises into <ProjectContent> inside <Suspense>.

export default function ProjectPage({
  params,
  searchParams,
}: PageProps<"/projects/[projectKey]">) {
  return (
    <main className="flex flex-col gap-6">
      <Suspense fallback={<ProjectPageSkeleton />}>
        <ProjectContent params={params} searchParams={searchParams} />
      </Suspense>
    </main>
  );
}
  • 1ProjectPage is synchronous because cacheComponents: true is enabled in next.config.ts.
  • 2Any request-time work (reading params, searchParams, headers(), cookies(), or uncached DB reads) must sit inside a <Suspense> boundary.

Nested <Suspense> streaming vs request waterfalls

ProjectContent awaits the project header (getProjectByKey) and immediately renders <header> plus a nested <Suspense fallback={<IssueListSkeleton />}> wrapping <IssueListSection>.

  1. 1

    Static outer shell arrives first

    Browser paints <main> and <ProjectPageSkeleton /> immediately.

  2. 2

    Project header and "New issue" button paint next

    getProjectByKey finishes; the browser renders the project title and "New issue" button while <IssueListSkeleton /> holds the table slot.

  3. 3

    Filtered issue table streams in last

    IssueListSection resolves listIssues and listAssignableUsers in parallel and swaps out <IssueListSkeleton />.

Waterfall: one await after another

await listIssues(...) finishes first. Only then does await listAssignableUsers(...) start.

→ you wait for the sum of both queries

Parallel: Promise.all

Both queries start together. For Angular developers: it works just like RxJS forkJoin.

→ you wait only for the slower query

const [page, users] = await Promise.all([
  listIssues(user, project.id, toIssueFilter(search)),
  listAssignableUsers(user),
]);
  • 1Both queries start at the same instant inside IssueListSection.
  • 2Writing await listIssues(...) and then await listAssignableUsers(...) would block the second query until the first finishes.

Granular error boundaries (SectionError vs error.tsx)

If listComments throws a database error, a page-level error.tsx would wipe out the entire Issue page. Wrapping <Comments> in SectionError (built with Next's catchError()) isolates the crash to the comments box.

<SectionError title="Comments">
  <Suspense fallback={<CommentsSkeleton />}>
    <Comments user={user} issueId={issue.id} />
  </Suspense>
</SectionError>
  • 1SectionError wraps the inner <Suspense> boundary so a database crash in Comments never reaches error.tsx.
  • 2requireUser() and notFound() in IssuePage run before this boundary starts streaming.

notFound() inside a streamed boundary

Once the outer <Suspense> shell flushes to the browser, HTTP headers (200 OK) are already sent. Next.js swaps in not-found.tsx UI and injects <meta name="robots" content="noindex">.

→ HTTP status stays 200 OK + noindex meta

notFound() before streaming starts

When notFound() runs before the outer shell flushes (or outside an inner streamed boundary), headers have not been sent yet.

→ real HTTP 404 status code

Senior interview questions

Interview answer · Q1

What happens to the HTTP status code when notFound() or forbidden() is called inside a streamed <Suspense> boundary vs. before streaming starts?

Inside a streamed boundary: Once the outer shell (<Suspense> fallback) flushes to the client, the HTTP headers are already sent with status 200 OK. When notFound() throws inside the streamed child later, Next.js swaps the fallback in the DOM with the not-found.tsx UI. It also injects <meta name="robots" content="noindex">, while the HTTP status code stays 200.

Before streaming starts: If notFound() runs before the shell flushes, Next.js returns an actual 404 HTTP status code.

Interview answer · Q2

Why do we use import "server-only" at the top of queries.ts, mutations.ts, and session.ts?

Build-time boundary protection: If a developer imports a database query module inside a "use client" file, Next.js fails the build immediately with a clear error.

This prevents bundling server code, database drivers, or environment secrets into the browser JavaScript bundle.

3.6 DAL · "use cache" · React.cache · updateTag

DAL and caching

Cache shared raw data across all users with "use cache", and compute per-user permissions outside the cache.

Real-world picture

A restaurant prints one shared menu for all guests, while the waiter checks each guest's allergies personally.

The Data Access Layer (DAL) pattern

Every query and mutation in src/features/*/ (docs/adr/0009-data-access-layer.md) enforces three strict rules.

Never import db in UI

React components never import db or Drizzle schemas directly.

actor: Actor comes first

Every query and mutation takes actor: Actor as its first parameter.

Return DTOs with viewerCan

Queries return clean DTOs with viewerCan: { edit, delete } computed via pure functions in permissions.ts.

How Next.js 16.4 "use cache" works (and why actor stays outside)

In a "use cache" function, Next.js automatically builds the cache key from the serialized arguments passed to the function (projectKey, issueNumber).

Trap · Security bug

Computing viewerCan inside "use cache" without passing actor

User B receives User A's cached viewerCan permissions! Always cache raw shared data and compute viewerCan outside "use cache".

export async function getIssue(
  actor: Actor,
  projectKey: string,
  issueNumber: number,
): Promise<IssueDetail | null> {
  const row = await cachedIssue(projectKey.toUpperCase(), issueNumber);
  if (!row) return null;

  // viewerCan depends on WHO is asking, so it is computed here, outside the
  // cache. The cached part is the same for everyone.
  const { reporterId, assigneeId, ...issue } = row;
  return {
    ...issue,
    viewerCan: {
      edit: can.editIssue(actor, { reporterId, assigneeId }),
      delete: can.deleteIssue(actor, { reporterId }),
    },
  };
}

async function cachedIssue(
  projectKey: string,
  issueNumber: number,
): Promise<CachedIssue | null> {
  "use cache";
  cacheLife("tracker");
  // ... DB query ...
  cacheTag(cacheTags.issue(row.id));
  return { ... };
}
  • 1cachedIssue caches the raw row by projectKey and issueNumber and tags it with cacheTags.issue(row.id).
  • 2getIssue strips reporterId and assigneeId and calculates viewerCan for the current actor.

Key idea · Normalize cache arguments

In listIssues, convert undefined and null into explicit strings ("any", "none") and call projectKey.toUpperCase() first. That way, equivalent requests always hit the same "use cache" key.

React.cache() vs "use cache"

Do not confuse React's per-request cache(fn) with Next.js's cross-request "use cache" directive.

export const getCurrentUser = cache(async (): Promise<CurrentUser | null> => {
  const session = await auth.api.getSession({ headers: await headers() });
  // ...
});
  • 1getCurrentUser reads request headers() and deduplicates the session lookup within a single HTTP request.
Feature React.cache(fn) (import { cache } from "react") "use cache" (Next.js Cache Components)
Lifetime One single server render pass (same HTTP request) Across requests and users via cacheLife("tracker") (stale, revalidate, expire)
Reads cookies / headers? Yes — ideal for getCurrentUser() No — reading cookies() or headers() throws
Invalidation Cleared automatically when the HTTP request ends Invalidated on writes via updateTag(tag) or revalidateTag(tag, "max")

Surgical cache invalidation on writes (updateTag)

When a Server Action mutates an issue, it calls invalidate.issueChanged(issue) to expire every affected tag immediately for read-your-own-writes consistency.

issueChanged(issue: { id: string; projectId: string }) {
  updateTag(cacheTags.issue(issue.id));                // the detail page
  updateTag(cacheTags.projectIssues(issue.projectId)); // title, status, updated time in the list
  updateTag(cacheTags.projects());                     // a status change moves the open-issue count
},
  • 1One helper centralizes the tag fan-out so no Server Action forgets a dependent view.

Senior interview questions

Interview answer · Q1

Explain the difference between React.cache and Next.js "use cache", and when you use both together.

React.cache (single request): Memoizes a function for the duration of a single request's render tree. If Layout, Page, and a child component all call getCurrentUser(), the session DB query runs only once for that request.

"use cache" (cross-request): Stores results in Next.js's cache shared across requests and users, controlled by cacheLife and cacheTag.

Using both together: "use cache" cannot read request-specific cookies(). We read the user outside with React.cache (getCurrentUser) and pass only non-user-specific arguments into "use cache" functions.

Interview answer · Q2

What is the difference between updateTag(tag) and revalidateTag(tag, "max") in Next.js 16?

updateTag(tag): Can only be called inside a Server Action. It expires the cache entry immediately so the next read in the same turn waits for fresh data (read-your-own-writes).

revalidateTag(tag, "max"): Used in Route Handlers or webhooks and performs stale-while-revalidate (serves stale data while refreshing in the background).

3.7 "use server" · HTTP POST · Zod · FormState · redirect()

Server Actions and security

When a file starts with "use server", Next.js creates a public HTTP POST endpoint for every exported function.

Real-world picture

A Server Action is a shop's back door. It must stay locked and checked even if no sign on the street points to it.

The 5-step security checklist in updateIssueAction

Every Server Action in src/features/issues/actions.ts treats the caller as untrusted and executes five steps in order.

5-step checklist · updateIssueAction

01

Authenticate

await requireUser() checks session.

02

Validate with Zod

EditIssueInput.safeParse.

03

Authorize + mutate

DAL checks can.editIssue.

04

Expire cache tags

invalidate.issueChanged.

05

Redirect outside

After try/catch block!

export async function updateIssueAction(
  issueId: string,
  _prev: FormState,
  formData: FormData,
): Promise<FormState> {
  // 1. Authenticate the caller (never trust that the button was hidden in UI)
  const user = await requireUser();

  // 2. Validate form data with Zod
  const values = formValues(formData);
  const parsed = EditIssueInput.safeParse(values);
  if (!parsed.success) return invalid(values, parsed.error);

  // 3. Authorize & mutate inside the DAL (checks can.editIssue)
  let issue;
  try {
    issue = await updateIssue(user, issueId, parsed.data);
  } catch (error) {
    return failed(values, error);
  }

  // 4. Expire affected cache tags
  invalidate.issueChanged(issue);

  // 5. Redirect OUTSIDE try/catch!
  redirect(`/projects/${issue.projectKey}/issues/${issue.number}` as Route);
}
  • 1requireUser(), EditIssueInput.safeParse(), and updateIssue() enforce authentication, schema validation, and can.editIssue authorization on the server.
  • 2The marked line places redirect() outside the try/catch block so catch cannot swallow the redirect exception.

Three traps every senior candidate must know

Bound arguments, redirect() exceptions, and validation errors behave differently from client-side routers.

Trap 1 · Bound arguments are untrusted input

updateIssueAction.bind(null, issue.id) is serialized into hidden HTML form fields

An attacker can edit that hidden field in browser DevTools and submit the form. Always validate bound arguments with Zod (Id.safeParse(projectId)) and check permissions inside the database mutation.

Trap 2 · redirect() throws NEXT_REDIRECT

Putting redirect() inside try { ... } catch (err) { return failed(...) } swallows the redirect

redirect() and notFound() throw an internal control-flow exception so React stops rendering immediately. A surrounding catch block intercepts it and turns a successful save into an error message.

Angular habit · Inside try / catch

In Angular, this.router.navigate(...) returns a normal Promise. In Next.js, calling redirect() inside try/catch catches NEXT_REDIRECT and runs return failed(values, error).

→ save succeeds, but UI shows an error

Next.js way · After try / catch

Call redirect() after the try/catch block (or call unstable_rethrow(err) inside catch) so Next.js catches NEXT_REDIRECT at the framework level.

→ sends 303 redirect / client navigation

Trap 3 · Expected validation errors must be returned as FormState values

Throwing a validation error triggers error.tsx and destroys what the user typed

Return { values, fieldErrors, message } into useActionState instead. IssueForm then preserves typed values (const v = { ...defaults, ...state.values }) and displays inline field errors.

Wrong: Throw validation error

Throwing from a Server Action jumps to the nearest error.tsx boundary and unmounts IssueForm.

→ error.tsx replaces form; typed values lost

Right: Return FormState value

Return invalid(values, parsed.error) as { values, fieldErrors, message } into useActionState.

→ form stays mounted with inline fieldErrors

Senior interview questions

Interview answer · Q1

Why does redirect() fail when placed inside a try/catch block in a Server Action?

redirect() throws NEXT_REDIRECT: In Next.js, redirect() does not return a value. It throws a special internal error (NEXT_REDIRECT). Next.js catches that error higher up to send a 303 redirect header or stream a client router navigation.

How to fix it: Putting redirect() inside try/catch intercepts that exception. Either place redirect() after the try/catch block or call unstable_rethrow(err) inside catch.

Interview answer · Q2

Does myAction.bind(null, secretId) keep secretId secret on the server?

No. Next.js sends bound arguments to the client in hidden form fields so the browser can send them back when the form is submitted.

Never pass secrets to .bind(), and always validate and authorize bound IDs on the server just like FormData fields.

3.8 Defense-in-Depth · proxy.ts · Session Cache · PGlite · Playwright

Auth defense-in-depth and testing

Layouts never gate authentication. Next Issue Tracker enforces three security layers and verifies them with a four-layer test pyramid using zero database mocks.

Real-world picture

A bank has a door guard, a counter clerk who checks your ID, and a vault with its own key.

Why layouts never gate authentication

Putting authentication checks only inside layout.tsx is a critical security vulnerability in Next.js App Router (docs/adr/0012-session-strategy.md).

Angular habit: Parent canActivate

In Angular, putting canActivate: [authGuard] on a parent route protects every child route. Trying to do the same in Next.js layout.tsx leaves child pages and actions exposed.

→ layout auth check is bypassed

Next.js way: 3-layer defense-in-depth

Check cookie existence in proxy.ts, validate the DB session with requireUser() in every page and action, and enforce can.* rules in the DAL.

→ every page and action verifies auth

Defense-in-depth across 3 layers

Authentication and authorization run at three concentric layers on the server.

1. src/proxy.ts · Cookie exists check (no DB)
2. Page & Action · requireUser / requireAdmin (React.cache DB session)
3. DAL · queries.ts / mutations.ts + permissions.ts (can.editIssue before SQL)

1. src/proxy.ts

Called middleware.ts prior to Next 16. Fast, optimistic check that verifies a session cookie exists (getSessionCookie(request)) and redirects anonymous visitors. No DB call here.

2. Page & Action (session.ts)

requireUser and requireAdmin validate the session token against the PostgreSQL sessions table, deduplicated per request via React.cache.

3. DAL (permissions.ts)

queries.ts and mutations.ts check role and ownership (can.editIssue(actor, row)) right before reading or writing SQL.

The 4-layer testing pyramid (zero database mocks)

Instead of mocking SQL queries, integration tests run real Drizzle migrations on in-memory PGlite (Postgres compiled to WASM; docs/adr/0010-integration-tests-pglite.md). Playwright E2E tests run against a production build (docs/adr/0006-testing-strategy.md).

4. Playwright E2E · next build && next start
3. DB & Action Integration · in-memory PGlite (*.int.test.ts)
2. Client Components & Hooks · Testing Library (*.test.tsx)
1. Unit · pure functions, Zod & URL parsers (*.test.ts)

1. Unit tests (*.test.ts)

Pure functions, Zod schemas, and URL search param parsers: permissions.test.ts and search-params.test.ts.

2. Client Components & Hooks (*.test.tsx)

Testing Library + userEvent + fake timers: comment-thread.test.tsx and use-debounced-callback.test.tsx.

3. DB & Action integration (*.int.test.ts)

Runs real Drizzle SQL migrations and queries against in-memory PGlite (WASM Postgres, zero mocked SQL). issues/actions.int.test.ts asserts exact updateTag() calls and redirect() targets.

4. Playwright E2E (e2e/)

Runs against a real next build && next start production build to test Server Components, streaming, caching, and React <Activity> DOM retention.

Senior interview questions

Interview answer · Q1

An Angular architect moving to Next.js suggests checking the user's session in src/app/(app)/layout.tsx so individual pages don't have to. How do you respond in a design review?

Reject that design. In Next.js App Router, layouts do not re-execute on client-side navigations between child routes. Pages also stream independently of layouts, and Server Actions bypass layouts completely.

Where auth belongs: Layout checks are only for displaying user UI (like the navbar avatar). Real authentication and authorization must happen in every page's data access calls and inside every Server Action.

Interview answer · Q2

Why can't you unit-test an async Server Component that uses <Suspense> and "use cache" in Vitest + Testing Library?

Missing server runtime in JSDOM: Testing Library's render() runs in a client-like JSDOM environment. It lacks Next.js's RSC stream serializer, "use cache" runtime, and server request context (headers(), cookies()).

Cleanest test split: Test data queries and Server Actions directly in fast integration tests with in-memory PGlite. Then test async Server Component pages end-to-end with Playwright against a production build.
