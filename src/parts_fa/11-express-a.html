1.1 Node.js HTTP · Express · آداپتورهای لبه (Edge)

زیر کاپوت اکسپرس

فراخوانی express() یک تابع جاوااسکریپتی معمولی با ساختار (req, res) => void بازمی‌گرداند. سرور HTTP نود این تابع را به ازای هر درخواست صدا می‌زند. اکسپرس همچنین متدهایی چون app.use() و app.get() را به آن ضمیمه می‌کند تا این تابع را پیکربندی نماید.

در دنیای واقعی

ماژول http.Server نود مانند یک ساختمان اداری است که درب ورودی را باز می‌کند. تابع app(req, res) در اکسپرس همان متصدی پذیرشی است که به هر مراجعه‌کننده خوش‌آمد گفته و او را به بخش مربوطه هدایت می‌کند.

نحوه اجرای اکسپرس در Cloudflare Workers

سرویس PhysioCoach AI با استفاده از وب استانداردهای API fetch(request, env, ctx) درون Cloudflare Workers اجرا می‌شود. یک پل ارتباطی بسیار کوچک شیء Request وب را به یک فراخوانی سوکت نود برای اکسپرس تبدیل می‌کند.

import { httpServerHandler } from 'cloudflare:node';
import { createServer } from 'node:http';
import { createApp } from './app';
import type { WorkerBindings } from './env';

const app = createApp();
const server = createServer(app);
const nodeHandler = httpServerHandler(server as unknown as Parameters<typeof httpServerHandler>[0]);

export default {
  async fetch(request: Request, env: WorkerBindings, ctx: ExecutionContext): Promise<Response> {
    // Inject Cloudflare per-request environment bindings (Hyperdrive DB, secrets) into Express
    app.locals.workerEnv = env;
    return (nodeHandler as { fetch: (req: Request, env: unknown, ctx: unknown) => Promise<Response> }).fetch(
      request,
      env,
      ctx,
    );
  },
};
  • 1createServer(app) تابع اکسپرس را مستقیماً به سرور HTTP نود تحویل می‌دهد.
  • 2httpServerHandler رویداد fetch کلودفلر را به سرور نود پل می‌زند.
  • 3app.locals.workerEnv = env سکرت‌ها و اتصالات دیتابیس Hyperdrive را در اختیار اکسپرس قرار می‌دهد.

چرا app.ts و index.ts از هم جدا هستند؟

فایل src/app.ts نمونه برنامه اکسپرس را از طریق createApp() می‌سازد، در حالی که src/index.ts آن را به محیط اجرای شبکه متصل می‌کند.

بدون خطای EADDRINUSE در تست‌ها

هر تست موازی بدون اشغال پورت 8787 تابع createApp() را صدا می‌زند.

آماده برای محیط‌های لبه (Edge)

فایل src/index.ts برنامه را در دل تابع fetch() ورکر کلودفلر قرار می‌دهد.

قابلیت حمل به Docker و Node استاندارد

دقیقاً همین برنامه بدون تغییر با دستور app.listen(8787) روی کانتینر لینوکس اجرا می‌شود.

برای استریم بدنه درخواست‌های POST چه اتفاقی می‌افتد؟

هنگامی که کلاینت یک درخواست POST حاوی JSON ارسال می‌کند، بدنه درخواست بلافاصله در دسترس نیست.

  1. 1

    بایت‌های خام به صورت قطعه‌قطعه روی یک استریم TCP دریافت می‌شوند

    نود این استریم خواندنی را درون یک شیء http.IncomingMessage (req) بسته‌بندی می‌کند.

  2. 2

    خصوصیت req.body هنوز وجود ندارد

    خواندن استریم شبکه عملیاتی ناهمگام است و تا زمانی که بادی‌پارسر قطعات را سرهم کند زمان می‌برد.

  3. 3

    اکسپرس پروتوتایپ‌های جاوااسکریپت را ارتقا می‌دهد

    اکسپرس با استفاده از Object.setPrototypeOf پروتوتایپ‌های express.request و express.response را متصل کرده و متدهایی چون req.header()، res.status() و res.json() را می‌افزاید.

پاسخ مصاحبه

تفاوت بین app.locals، res.locals و الصاق ویژگی‌ها به req چیست؟

طول عمر app.locals برابر با کل پروسه یا ایزوله سرور است. از آن برای پیکربندی‌های سراسری یا اتصالات محیطی (Environment Bindings) استفاده کنید.

هشدار شرایط رقابتی (Race Condition): در یک سرور نود با درخواست‌های هم‌زمان، تغییر دادن مقادیر app.locals به ازای هر درخواست، منجر به تداخل داده در درخواست‌های هم‌پوشان می‌شود. وضعیت‌های مختص به هر درخواست را همیشه روی req یا res.locals قرار دهید.

طول عمر req و res.locals فقط به اندازه یک درخواست HTTP است. به محض پایان پاسخ‌دهی، حافظه آن‌ها توسط زباله‌روب (Garbage Collector) آزاد می‌شود. قرار دادن req.user یا req.traceId روی شیء req تضمین می‌کند که داده‌های کاربر الف هرگز به درخواست هم‌زمان کاربر ب درز نکند.

طول عمر پروسه / ایزوله

app.locals

بین تمام درخواست‌ها مشترک است. تغییر آن به ازای هر درخواست خطر ایجاد Race Condition دارد.

طول عمر یک درخواست HTTP

req و res.locals

به ازای هر بازدیدکننده ایزوله بوده و بلافاصله پس از اتمام پاسخ از حافظه پاک می‌شود.

1.2 خط لوله · ترتیب فراخوانی · امنیت با پیش‌فرض مسدود

ترتیب اجرا، همان معماری است

اکسپرس تنها یک مدل ذهنی دارد: یک آرایه مرتب از توابع. وقتی درخواستی می‌رسد، اکسپرس از ایندکس 0 آغاز کرده و هر تابع را به ترتیب فراخوانی می‌کند.

دام پروداکشن

فراخوانی next() پس از res.json()

میان‌افزار بعدی تلاش می‌کند پاسخ دومی ارسال کند. سرور نود با خطای Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client متوقف می‌شود. همیشه بنویسید: return res.json(...)!

سرهم‌بندی خط لوله در کد

export function createApp(): TestableExpressApp {
  const app = express();

  app.use(cors());          // 1. Fast OPTIONS preflight
  app.use(express.json());  // 2. Parse JSON stream into req.body

  // 3. Distributed Trace ID (before auth so 401s still get a traceId!)
  app.use((req, res, next) => {
    req.traceId = req.header('x-request-id') || crypto.randomUUID();
    res.setHeader('x-request-id', req.traceId);
    next();
  });

  // 4. Global Authentication gate
  app.use(authMiddleware);

  // 5. Backward-compatible URL aliasing middleware
  app.use('/api/v1', (req, _res, next) => {
    const aliases: Record<string, string> = {
      '/profiles': '/profile',
      '/workout-plans/active': '/workout-plans/current',
      '/auth/google/exchange': '/auth/oauth/exchange',
      '/exercises': '/exercise-catalog/exercises',
    };
    const queryIndex = req.url.indexOf('?');
    const path = queryIndex >= 0 ? req.url.slice(0, queryIndex) : req.url;
    const query = queryIndex >= 0 ? req.url.slice(queryIndex) : '';
    const target = aliases[path];
    if (target) req.url = `${target}${query}`;
    next();
  });

  // 6. Feature Routers mounted under /api/v1
  app.use('/api/v1', healthRouter);
  app.use('/api/v1', authRouter);
  // ... profilesRouter, assessmentsRouter, workoutPlansRouter, workoutSessionsRouter

  // 7. Central Error Funnel (MUST BE LAST)
  app.use(errorHandler);
  return testableApp;
}
  • 1شناسه ردیابی Trace ID در مرحله ۳ قبل از authMiddleware در مرحله ۴ اجرا می‌شود.
  • 2مرحله ۵ مسیرهای قدیمی را در حافظه بازنویسی کرده و در عین حال Query Stringها را حفظ می‌کند.
  • 3میان‌افزار errorHandler در آخرین ردیف ثبت شده تا خطاهای ناشی از تمام گام‌های بالادستی را دریافت کند.

پاسخ مصاحبه

چرا از یک authMiddleware سراسری با لیست سفید مسیرهای عمومی استفاده می‌کنیم، به جای اینکه آن را تک‌تک روی روت‌ها قرار دهیم؟

امنیت با پیش‌فرض مسدود (Fail-Closed / Secure by Default). هر اندپوینت جدیدی که افزوده شود، به شکل خودکار محافظت‌شده خواهد بود.

با داشتن بیش از ۴۰ اندپوینت روی ۱۰ روتر مختلف، افزودن دستی router.post('/secret', authMiddleware, handler) به شدت مستعد خطاست. در نهایت برنامه‌نویسی یک مسیر را فراموش کرده و داده‌های خصوصی در معرض دید عموم قرار می‌گیرند.

سوار کردن authMiddleware به صورت سراسری در src/app.ts به همراه لیست صریح PUBLIC_PATHS در src/middleware/auth.ts این خطر را به کلی برطرف می‌سازد.

1.3 Express 5 · خطاهای ناهمگام (Async Errors) · مسیریابی

مقایسه Express 4 و Express 5

پروژه PhysioCoach AI روی "express": "^5.0.0" اجرا می‌شود. اکسپرس ۵ بررسی می‌کند که آیا یک هندلر Promise برمی‌گرداند یا خیر و رد شدن پرامیس‌ها (Rejections) را به صورت خودکار به next(err) ارسال می‌کند.

در دنیای واقعی

اکسپرس ۵ مثل بستن تور نجات زیر پای بندباز است. در اکسپرس ۴، اگر یک هندلر async بدون تور نجات خودش سقوط می‌کرد، مستقیماً به زمین می‌خورد و سرور از کار می‌افتاد.

وقتی یک دستور await دچار خطا می‌شود چه اتفاقی می‌افتد؟

اکسپرس ۴ قبل از پیدایش async/await در جاوااسکریپت ساخته شده بود. اکسپرس ۵ ذاتاً پرامیس‌ها (Thenables) را درک می‌کند.

Express 4

هندلرها را به صورت همگام صدا می‌زند. اگر یک await رد شود و شما try / catch یا پکیج express-async-errors را فراموش کرده باشید، هیچ‌کس پرامیس ردشده را مهار نمی‌کند.

← خطای unhandled rejection باعث کرش نود یا معلق ماندن درخواست می‌شود

Express 5

هسته روتر بررسی می‌کند که آیا هندلر Promise برگردانده است یا خیر. به محض Reject شدن، اکسپرس آن را به دام انداخته و خودش next(err) را صدا می‌زند.

← تابع مدیریت خطای ۴ آرگومانی یک پاسخ تمیز JSON برمی‌گرداند

پاک‌سازی تضمینی اتصالات دیتابیس با بلوک finally

سرویس PhysioCoach AI اکسپرس ۵ را با یک آداپتور سفارشی روتر ترکیب کرده تا اطمینان حاصل کند اتصالات دیتابیس همواره بسته می‌شوند، حتی اگر در مسیر خطایی رخ دهد.

register(path, async (req, res, next) => {
  const context = createRouteContext(req, res);
  try {
    const response = await handler(context);
    await sendWebResponse(res, response);
  } catch (error) {
    next(error); // Forward any thrown error or rejected promise to errorHandler
  } finally {
    await context.closeDb?.();
  }
});
  • 1بلوک catch (error) هرگونه خطای همگام یا ناهمگام را مستقیماً به next(error) می‌فرستد.
  • 2بلوک finally دستور await context.closeDb?.() را هم در مسیر موفقیت و هم در مسیر خطا بدون استثنا اجرا می‌کند.

سه تغییر ساختاری و ناسازگار در Express 5

هدایت خودکار پرامیس‌ها

هر تابع async (req, res) که خطایی پرتاب کند یا رد شود، به طور خودکار هندلر خطای ۴ آرگومانی را فعال می‌کند.

وایلدکارت‌های نام‌دار و امنیت ReDoS

کاراکترهای وایلدکارت باید نام‌گذاری شوند، مثل /*splat به جای * خالی. قوانین سخت‌گیرانه‌تر مسیرها همچنین حملات ReDoS (رجکس‌هایی که روی ورودی مخرب معلق می‌مانند) را مسدود می‌سازد.

متد req.query به صورت Getter فقط‌خواندنی است

به صورت پیش‌فرض از پارسر ساده‌تری استفاده می‌کند. این تغییر اشیای تودرتوی مخرب که قصد آلودگی پروتوتایپ (Prototype Pollution) دارند را مسدود می‌سازد.

پاسخ مصاحبه

چرا ارتقا از Express 4 به Express 5 یک دستاورد معماری مهم به شمار می‌رود؟

۱. انتشار بومی خطاهای ناهمگام (Native Async Error Propagation): اکسپرس ۴ پرامیس‌های بازگردانده شده از هندلرهای async را نادیده می‌گرفت. بدون try / catch یا پکیج express-async-errors، پرامیس‌های رد شده سرور نود را متوقف یا درخواست را معلق می‌کردند. اکسپرس ۵ پرامیس‌ها (Thenables) را دریافت کرده و به شکل خودکار next(err) را صدا می‌زند.

۲. تطبیق امن‌تر مسیرها (Hardened Route Matching): وایلدکارت‌های ستاره خالی * اکنون باید نام داشته باشند (مانند /*splat). الگوهای رجکس مسیرها نیز برای جلوگیری از حملات منع سرویس با عبارات باقاعده (ReDoS) مستحکم شده‌اند.

۳. گتر امن‌تر برای req.query: پارامترهای کوئری به طور پیش‌فرض فقط‌خواندنی هستند و از یک پارسر مسطح استفاده می‌کنند که از نفوذ اشیای تودرتو و آلودگی پروتوتایپ جلوگیری می‌نماید.

1.4 TypeScript · ادغام اعلان‌ها (Declaration Merging) · آداپتور Context

کانتکست درخواست با امنیت کامل انواع داده

هرگز ننویسید (req as any).user. از ادغام اعلان‌های تایپ‌اسکریپت (Declaration Merging) و یک آداپتور کانتکست استفاده کنید که هر روت را موظف می‌کند یک شیء Response استاندارد وب برگرداند.

در دنیای واقعی

ساخت تنبل (Lazy) دیتابیس درست مثل چراغ مجهز به سنسور حرکتی کار می‌کند. چراغ فقط زمانی روشن می‌شود که اولین نفر وارد اتاق شود، و برای بقیه مراجعان در همان حضور روشن می‌ماند.

راهکار ۱: ادغام اعلان‌ها به جای تایپ‌کست به any

تایپ‌اسکریپت به صورت پیش‌فرض خطا می‌دهد: Property 'user' does not exist on type 'Request'. ادغام اعلان‌ها این مشکل را به شکلی تمیز در کل پروژه برطرف می‌سازد.

کست کردن با (req as any).user

کامپایلر را با خاموش کردن سیستم بررسی نوع بی‌صدا می‌کند. خطاهای املایی و بررسی‌های فراموش‌شده به محیط پروداکشن درز می‌کنند.

← امنیت نوع داده (Type Safety) در تمام کدها از بین می‌رود

ادغام اعلان‌ها با declare global

اینترفیس Express.Request را در یک نقطه توسعه می‌دهد. همه روت‌ها بررسی نوع دقیق و تکمیل خودکار هوشمند IDE را دریافت می‌کنند.

← فیلدهای req.user، req.traceId و req.authSessionId صددرصد تایپ‌شده هستند

راهکار ۲: الگوی آداپتور کانتکست (createExpressRouter)

پاسخ مصاحبه

چگونه وضعیت‌های اختصاصی هر درخواست را در اکسپرس با TypeScript و بدون استفاده از any منتقل می‌کنید، و چرا Router() را در یک آداپتور می‌پیچید؟

۱. ادغام اعلان‌ها در تایپ‌اسکریپت (Declaration Merging): در فایل src/middleware/auth.ts، با دستور declare global اینترفیس Express.Request را گسترش داده و فیلدهای user، authSessionId، traceId و auditLogId را با تایپ دقیق تعریف می‌کنیم.

1.5 عدم اعتماد مطلق (Zero-Trust) · Zod · انتساب انبوه (Mass Assignment)

اعتبارسنجی با عدم اعتماد مطلق

تایپ‌های تایپ‌اسکریپت در زمان کامپایل ناپدید می‌شوند. فیلدهای ورودی req.body، req.query و req.params کاملاً unknown هستند تا زمانی که یک اسکیما در زمان اجرا صحت آن‌ها را تأیید کند.

در دنیای واقعی

استفاده از Zod در مرز HTTP مانند گیت کنترل گذرنامه در مرز کشور است. نوشتن as RegisterPayload مانند این است که بدون بازرسی بار و چمدان‌ها، به همه اجازه ورود بدهید.

گیت مرزی درخواست‌های HTTP

هرگز ننویسید const body = req.body as RegisterPayload. کلاینت می‌تواند به جای رشته، اشیاء یا آرایه‌ها را ارسال کند و همچنین فیلد "isAdmin": true را بگنجاند، و کدهای زمان اجرا به اشتباه به آن اعتماد خواهند کرد.

export const workoutSessionCreateSchema = z
  .object({
    workoutPlanId: z.string().min(1),
    dayIndex: z.number().int().min(0),
    scheduledDate: z.string().min(1),
  })
  .strict(); // <-- Notice .strict()!
  • 1هر فیلد نوع دقیق و محدوده‌های مجاز را اعتبارسنجی می‌کند (.min(1)، .int().min(0)).
  • 2متد .strict() در صورت وجود هرگونه کلید ناشناخته، کل درخواست را بلافاصله رد می‌کند.

چرا متد .strict() جلوی انتساب انبوه (Mass Assignment) را می‌گیرد؟

حمله انتساب انبوه (Over-posting) زمانی رخ می‌دهد که مهاجم ستون‌های داخلی دیتابیس مانند role: "admin" یا verified: true را حدس زده و آن‌ها را مخفیانه در پی‌لود JSON جا می‌دهد.

رفتار پیش‌فرض z.object({ ... })

کلیدهای ناشناخته مثل role: "admin" را در سکوت حذف کرده و اجازه ادامه درخواست را بدون هیچ هشداری صادر می‌کند.

استفاده از z.object({ ... }).strict()

اگر کلاینت فیلدهایی چون role: "admin" یا verified: true بفرستد، Zod بلافاصله کل درخواست را در بدو ورود متوقف می‌سازد.

مقایسه .parse() و .safeParse() در تابع parseJsonPayload

اشتباهات ورودی کاربر اتفاقی روزمره هستند، نه یک فاجعه و کرش غیرمنتظره. سیستم PhysioCoach AI به جای پرتاب استثنا از یک هلپر با ساختار Discriminated Union استفاده می‌کند.

پاسخ مصاحبه

چرا نوشتن req.body as Payload ناامن است، و چرا باید .strict() را با .safeParse() در Zod ترکیب کرد؟

۱. مرز عدم اعتماد مطلق (Zero-Trust): تایپ‌های تایپ‌اسکریپت پس از کامپایل از بین می‌روند. یک مهاجم می‌تواند مقادیر نامتعارفی چون {"email": {"$gt": ""}, "password": ["array_instead_of_string"], "isAdmin": true} ارسال کند. با فیلدهای req.body، req.query و req.params تا زمان اعتبارسنجی در زمان اجرا باید به عنوان unknown رفتار شود.

۲. جلوگیری از انتساب انبوه با .strict(): حالت پیش‌فرض Zod فیلدهای اضافه را بی‌صدا حذف می‌کند. فراخوانی .strict() هر درخواستی که حاوی کلیدهای ناشناخته نظیر role: "admin" یا verified: true باشد را با خطای 400 Bad Request رد می‌کند.

۳. کنترل جریان صریح با .safeParse(): استفاده از آن در تابع parseJsonPayload(c, schema) یک حاصل Discriminated Union تمیز تولید می‌کند و مانع از پرتاب استثناهای پرهزینه به ازای خطاهای ورودی عادی کاربران می‌شود.

1.6 رمزنگاری تحت وب · توکن دوگانه · شناسایی استفاده مجدد

احراز هویت در تراز مهندسی ارشد

هر کسی می‌تواند بگوید «من از JWT و bcrypt استفاده می‌کنم». احراز هویت در سطح سنیور چهار بردار حمله واقعی را خنثی می‌کند: کانال‌های جانبی زمان‌بندی (Timing Side-Channels)، سرشماری کاربران (User Enumeration)، لو رفتن دیتابیس، و سرقت توکن رفرش.

در دنیای واقعی

توکن‌های رفرش درست مانند کارت کلید اتاق هتل عمل می‌کنند. پذیرش هر روز یک کارت جدید به شما می‌دهد و کارت دیروز را باطل می‌کند. اگر کسی مجدداً کارت دیروز را بکشد، حراست بی‌درنگ درب اتاق را قفل امنیتی خواهد کرد.

۴ ستون امنیتی در src/auth/ و src/routes/auth.ts

ستون ۱ · وب کریپتو PBKDF2 و مقایسه XOR با زمان ثابت

ستون ۲ · هش ساختگی برای جلوگیری از سرشماری کاربران

اجرای PBKDF2 روی DUMMY_PASSWORD_HASH در صورت عدم وجود ایمیل، تا زمان لاگین همواره حدود ۴۵ میلی‌ثانیه طول بکشد.

ستون ۳ · معماری توکن دوگانه (Dual-Token)

ستون ۱: وب کریپتو PBKDF2-SHA256 و مقایسه در زمان ثابت

ماژول‌های نیتیو C++ نظیر bcrypt روی محیط‌های ایزوله بدون سرور لبه (Edge) مانند Cloudflare Workers قابل اجرا نیستند و می‌توانند Thread Pool نود را مسدود کنند. فایل src/auth/password.ts از استاندارد crypto.subtle PBKDF2-SHA256 در قالب یک ساختار خودتوصیف استفاده می‌کند:

ساختار خودتوصیف هش رمز عبور

pbkdf2 $ 50000 $ <base64-salt> $ <base64-hash>

الگوریتم · تعداد تکرار · نمک تصادفی ۱۶ بایتی به ازای هر کاربر · کلید مشتق‌شده با SHA-256.

نمک تصادفی رمزنگاری‌شده

توکن رفرش مات (Opaque)

function timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean {
  if (a.length !== b.length) {
    return false;
  }

  let diff = 0;
  for (let i = 0; i < a.length; i += 1) {
    diff |= a[i]! ^ b[i]!; // Bitwise XOR every single byte without short-circuiting!
  }

  return diff === 0;
}
  • 1عبارت a[i]! ^ b[i]! تنها زمانی مقدار 0 می‌دهد که هر دو بایت کاملاً یکسان باشند.
  • 2دستور diff |= ... هرگونه عدم تطابق را در طول کل آرایه انباشته کرده و در انتها عبارت diff === 0 را ارزیابی می‌کند.

ستون ۲: جلوگیری از سرشماری کاربران با DUMMY_PASSWORD_HASH

انجام ۵۰,۰۰۰ تکرار PBKDF2 حدود ۳۰ الی ۵۰ میلی‌ثانیه از پردازنده زمان می‌برد. اگر لاگین در صورت null بودن کاربر در عرض ۲ میلی‌ثانیه خطای 401 برگرداند، مهاجم می‌تواند با تست ۱۰۰,۰۰۰ ایمیل، حساب‌های ثبت‌نام‌شده را فقط از روی زمان پاسخ تشخیص دهد.

const DUMMY_PASSWORD_HASH =
  'pbkdf2$50000$AAAAAAAAAAAAAAAAAAAAAA==$2ffAJAWDOjK7twSNwuk4ViIEALV8TIAHNuZwB+zAsDo=';

const user = await getUserByEmail(db, normalizeEmail(parsed.data.email));
if (!user) {
  await verifyPassword(parsed.data.password, DUMMY_PASSWORD_HASH);
  return authRouteError(c, new AuthError('invalid_credentials', 'Invalid email or password.'));
}
  • 1حتی اگر !user برقرار باشد، سرور همچنان عملیات کامل ۵۰,۰۰۰ تکراری PBKDF2 را روی DUMMY_PASSWORD_HASH اجرا می‌کند.
  • 2کد خطای invalid_credentials و پیام Invalid email or password. دقیقاً مشابه با حالت رمز عبور اشتباه است.

ستون ۳: معماری توکن دوگانه

توکن‌های JWT بدون وضعیت (Stateless) را نمی‌توان قبل از انقضا بدون مراجعه به دیتابیس در هر درخواست باطل کرد. سرویس PhysioCoach AI یک اکسس توکن کوتاه‌مدت JWT را با یک توکن رفرش هش‌شده در PostgreSQL ترکیب می‌کند. اگر بکاپ دیتابیس لو برود، مهاجمان فقط هش‌های SHA-256 را در دست دارند و نمی‌توانند هویت کاربران را جعل کنند.

مشخصه اکسس توکن (src/auth/tokens.ts) رفرش توکن (src/auth/sessions.ts)

ستون ۴: چرخش توکن رفرش، شناسایی استفاده مجدد و مقایسه اتمیک (CAS)

بر اساس استاندارد RFC 6819 و توصیه‌های امنیتی OAuth 2.0، با هر بار رفرش، توکن قدیمی باطل شده و توکن جدیدی صادر می‌شود. تلاش برای استفاده مجدد از یک توکن قدیمی و چرخیده‌شده، منجر به ابطال فوری کل نشست خواهد شد.

چرخش توکن رفرش و ردیابی سرقت (src/auth/sessions.ts)

  1. 1

    لاگین توکن رفرش R1 را صادر می‌کند

    هش SHA-256 آن در auth_sessions و auth_refresh_token_history ذخیره می‌شود.

  2. 2

    کلاینت با R1 درخواست رفرش می‌دهد ← سرور توکن R2 را صادر می‌کند

    سرور R1 را باطل می‌کند (آن را به previousRefreshTokenHash منتقل می‌نماید) و R2 را به عنوان توکن فعال قرار می‌دهد.

  3. 3

    مهاجم (یا کلاینت قربانی پس از سرقت) دوباره از توکن R1 استفاده می‌کند

    سرور متوجه می‌شود که R1 توکن فعال فعلی نیست و تاریخچه auth_refresh_token_history را جستجو می‌کند.

  4. 4

    سرور متوجه می‌شود R1 متعلق به سشن S بوده و کل سشن S را باطل می‌کند

    بلافاصله مقدار revokedAt = now را تنظیم می‌کند تا نه سارق و نه نشست قدیمی دیگر نتوانند توکنی رفرش کنند.

// Optimistic Concurrency Control (CAS - Compare-And-Swap in SQL)
const updated = await db
  .update(authSessions)
  .set({
    refreshTokenHash: nextHash,
    previousRefreshTokenHash: presentedHash,
    previousRefreshRotatedAt: nowIso,
    idleExpiresAt: nextIdle.toISOString(),
  })
  .where(
    and(
      eq(authSessions.id, session.id),
      eq(authSessions.refreshTokenHash, presentedHash), // MUST still hold the current hash!
      isNull(authSessions.revokedAt),
    ),
  )
  .returning({ id: authSessions.id });

if (updated.length === 0) {
  // Another concurrent request already rotated this token! Revoke the session.
  await revokeSession(db, session.id, nowIso);
  throw new AuthError('token_invalid', 'Refresh token is not valid.');
}
  • 1شرط WHERE ملزم می‌کند که هم refreshTokenHash === presentedHash باشد و هم revokedAt IS NULL، در قالب یک دستور اتمیک در SQL.
  • 2اگر مقدار updated.length === 0 باشد، به این معنی است که درخواست دیگری قبلاً توکن را چرخانده است؛ بنابراین نشست بی‌درنگ باطل می‌شود.

دام پروداکشن · شرایط رقابتی در رفرش هم‌زمان

دو درخواست رفرش در دقیقاً همان میلی‌ثانیه یکسان

شرط SQL دستور می‌دهد eq(authSessions.refreshTokenHash, presentedHash). درخواست دوم می‌بیند که updated.length === 0 است، بلافاصله تابع revokeSession(db, session.id, nowIso) را صدا می‌زند و خطای token_invalid پرتاب می‌کند.

دو پنجره انقضا

idleExpiresAt در برابر absoluteExpiresAt

idleExpiresAt با هر بار رفرش به جلو حرکت می‌کند
absoluteExpiresAt سقف سخت و ثابت ← کاربر را ملزم به ورود مجدد می‌کند

پاسخ مصاحبه

چرا از ماژول بومی bcrypt و عملگر === برای هش پسورد اجتناب می‌کنیم، و چرا در صورت پیدا نشدن کاربر باز هم با DUMMY_PASSWORD_HASH اعتبارسنجی را اجرا می‌کنیم؟

۱. سازگاری با لبه شبکه (Edge): افزونه‌های نیتیو C++ نظیر bcrypt در محیط‌های ایزوله Cloudflare Workers کار نمی‌کنند و ترد‌پول نود را مسدود می‌نمایند. ما از Web Crypto (crypto.subtle) با PBKDF2-SHA256 و ۵۰,۰۰۰ دور تکرار به همراه نمک ۱۶ بایتی استفاده می‌کنیم (pbkdf2$50000$<base64-salt>$<base64-hash>).

۲. عملیات بیتی با زمان ثابت (timingSafeEqual): عملگر متداول === در اولین بایت مغایر خارج می‌شود و راه را برای حملات زمان‌بندی (Timing Attacks) باز می‌گذارد. تابع timingSafeEqual با محاسبه diff |= a[i]! ^ b[i]! تمام بایت‌ها را در زمان پردازشی کاملاً یکنواخت مقایسه می‌کند.

۳. جلوگیری از سرشماری کاربران (User Enumeration): الگوریتم PBKDF2 حدود ۳۰ تا ۵۰ میلی‌ثانیه زمان می‌برد، در حالی که خروج زودهنگام تنها ۲ میلی‌ثانیه طول می‌کشد. اجرای verifyPassword در برابر DUMMY_PASSWORD_HASH (~۴۵ میلی‌ثانیه) و بازگرداندن پیام یکسان Invalid email or password. امکان حدس وجود یا عدم وجود یک حساب کاربری را از بین می‌برد.

پاسخ مصاحبه

چرا یک توکن JWT ۳۰ روزه صادر نمی‌کنیم، و سازوکار چرخش و ردیابی استفاده مجدد چگونه جلوی سرقت توکن رفرش را می‌گیرد؟

۱. توکن‌های دوگانه و ذخیره‌سازی هش‌شده: توکن‌های JWT بدون وضعیت را نمی‌توان تا قبل از سررسید باطل کرد. ما یک توکن دسترسی ۱۵ دقیقه‌ای با HS256 (بررسی در زیر ۱ میلی‌ثانیه) را با یک توکن رفرش ۳۲ بایتی جفت می‌کنیم که فقط هش SHA-256 آن (refreshTokenHash) در auth_sessions نگهداری می‌شود. حتی اگر نسخه پشتیبان دیتابیس به سرقت برود، نفوذگران تنها به هش‌ها دسترسی خواهند داشت و امکان سوءاستفاده از نشست کاربران را نخواهند داشت.

۲. چرخش و ردیابی استفاده مجدد (RFC 6819): با هر بار استفاده از R1، این توکن باطل شده و توکن R2 صادر می‌شود. اگر فرد دیگری دوباره از R1 استفاده کند، سرور وجود آن را در auth_refresh_token_history ردیابی کرده و کل نشست را بلافاصله لغو می‌کند (revokedAt = now).

۳. مقایسه و جایگزینی اتمیک (CAS) و پنجره انقضای دوگانه: اجرای اتمیک Compare-And-Swap در SQL (eq(authSessions.refreshTokenHash, presentedHash)) در برابر رفرش‌های هم‌زمان از نشست محافظت می‌کند. به علاوه، هر نشست از یک انقضای شناور idleExpiresAt به همراه یک سقف سخت و قطعی absoluteExpiresAt بهره می‌برد.
