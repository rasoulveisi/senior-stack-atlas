3.1 توابع · اسنپ‌شات‌ها · رندر خالص · کلیدها

رندرینگ و وضعیت (State)

یک کامپوننت ری‌اکت یک نمونه زنده از یک کلاس نیست؛ بلکه یک فراخوانی تابع خالص است که props و state فعلی را به رابط کاربری (UI) تبدیل می‌کند.

فرمول بنیادین

UI = f(props, state)

با هر بار تغییر state، ری‌اکت تابع شما را از بالا تا پایین مجدداً اجرا می‌کند.

تصویر دنیای واقعی

یک کامپوننت ری‌اکت شبیه باجه عکاسی فوری است؛ با هر تغییر، عکسی کاملاً جدید چاپ می‌کند، نه اینکه روی عکس قبلی با خودکار نقاشی بکشد.

یک فراخوانی تابع، نه یک نمونه کلاس

متغیرهای محلی تعریف‌شده با const یا let در هر بار رندر از نو ساخته می‌شوند. هندلرهای رویداد، مقادیر props و state مربوط به همان رندر به‌خصوص را در حافظه کلوژر خود نگه‌می‌دارند (Capture می‌کنند).

عادت انگولار: نمونه کلاس

انگولار یک بار new MyComponent() را صدا می‌زند، متغیر this.someProperty را در طول زمان جهش می‌دهد (Mutate می‌کند)، و هنگام انتشار سیگنال‌ها یا رویدادهای زون، تمپلیت را بررسی می‌نماید.

شیوه ری‌اکت: اسنپ‌شات تابع

ری‌اکت با هر تغییر state، تابع شما را از نو اجرا می‌کند. متغیرهای محلی تازه هستند و پس از بازگشت تابع ناپدید می‌شوند.

← هندلرها دقیقاً مقادیر همان رندر را ثبت و ضبط می‌کنند

وضعیت (State) تغییرناپذیر است و با Object.is مقایسه می‌شود

ری‌اکت تغییر وضعیت را با مقایسه رفرنس‌های قدیمی و جدید از طریق Object.is(oldState, newState) تشخیص می‌دهد.

دام پروداکشن · عادت آسیب‌رسان در انگولار

toasts.push(newItem); setToasts(toasts)

رفرنس آرایه تغییر نکرده است، بنابراین Object.is(oldArray, newArray) === true خواهد بود. ری‌اکت می‌پندارد چیزی تغییر نکرده و از رندر مجدد صرف‌نظر می‌کند.

const [toasts, setToasts] = useState<ToastItem[]>([]);

const toast = useCallback<ShowToast>((message, tone = "success") => {
  const id = nextId.current++;
  setToasts((current) => [...current, { id, message, tone }]);
}, []);
  • 1[...current, { id, message, tone }] آرایه جدیدی تخصیص می‌دهد تا Object.is یک رفرنس تازه را تشخیص دهد.
  • 2الگوی current => ... آخرین آرایه موجود در صف به‌روزرسانی را می‌خواند، نه یک کلوژر کهنه و بیات‌شده را.

نکته کلیدی

هنگامی که دو رویداد در یک تیک زمانی یکسان رخ می‌دهند، ساختار setToasts(current => ...) تضمین می‌کند که آپدیت دوم حتماً به انتهای آرایه حاصل از آپدیت اول ملحق شود.

مقادیر مشتق‌شده: محاسبه مستقیم در حین رندر

هنگامی که مقداری از props یا state به دست می‌آید، آن را مستقیماً درون بدنه تابع محاسبه کنید. آن را در useState یا useEffect قرار ندهید.

// Derived value: computed while rendering, from props. Not state, not an Effect.
const hasFilters = Boolean(search.q || search.status || search.assignee);
  • 1hasFilters در هر بار رندر مجدداً محاسبه می‌شود و هرگز هماهنگی خود را با search از دست نمی‌دهد.

عادت انگولار: computed()

در انگولار، نمونه کلاس فقط یک بار اجرا می‌شود، بنابراین شما وضعیت مشتق‌شده را درون computed(() => ...) قرار می‌دهید تا تغییرات سیگنال‌ها رصد شود.

شیوه ری‌اکت: یک const ساده

تابع کامپوننت شما از قبل با هر رندر دوباره اجرا می‌شود. یک متغیر ساده const بسیار پرسرعت است و به هیچ رپری نیاز ندارد.

نکته کلیدی · کامپایلر ری‌اکت (React Compiler)

پروژه Next Issue Tracker گزینه reactCompiler: true را در فایل next.config.ts فعال ساخته است (docs/adr/0003-react-compiler.md). در زمان بیلد، کامپایلر مقادیر مشتق‌شده و گره‌های JSX را به‌طور خودکار کش (Memoize) می‌کند، بدون آنکه نیازی به نوشتن دستی useMemo، useCallback یا React.memo باشد.

قانون رندر خالص (Pure Render Rule)

ری‌اکت و کامپایلر ری‌اکت می‌توانند کامپوننت شما را چندین بار فراخوانی کرده یا خروجی آن را کش کنند. رندر حتماً باید خالص باقی بماند.

متغیرهای بیرونی را تغییر ندهید

در زمان رندر، هرگز متغیرهای خارج از تابع کامپوننت را تغییر (Mutate) ندهید.

توابع ناخالص را در رندر صدا نزنید

هرگز توابعی مانند Date.now()، new Date() یا Math.random() را حین رندر یا در ردیوسر وضعیت فراخوانی نکنید.

کارهای ناخالص را به هندلرها بسپارید

هندلرهای رویداد نظیر submit بخشی از مرحله رندر نیستند؛ آن‌ها می‌توانند با خیال راحت new Date() را فراخوانی کرده و مقدار حاصل را به داخل بفرستند.

const [visible, addOptimistic] = useOptimistic<CommentView[], OptimisticComment>(
  comments,
  (current, { body, at }) => [
    ...current,
    {
      id: `pending-${current.length}`,
      body,
      author: { id: "me", name: currentUserName },
      createdAt: at, // Uses `at` passed in, NOT `new Date()` inside the reducer!
      updatedAt: at,
      viewerCan: { edit: false, delete: false },
      pending: true,
    },
  ],
);

function submit(formData: FormData) {
  const body = String(formData.get("body") ?? "").trim();
  if (body) addOptimistic({ body, at: new Date() });
  return dispatch(formData);
}
  • 1تابع submit() یک هندلر رویداد است، بنابراین ساختن new Date() در آن کاملاً ایمن است.
  • 2ردیوسر هوک useOptimistic در حین رندر اجرا می‌شود و با خواندن آرگومان پاس‌داده‌شده at، خلوص خود را حفظ می‌نماید.

همگام‌سازی وضعیت با تغییر Props: کلید در برابر setState در زمان رندر

به‌جای چرخه حیات ngOnChanges در انگولار، ری‌اکت دو الگو در اختیارتان می‌گذارد: تغییر مقدار key برای ریست کامل کامپوننت، یا صدا زدن setState در حین رندر برای اصلاح فیلدهای به‌خصوص.

عادت انگولار: ngOnChanges

منتظر هوک چرخه حیات @Input() ماندن و رونویسی دستی فیلدهای داخلی روی نمونه کلاس موجود.

شیوه ری‌اکت: key یا گارد رندر

ارسال یک key جدید برای ریمونت یک نمونه پاک، یا به‌روزرسانی state درون یک گارد شرطی if (prop !== seenProp) حین رندر.

پرسش‌های مصاحبه سنیور

پاسخ مصاحبه · سؤال ۱

چرا کپی کردن props درون state در هوک useEffect یک آنتی‌پترن مخرب است، و سه رویکرد اصولی برای مدیریت داده‌های حاصل از props کدامند؟

علت آسیب: فراخوانی setState(prop) درون useEffect باعث می‌شود ری‌اکت ابتدا یک چرخه کامل رندر و ترسیم (Paint) را با وضعیت قدیمی به پایان برساند، و سپس بلافاصله یک رندر دوم را آغاز کند که منجر به افت عملکرد و پرش بصری می‌شود.

۱. محاسبه حین رندر: اگر مقدار از props یا state محاسبه می‌شود، آن را به‌عنوان یک متغیر ساده درون بدنه تابع محاسبه کنید (مانند hasFilters در IssueFilters).

۲. ریست کردن کل state با کلید key: هر زمان که یک شناسه یا شماره نسخه تغییر کرد و شما یک نقطه شروع کاملاً پاک می‌خواهید، یک key جدید بفرستید. کامپوننت IssueForm از key={issue.updatedAt.toISOString()} استفاده می‌کند.

۳. اصلاح state خاص در حین رندر: برای به‌روزرسانی تنها برخی فیلدها ضمن حفظ فوکوس درون SearchBox، کامپوننت را در حالت مونت نگه دارید. setState را مستقیماً حین رندر درون شرط if (prop !== prevProp) صدا بزنید.

پاسخ مصاحبه · سؤال ۲

با فعال بودن کامپایلر جدید ری‌اکت (React Compiler)، آیا هنوز هم باید نگران تغییرناپذیری (Immutability) یا رندر خالص باشیم؟

بله، حتی بسیار جدی‌تر از گذشته. کامپایلر ری‌اکت مقادیر و بلوک‌های JSX را بر مبنای برابری رفرنس‌ها (Object.is) به‌صورت خودکار مموایز می‌کند و این فرض قطعی را دارد که تابع رندر شما کاملاً بدون ساید افکت است.

هرگز یک آرایه را در محل تغییر ندهید و توابع ناخالص مانند new Date() را حین رندر صدا نزنید. در غیر این صورت، کامپایلر ممکن است از محاسبه مجدد یک بلوک صرف‌نظر کرده و رابط کاربری کهنه و غلط روی صفحه باقی بماند.

3.2 useEffect · useEffectEvent · Refs · هایدریشن

افکت‌ها و سیستم‌های خارجی

یک افکت تنها و تنها برای همگام‌سازی با یک سیستم خارجی است؛ مانند لیسنرهای DOM، تایمرها، اتصالات وب‌سوکت یا ویجت‌های غیر ری‌اکتی.

تصویر دنیای واقعی

هوک useEffect درست مثل تبدیل دوشاخه برق در سفر است. شما فقط در مرز اتصال میان دستگاه خود و پریز برق بیگانه روی دیوار به آن احتیاج پیدا می‌کنید.

قانون طلایی useEffect

اگر پای هیچ سیستم خارجی در میان نیست، به هیچ عنوان به useEffect نیازی ندارید.

عادت انگولار: effect() / ngOnInit

استفاده از effect() یا ngOnInit برای واکنش به تغییرات وضعیت یا محاسبه فیلدهای مشتق‌شده در کامپوننت.

شیوه ری‌اکت: فقط همگام‌سازی مرزی

هوک useEffect را منحصراً برای لیسنرهای DOM مرورگر، setTimeout/setInterval، وب‌سوکت‌ها یا ویجت‌های غیر ری‌اکتی نگه دارید.

از useEffect + پاکسازی بهره ببرید

در زمان setup سابسکرایب کنید و در تابع پاکسازی (cleanup) لغو اشتراک نمایید.

اشتراک در رویدادهای DOM با useEffectEvent

فراخواننده‌ها یک تابع ناشناس (Arrow Function) مانند useHotkey("/", (e) => { ... }) ارسال می‌کنند که در هر بار رندر رفرنس جدیدی ایجاد می‌کند. هوک useEffectEvent (در ری‌اکت ۱۹.۲+) همیشه آخرین نسخه handler را بدون لزوم ثبت مجدد لیسنر DOM می‌خواند.

export function useHotkey(
  key: string,
  handler: (event: KeyboardEvent) => void,
) {
  const onKey = useEffectEvent(handler);

  useEffect(() => {
    function listener(event: KeyboardEvent) {
      if (event.key !== key || event.metaKey || event.ctrlKey || event.altKey)
        return;
      if (isTyping(event.target)) return;
      onKey(event);
    }
    document.addEventListener("keydown", listener);
    return () => document.removeEventListener("keydown", listener);
  }, [key]);
}
  • 1useEffectEvent(handler) همیشه جدیدترین نسخه handler را صدا می‌زند در حالی که نیازی نیست handler درون آرایه وابستگی‌های [key] قرار گیرد.
  • 2بازگرداندن () => document.removeEventListener(...) لیسنر را در زمان آنمونت یا تغییر key به‌خوبی پاکسازی می‌کند.
  1. 1

    اجرای Setup در زمان مونت

    ری‌اکت متد document.addEventListener("keydown", listener) را فراخوانی می‌کند.

  2. 2

    بررسی پاکسازی در Strict Mode (فقط در محیط توسعه)

    ری‌اکت بلافاصله آنمونت شدن را شبیه‌سازی کرده و removeEventListener را اجرا می‌کند تا پاکسازی‌های جاافتاده را کشف کند.

  3. 3

    اجرای مجدد Setup برای بار دوم

    اثبات‌شده در تست‌های use-hotkey.test.tsx: پس از چرخه setup → cleanup → setup تنها یک لیسنر ثبت‌شده باقی می‌ماند.

الگوی Latest-Ref برای تایمرها

هنگامی که یک setTimeout به‌جای useEffect درون یک هندلر رویداد استارت می‌خورد، آخرین نسخه کالبک را درون یک جعبه useRef نگهداری کنید.

export function useDebouncedCallback<Args extends unknown[]>(
  fn: (...args: Args) => void,
  delayMs: number,
) {
  const latest = useRef(fn);
  const timer = useRef<ReturnType<typeof setTimeout> | undefined>(undefined);

  useEffect(() => {
    latest.current = fn;
  });

  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback(
    (...args: Args) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => latest.current(...args), delayMs);
    },
    [delayMs],
  );
}
  • 1latest.current = fn درون یک افکت پس از هر کامیت به‌روزرسانی می‌شود.
  • 2هنگامی که تایمر پس از delayMs (برای مثال ۳۰۰ میلی‌ثانیه) فعال می‌شود، تابع latest.current(...args) را با جدیدترین مقادیر props و state فراخوانی می‌کند.

چرا useRef؟

{ current: value } یک ظرف تغییرپذیر است که در طول رندرهای مختلف زنده می‌ماند، بدون آنکه تغییر فیلد .current رندر مجددی ایجاد نماید.

چرا از useEffectEvent استفاده نمی‌کنیم؟

توابع حاصل از Effect Event را فقط می‌توان از درون خود useEffect صدا زد. در اینجا تایمر درون یک هندلر رویداد فراخواننده (onChange) شروع می‌شود.

چرا مقدار latest.current را در حین رندر نمی‌نویسیم؟

موتور همروند (Concurrent) ری‌اکت ممکن است رندری را آغاز کرده و آن را نیمه‌کاره رها کند یا با ترتیبی نامنتظره رندر نماید. تغییر دادن یک Ref حین رندر، خلوص آن را نقض می‌کند.

مقادیر ایمن مرورگر در زمان هایدریشن با useSyncExternalStore

سرور تاریخ‌ها را بر مبنای UTC قالب‌بندی می‌کند در حالی که مرورگر از منطقه زمانی کاربر (مثلاً +04:00) بهره می‌برد. فراخوانی مستقیم date.toLocaleString() حین رندر باعث می‌شود سرور ساعت 14:00 UTC و مرورگر ساعت 18:00 را تولید کند که منجر به خطای عدم تطابق هایدریشن (Hydration Mismatch) در ری‌اکت می‌گردد. هوک useSyncExternalStore تضمین می‌کند HTML اولیه سرور و گذر نخست هایدریشن کلاینت کاملاً یکسان باشند و سپس به زمان محلی تبدیل شوند.

const subscribe = () => () => {};

export function LocalTime({ date }: { date: Date }) {
  const text = useSyncExternalStore(
    subscribe,
    () => formatLocalDateTime(date), // 2nd arg: Client snapshot (after hydration)
    () => formatDateTime(date),      // 3rd arg: Server & hydration snapshot (UTC)
  );
  return <time dateTime={date.toISOString()}>{text}</time>;
}
  • 1آرگومان سوم (formatDateTime) روی سرور و در گذر ابتدایی هایدریشن کلاینت فراخوانی می‌شود.
  • 2درست پس از تکمیل موفقیت‌آمیز هایدریشن، ری‌اکت به سراغ آرگومان دوم (formatLocalDateTime) می‌رود.

الگوی قدیمی useState("") + useEffect

روی سرور یک رشته خالی "" رندر می‌کند که باعث برچسب‌های زمانی خالی در HTML اولیه SSR و جابه‌جایی چیدمان صفحه (Layout Shift) پس از بارگذاری می‌شود.

در محیط توسعه، هوک useEffect من هنگام مونت کامپوننت دو بار اجرا می‌شود. آیا این یک باگ است، و چگونه باید با آن رفتار کرد؟

این یک رفتار کاملاً عمدی و طراحی‌شده توسط <StrictMode> ری‌اکت است. ری‌اکت در محیط توسعه آنمونت و مونت مجدد هر کامپوننت را شبیه‌سازی می‌کند (setup → cleanup → setup) تا راستی‌آزمایی کند که تابع پاکسازی (Cleanup) شما کلیه آثار فاز setup را پاک می‌کند.

هرگز اجرای دوم را با متغیرهای قفلی مثل useRef(false) مسدود نکنید. در عوض یک تابع پاکسازی اصولی نظیر removeEventListener، clearTimeout یا abortController.abort() بنویسید.

هنگام رندر داده‌های مختص مرورگر مانند window.innerWidth، localStorage یا منطقه زمانی کاربر، چگونه جلوی بروز خطای Hydration Mismatch را می‌گیرید؟

از هوک useSyncExternalStore(subscribe, getClientSnapshot, getServerSnapshot) استفاده کنید.

در تابع getServerSnapshot یک مقدار قطعی و معین برگردانید (که در رندر SSR سرور و اولین گذر هایدریشن مصرف شود) و API مرورگر را در تابع getClientSnapshot درست پس از تکمیل هایدریشن بخوانید.

3.3 سرور و کلاینت · الگوی دونات · کانتکست · useId

ترکیب کامپوننت‌ها و الگوی دونات (Donut Pattern)

یک کامپوننت کلاینت می‌تواند کامپوننت‌های سرور را در قالب children احاطه کند بدون اینکه حجم کدهای آن‌ها به باندل جاوااسکریپت مرورگر تحمیل شود.

تصویر دنیای واقعی

یک کامپوننت کلاینت شبیه یک قاب عکس مجهز به پیچ تنظیم روشنایی است. کامپوننت سرور مثل عکس چاپ‌شده‌ای است که درون این قاب قرار می‌گیرد.

مرز سرور/کلاینت و الگوی دونات

در ساختار App Router در Next.js، همه کامپوننت‌ها به‌طور پیش‌فرض کامپوننت سرور (Server Component) هستند مگر آنکه فایل با راهنمای "use client" آغاز شود. کامپوننت‌های سرور منحصراً روی سرور اجرا می‌شوند، می‌توانند مستقیماً کوئری‌های دیتابیس را await کنند، و حجم خروجی آن‌ها برابر با 0 KB JS برای مرورگر است.

قاعده ۱ · ایمپورت‌ها به کد کلاینت تبدیل می‌شوند

هر ماژولی که مستقیماً توسط یک فایل دارای "use client" ایمپورت شود، درون باندل کلاینت جاوااسکریپت بسته‌بندی خواهد شد.

قاعده ۲ · راه نجات با الگوی دونات

یک کامپوننت "use client" می‌تواند کامپوننت‌های سرور را در قالب children (یا هر پراپ JSX دیگری) بپذیرد، در حالی که ماهیت سروری آن‌ها حفظ می‌گردد.

معماری Context در ری‌اکت ۱۹: دور نگه داشتن وضعیت‌های متغیر از کانتکست‌های فراگیر

ToastContext فقط تابع پایدار toast را در اختیار می‌گذارد، نه آرایه متغیر toasts را.

const ToastContext = createContext<ShowToast | null>(null);

export function useToast(): ShowToast {
  const toast = use(ToastContext);
  if (!toast) throw new Error("useToast must be used inside <ToastProvider>.");
  return toast;
}
  • 1ToastContext حاوی تایپ ShowToast (یک کالبک پایدار) است، نه آرایه ToastItem[].
  • 2دستور use(ToastContext) این کانتکست را با بهره‌گیری از هوک مدرن use() در ری‌اکت ۱۹ می‌خواند.

سینتکس نسخه‌های قدیمی ری‌اکت

رندر کردن <ToastContext.Provider value={toast}> و خواندن با useContext(ToastContext)، که قابلیت فراخوانی درون بلاک‌های if را نداشت.

سینتکس مدرن در ری‌اکت ۱۹

رندر مستقیم <ToastContext value={toast}> و خواندن با use(ToastContext)، که می‌تواند به‌صورت شرطی پس از returnهای زودهنگام یا درون بلاک‌های if صدا زده شود.

هوک useId و علت شکست شناسه‌های ثابت DOM در Next.js 16

نسخه ۱۶ فریم‌ورک Next.js از کامپوننت جدید <Activity> ری‌اکت استفاده می‌کند تا مسیرهای قبلی را به‌صورت پنهان در DOM نگه دارد. اگر هر دو مسیر /issues/new و /issues/1/edit ویژگی ثابت id="title" را رندر کنند، کلیک کردن روی لیبل در صفحه ویرایش باعث پرش فوکوس به فیلد ورودی پنهان‌شده در صفحه ایجاد ایشیو می‌شود.

export function useFieldId() {
  const base = useId();
  return (name: string) => `${base}-${name}`;
}
  • 1useId() یک شناسه معین و پایدار می‌سازد که بین سرور و هایدریشن کلاینت مشترک است.
  • 2هر فرم مونت‌شده فضای نام اختصاصی خود را خواهد داشت (برای مثال ${base}-title).

آیا یک کامپوننت کلاینت می‌تواند یک کامپوننت سرور را رندر کند؟ گراف ماژول‌ها در این سناریو چگونه کار می‌کند؟

عدم امکان ایمپورت مستقیم: یک کامپوننت کلاینت نمی‌تواند یک کامپوننت سرور را import کند. عبارت "use client" مرزی را معین می‌سازد که تمامی فایل‌های ایمپورت‌شده در آن برای مرورگر باندل می‌شوند.

امکان رندر از طریق Props: یک کامپوننت سرور والد می‌تواند یک کامپوننت سرور دیگر را از طریق پراپ children یا هر پراپ JSX دیگری به یک کامپوننت کلاینت ارسال کند. ری‌اکت کامپوننت سرور را روی سرور به یک پی‌لود سریالایز شده RSC (توصیف مجازی DOM) رندر کرده و آن را در اسلات کلاینت قرار می‌دهد.

3.4 useTransition · useOptimistic · useActionState · useFormStatus

قابلیت‌های همروند و فرم‌ها در ری‌اکت ۱۹

ری‌اکت ۱۹ کدهای تکراری مدیریت دستی isLoading و منطق بازگشت (Rollback) را با چهار هوک هماهنگ برای ترنزیشن‌ها، رابط کاربری خوش‌بینانه و فرم‌ها جایگزین کرده است.

تصویر دنیای واقعی

گارسونی که بلافاصله روی برگه سفارش میز شما می‌نویسد «در حال آماده‌سازی»، و اگر آشپزخانه اعلام کند موجودی تمام شده، آن را فوراً پاک می‌کند.

چهار هوک هماهنگ در ری‌اکت ۱۹

سه هوک از بسته اصلی react و یک هوک از بسته react-dom ارائه می‌شوند.

عادت انگولار یا نسخه‌های قدیمی ری‌اکت

مدیریت دستی متغیرهای isLoading، error، و ذخیره متغیر prevValue همراه با کدهای بازگشت در بلوک‌های try / catch با هر تغییر وضعیت.

شیوه مدرن ری‌اکت ۱۹

هماهنگ‌سازی جهش‌های ناهمگام با استفاده از useTransition، useOptimistic، useActionState و useFormStatus.

useTransition · از پکیج react

اجرای یک به‌روزرسانی وضعیت یا اکشن ناهمگام در پس‌زمینه بدون مسدود ساختن ورودی کاربر؛ ردیابی وضعیت pending. مثال‌ها: StatusControl، SearchBox.

useOptimistic · از پکیج react

نمایش بی‌درنگ حالت جدید رابط کاربری در حین در جریان بودن ترنزیشن یا اکشن ناهمگام؛ بازگشت خودکار در صورت لغو یا خطا. مثال‌ها: StatusControl، CommentThread.

useActionState · از پکیج react

متصل ساختن یک <form> به امضای (prevState, formData) => nextState، با ردیابی آخرین FormState و وضعیت isPending. مثال‌ها: IssueForm، CommentThread.

useFormStatus · از پکیج react-dom

خواندن مقادیر { pending, data } فرم دربرگیرنده (<form>) از درون یک کامپوننت فرزند. مثال: SubmitButton.

هماهنگی میان useTransition و useOptimistic

کامپوننت StatusControl منوی آبشاری را فوراً به‌روزرسانی می‌کند و اجازه می‌دهد ری‌اکت هر دو فرآیند تأیید سمت سرور و بازگشت خودکار در صورت خطا را به‌زیبایی مدیریت کند.

بازگشت خودکار

ترنزیشن تمام می‌شود؛ ری‌اکت به مقدار اصلی status در سرور بازمی‌گردد.

const [optimisticStatus, setOptimisticStatus] = useOptimistic(status);
const [pending, startTransition] = useTransition();

function onChange(next: IssueStatus) {
  startTransition(async () => {
    setOptimisticStatus(next);
    const result = await changeStatusAction(issueId, next);
    if (result.ok) toast(`Status changed to ${STATUS_LABELS[next]}.`);
    else toast(result.message, "error");
  });
}
  • 1setOptimisticStatus(next) وضعیت نمایش‌داده‌شده را پیش از شروع درخواست شبکه تغییر می‌دهد.
  • 2اگر result.ok برابر با false باشد، شما فقط یک پیام خطای توست نشان می‌دهید؛ ری‌اکت با اتمام ترنزیشن، پوشش خوش‌بینانه را به‌صورت خودکار کنار می‌گذارد.

چرا SubmitButton باید یک کامپوننت فرزند مستقل باشد

useFormStatus() دقیقاً مانند خواندن Context از نزدیک‌ترین تگ والد <form> عمل می‌کند.

دام پروداکشن

فراخوانی useFormStatus() در همان کامپوننتی که <form> را رندر می‌کند همواره برابر با false است

هوکی که در سطحی بالاتر از <form> صدا زده شود، هیچ فرم والدی برای خواندن اطلاعات ندارد. همیشه useFormStatus() را درون یک کامپوننت فرزند که داخل <form>...</form> قرار می‌گیرد فراخوانی نمایید.

export function SubmitButton({ children, pendingLabel, ...props }) {
  const { pending } = useFormStatus();
  return (
    <Button type="submit" disabled={pending || props.disabled} aria-disabled={pending} {...props}>
      {pending && pendingLabel ? pendingLabel : children}
    </Button>
  );
}
  • 1هوک useFormStatus() وضعیت { pending } را از تگ دربرگیرنده <form> دریافت می‌کند.
  • 2در زمان اجرای اکشن فرم، دکمه خودش را غیرفعال کرده و برچسب pendingLabel را جایگزین می‌نماید.

پاسخ مصاحبه · سؤال ۱

تفاوت بین یک به‌روزرسانی عادی وضعیت با وضعیتی که درون startTransition قرار می‌گیرد چیست؟

فوری در برابر غیرفوری: آپدیت‌های عادی وضعیت (مانند تایپ کردن در یک ورودی <input>) فوری (Urgent) و همگام هستند؛ آن‌ها رابط کاربری را تا زمان پایان رندر مسدود می‌کنند.

ترنزیشن‌های قابل وقفه (Interruptible): قرار دادن یک آپدیت (یا ناوبری روتر Next.js) درون startTransition آن را به‌عنوان عملیاتی غیرفوری و قابل وقفه نشانه‌گذاری می‌کند. در حین در جریان بودن یک ترنزیشن، ری‌اکت رابط کاربری فعلی را روی صفحه کاملاً تعاملی نگه می‌دارد به‌جای اینکه یک صفحه خالی یا لودر نشان دهد. چنانچه کاربر مجدداً کلیدی را فشار دهد، ری‌اکت رندر ناتمام قبلی را متوقف کرده و رندر جدید را در اولویت می‌گذارد.

پاسخ مصاحبه · سؤال ۲

هوک useOptimistic هنگام شکست یک جهش در سمت سرور، چگونه بازگشت به حالت قبل (Rollback) را مدیریت می‌کند؟

useOptimistic(passthroughState) هرگز وضعیت را به‌طور دائمی جهش (Mutate) نمی‌دهد.

مقدار موقت خوش‌بینانه تنها تا زمانی وجود دارد که اکشن ناهمگام یا startTransition به‌طور فعال در جریان (Pending) باشد. لحظه‌ای که ترنزیشن به سرانجام برسد، ری‌اکت لایه خوش‌بینانه را کنار گذاشته و به مقدار معتبر و قطعی passthroughState که از سرور آمده رجوع می‌کند.
