مهندسی پایگاه داده در لبه شبکه

ورکرهای لبه شبکه (Edge) در قالب صدها نمونه فعال می‌شوند. بدون استخر اتصال در حالت تراکنش (Transaction-Mode Pooling)، یک جهش ناگهانی ترافیک تمامی اتصالات PostgreSQL را ظرف چند ثانیه به نابودی می‌کشاند.

در دنیای واقعی

سرویس Cloudflare Hyperdrive شبیه ایستگاه تاکسی مشترک در مقابل یک هتل شلوغ است. به جای اینکه ۵۰۰ مسافر هر کدام برای یک سفر کوتاه خودرویی مجزا بخرند، مسافران سوار تاکسی‌های گرم و آماده می‌شوند و بلافاصله پس از پایان سفر، آن را برمی‌گردانند.

  idle_timeout: 10,

  fetch_types: false, // <-- Saves an extra startup round-trip query on cold start!

return drizzle(client, { schema });
  • 1prepare: false عبارت‌های از پیش کامپایل‌شده نام‌دار (Named Prepared Statements) را غیرفعال می‌کند تا استخر در حالت تراکنش با تغییر اتصالات بک‌اند دچار شکست نشود.
  • 2fetch_types: false از اجرای کوئری خودکار بررسی انواع در جدول pg_type صرف‌نظر می‌کند و رفت‌وبرگشت‌های شبکه در اتصال اولیه (Cold Start) را به نصف کاهش می‌دهد.

پاسخ مصاحبه

چرا در فایل src/db/client.ts دو گزینه prepare: false و fetch_types: false تنظیم شده‌اند؟

۱. prepare: false (غیرفعال‌سازی عبارات آماده نام‌دار): مدیریت‌کننده‌های استخر اتصال مانند Cloudflare Hyperdrive و PgBouncer در حالت استخر تراکنش (Transaction Pooling Mode) کار می‌کنند. ممکن است تراکنش شماره ۱ روی اتصال بک‌اند پستگرس #42 اجرا شود، در حالی که تراکنش شماره ۲ روی اتصال بک‌اند #19 قرار گیرد. عبارات آماده نام‌دار در پستگرس به یک اتصال فیزیکی خاص TCP وابسته هستند. فرض کنید کتابخانه postgres.js دستور آماده s1 را روی اتصال #42 ایجاد کند و در ادامه کوئری بعدی را روی اتصال #19 بفرستد. در این لحظه پستگرس با خطای ERROR: prepared statement "s1" does not exist متوقف می‌شود. قرار دادن prepare: false اجرای ساده/بدون‌نام پروتکل را فعال می‌کند تا مدیریت استخر در سطح تراکنش بدون مشکل عمل کند.

۲. fetch_types: false (درون‌نگری در زمان اتصال سرد): درایور postgres.js به طور پیش‌فرض هنگام اتصال، کوئری SELECT oid, typname FROM pg_type... را اجرا می‌کند تا انواع داده‌های سفارشی پستگرس را پیش از اجرای نخستین کوئری شما شناسایی کند. در محیط سرورلس Worker، این کوئری اضافی تعداد رفت‌وبرگشت‌ها به دیتابیس را در نخستین اتصال دو برابر می‌کند. خاموش کردن fetch_types تاخیر اتصال سرد دیتابیس را به نصف می‌رساند.

هنگام ایجاد یک کاربر دارای رمز عبور در src/routes/auth.ts، باید درج داده در جداول users و auth_credentials به صورت اتمیک (همه‌یاهیچ) انجام شود. اگر درج دوم شکست بخورد، هرگز ردیف کاربری رهاشده و بدون رمز عبور در سیستم باقی نمی‌ماند.

export async function withTransactionFallback<T>(
  db: ClientWithTransaction,
  operation: (client: T) => Promise<void>,
  contextLabel: string,
): Promise<void> {
  try {
    await db.transaction(async (tx) => {
      await operation(tx as T);
    });
    return;
  } catch (error) {
    if (!isTransactionBeginFailure(error)) {
      throw error;
    }
    // ... fallback for stateless HTTP drivers that disallow BEGIN
  }
  await operation(db as unknown as T);
}
  • 1db.transaction تابع operation(tx) را به صورت کاملاً اتمیک روی جداول users و auth_credentials اجرا می‌کند.
  • 2چنانچه درایور فاقد حالت HTTP اجازه اجرای دستور BEGIN را ندهد، تابع isTransactionBeginFailure عملیات را با اجرای operation(db) پشتیبانی می‌کند.

نکته کلیدی

شیء تراکنش Drizzle (tx) دقیقاً همان رابط کوئری‌نویسی شیء پایه db را دارد. هر تابعی که برای دریافت پارامتر عمومی client: T طراحی شود، هم درون یک تراکنش و هم خارج از آن بدون هیچ تغییری کار می‌کند.

ادغام ایمن با هوش مصنوعی

در یک دامنه درمانی و بالینی، مدل‌های زبانی (LLM) دچار توهم می‌شوند. فراخوانی‌های هوش مصنوعی بیرونی را با فهرست‌های از پیش فیلترشده در دیتابیس و دروازه‌های ایمنی قطعی مهار کنید.

در دنیای واقعی

1.9 میان‌افزار خطا · استاندارد RFC 7807 · مهار هشدارهای لاگ

مدیریت متمرکز خطا

اکسپرس یک میان‌افزار مدیریت خطا را با بررسی شرط fn.length === 4 در زمان اجرا شناسایی می‌کند. هر شکستی در سیستم باید از مسیر یک قرارداد یکپارچه Problem Details بر پایه RFC 7807 به بیرون هدایت شود.

در دنیای واقعی

در یک بیمارستان، تمامی بخش‌ها از یک فرم گزارش حادثه یکسان استفاده می‌کنند. حادثه در پذیرش رخ داده باشد، در آزمایشگاه یا در داروخانه، هر پزشکی می‌تواند ظرف چند ثانیه گزارش را بخواند و متوجه ماجرا شود.

دام شرط زمان اجرای fn.length === 4

در اکسپرس، یک میان‌افزار مدیریت خطا صرفاً با داشتن دقیقاً ۴ آرگومان شناسایی می‌شود: (error, req, res, next).

دام پروداکشن · اکسپرس مقدار fn.length === 4 را چک می‌کند

حذف _next مقدار را به fn.length === 3 تغییر داده و هندلر خطای شما بی‌پاسخ نادیده گرفته می‌شود

حتی اگر داخل تابع مدیریت خطا نیازی به فراخوانی next نداشته باشید، حتماً باید پارامتر چهارم _next را در ساختار (error, req, res, _next) نگه دارید. اگر بنویسید (error, req, res)، ویژگی fn.length برابر 3 می‌شود و اکسپرس آن را یک میان‌افزار عادی در نظر می‌گیرد و هنگام وقوع خطا اصلاً آن را اجرا نمی‌کند.

۳ آرگومان: (error, req, res)

مقدار fn.length تابع در جاوااسکریپت 3 است. اکسپرس آن را به عنوان یک میان‌افزار معمولی ثبت می‌کند.

→ هنگام صدا زدن next(err) کاملاً نادیده گرفته شده و اجرا نمی‌شود

۴ آرگومان: (error, req, res, _next)

مقدار fn.length تابع برابر 4 است. عبارت void _next; لینتر را راضی نگه داشته و پارامتر چهارم را حفظ می‌کند.

→ تمامی خطاهای پرتاب‌شده در کل برنامه را با موفقیت دریافت و مدیریت می‌کند

استاندارد RFC 7807 / RFC 9457 (application/problem+json)

در فایل src/middleware/error.ts، سامانه PhysioCoach AI خروجی‌های خطای سلیقه‌ای و نامنظم را با ساختار استاندارد RFC 7807 Problem Details برای APIهای HTTP جایگزین می‌کند.

ساختارهای ناسازگار و متناقض خطا در مسیرها

یک اندپوینت شیء { error: "bad" } بازمی‌گرداند در حالی که دیگری { msg: "failed", code: 12 } می‌دهد.

→ فرانت‌اند ناچار است برای هر اندپوینت لاجیک مجزایی برای خواندن خطا پیاده‌سازی کند

یک قرارداد یکتا بر پایه RFC 7807

هر خطایی هدر Content-Type: application/problem+json را به همراه فیلدهای type، title، detail، instance، traceId و auditLogId برمی‌گرداند.

→ یک ساختار کاملاً پیش‌بینی‌پذیر برای کلاینت‌ها و سیستم‌های لاگینگ

export const errorHandler: ErrorRequestHandler = (error: unknown, req, res, _next) => {
  void _next;
  const candidate: HttpError =
    error instanceof Error ? error : new Error('Unexpected API error.');
  const status = resolveStatusCode(error, candidate);
  const traceId = req.traceId || crypto.randomUUID();
  const auditLogId = candidate.auditLogId || req.auditLogId || null;

  if (status >= 500) {
    console.error('request.failed', { traceId, auditLogId, error: candidate.message });
  }

  res
    .status(status)
    .type('application/problem+json')
    .json({
      type: `https://physiocoach.devbench.ir/problems/${status}`,
      title: STATUS_TITLES[status] || 'Request Failed',
      detail: candidate.message || 'Unexpected API error.',
      instance: req.originalUrl,
      traceId,
      auditLogId,
      ...(error instanceof ZodError ? { errors: error.issues } : {}),
    });
};
  • 1تعریف (error: unknown, req, res, _next) مقدار fn.length === 4 را حفظ می‌کند تا اکسپرس در صورت بروز خطا آن را فراخوانی کند.
  • 2شرط if (status >= 500) فقط کرش‌ها و خطاهای سمت سرور را لاگ می‌کند و اشتباهات موردانتظار کلاینت با کدهای 4xx را ثبت نمی‌کند.
  • 3هدر پاسخ را روی application/problem+json قرار داده و مقادیر traceId، auditLogId و آرایه اختیاری errors ناشی از Zod را ضمیمه می‌نماید.

  • 1type: یک URI پایدار که دسته‌بندی مشکل را بر اساس کد وضعیت HTTP مشخص می‌کند.
  • 2title: خلاصه کوتاه و خوانا برای انسان برگرفته از آرایه STATUS_TITLES[status].
  • 3detail: پیام دقیق و مشخص (candidate.message) مربوط به این رخداد خاص.
  • 4instance: مسیر کامل درخواستی که منجر به خطا شده از طریق req.originalUrl.
  • 5traceId: شناسه توزیع‌شده UUID درخواست برگرفته از req.traceId.
  • 6auditLogId: خطاهای مرتبط با هوش مصنوعی را مستقیماً به جدول ai_audit_logs پیوند می‌دهد (یا مقدار null).
  • 7errors: آرایه در سطح فیلد error.issues که هنگام وقوع error instanceof ZodError در پاسخ قرار می‌گیرد.

تنها خطاهای با وضعیت status >= 500 را لاگ بحرانی کنید. هرگز با وارد کردن رمز عبور اشتباه توسط یک کاربر (401) هشدارهای مانیتورینگ خطا را پر نکنید؛ آلارم‌ها فقط زمانی باید فعال شوند که خود سرور با شکست مواجه شده باشد.

محدودسازی نرخ درخواست پشت پراکسی

پشت شبکه کلودفلر، آی‌پی سوکت TCP همان آی‌پی پراکسی است. سیستم محدودکننده نرخ درخواست باید هدر معتبر لبه شبکه را بخواند و حافظه خود را بدون نیاز به تایمرهای سراسری پاک‌سازی کند.

در دنیای واقعی

نگهبان یک باشگاه شبانه تعداد دفعات ورود را بر اساس کارت شناسایی اختصاصی هر فرد (cf-connecting-ip) می‌شمارد، نه بر اساس پلاک تاکسی مشترکی (req.socket.remoteAddress) که همه را جلوی درب پیاده کرده است.

چرا هدر cf-connecting-ip بر x-forwarded-for اولویت دارد

فایل src/auth/rate-limit.ts از اندپوینت‌های /auth/login، /auth/register و /auth/refresh در برابر حملات آزمون مکرر اطلاعات کاربری (Credential Stuffing) محافظت می‌کند. پشت کلودفلر، مقدار req.socket.remoteAddress در حقیقت آی‌پی پراکسی کلودفلر است، نه آی‌پی واقعی کلاینت.

function getClientKey(c: ExpressRouteContext): string {
  const cfConnectingIp = c.req.header('cf-connecting-ip');
  if (cfConnectingIp) {
    return cfConnectingIp;
  }

  const forwardedFor = c.req.header('x-forwarded-for');
  if (forwardedFor) {
    return forwardedFor.split(',')[0]?.trim() || 'unknown';
  }

  const realIp = c.req.header('x-real-ip');
  return realIp?.trim() || 'unknown';
}
  • 1هدر cf-connecting-ip در ابتدا بررسی می‌شود چرا که کلودفلر هرگونه مقدار جعلی ارسال‌شده توسط کلاینت را بازنویسی می‌کند.
  • 2هدر x-forwarded-for می‌تواند شامل رشته‌ای مثل client, proxy1, proxy2 باشد، بنابراین دستور .split(',')[0]?.trim() آی‌پی آغازین کلاینت را استخراج می‌کند.

تست‌نویسی برای Express

پورت شماره 0 را به متد server.listen(0, '127.0.0.1') پاس دهید تا هسته سیستم‌عامل یک پورت موقت و آزاد لوپ‌بک را به هر تست هم‌زمان اختصاص دهد.

در دنیای واقعی

هاردکد کردن پورت 8787 شبیه هتلی است که ۵۰ مسافر هم‌زمان بر سر اتاق شماره ۸۷۸۷ دعوا کنند! پاس دادن پورت 0 به مسئول پذیرش اجازه می‌دهد هر اتاق خالی موجود را به مسافر تحویل دهد و هنگام خروج، کلید را پس بگیرد.

چرا آزمون‌های سنتی API با شکست مواجه می‌شوند

بسیاری از تیم‌ها هنگام تست APIهای اکسپرس در یکی از دو دام رایج گرفتار می‌شوند: یا همه چیز را ماک می‌کنند، یا یک پورت مشخص را هاردکد می‌کنند.

const testableApp = app as unknown as TestableExpressApp;
testableApp.fetch = async (input, init, bindings) => {
  app.locals.workerEnv = bindings ?? {};
  const server = createServer(app);
  await new Promise<void>((resolve, reject) => {
    server.once('error', reject);
    server.listen(0, '127.0.0.1', resolve); // <-- Port 0 = OS assigns a free ephemeral port!
  });

  try {
    const address = server.address();
    if (!address || typeof address === 'string') throw new Error('Test server did not start.');
    // ... forwards Web Standard Request to http://127.0.0.1:${address.port}
    return await fetch(`http://127.0.0.1:${address.port}${parsed.pathname}${parsed.search}`, requestInit);
  } finally {
    await new Promise<void>((resolve) => server.close(() => resolve()));
  }
};

  • 2فراخوانی fetch(...) یک درخواست واقعی HTTP را از طریق پشته TCP نودجی‌اس به پورت اختصاص‌یافته address.port ارسال می‌نماید.
  • 3بلوک finally تضمین می‌کند که متد server.close() حتی در صورت شکست ادعاها (Assertions) یا خطای درخواست حتماً اجرا شود.

برخلاف فراخوانی مستقیم یک تابع کنترلر در تست‌های واحد معمولی، فراخوانی app.fetch('/api/v1/health') یک درخواست واقعی شبکه می‌فرستد که از کل زنجیره میان‌افزارها به طور سرتاسری عبور می‌کند.

این ۲۰ پرسش و پاسخ تخصصی بک‌اند سنیور و متن ۶۰ ثانیه‌ای معرفی معماری را درست پیش از جلسه مصاحبه مرور کنید.

در دنیای واقعی

این چک‌لیست مانند چک‌لیست نهایی خلبان روی باند فرودگاه است. همه سیستم‌ها قبلاً ساخته و پرداخته شده‌اند؛ اکنون فقط آخرین نگاه را به نشانگرها می‌اندازید تا آماده برخاستن شوید.

هسته Node.js و Express (پرسش‌های ۱ تا ۵)

پاسخ مصاحبه · پرسش ۱

۱. آیا Node.js تک‌رشته‌ای (Single-threaded) است؟

کدهای جاوااسکریپت شما روی یک رشته منفرد (حلقه رویداد یا V8 Event Loop) اجرا می‌شوند. یک حلقه سنگین محاسباتی یا تابع همگام JSON.parse حجیم، تمامی کاربران هم‌زمان را مسدود می‌کند.

ران‌تایم C++ (کتابخانه libuv) و هسته سیستم‌عامل چندرشته‌ای و غیرهمگام هستند. کتابخانه libuv از یک استخر پس‌زمینه نخ‌ها (به طور پیش‌فرض ۴ رشته) برای عملیات ورودی/خروجی فایل، پرس‌وجوهای DNS و پردازش‌های رمزنگاری (PBKDF2) استفاده می‌کند. همچنین سوکت‌های شبکه (http و TCP در PostgreSQL) را به APIهای ناهمگام کرنل سیستم‌عامل (مثل epoll در لینوکس و kqueue در macOS) محول می‌نماید.

حلقه رویداد V8 (تک‌رشته)

کال‌بک‌های JS را اجرا می‌کند. با حلقه‌های همگام یا JSON.parse حجیم مسدود می‌شود.

استخر libuv (۴ نخ)

عملیات فایل I/O، پرس‌وجوی DNS و محاسبات رمزنگاری PBKDF2 را اجرا می‌کند.

کرنل ناهمگام سیستم‌عامل

سازوکارهای epoll و kqueue سوکت‌های شبکه HTTP و Postgres را مدیریت چندگانه می‌کنند.

پاسخ مصاحبه · پرسش ۲

۲. تفاوت میان app.use('/api', fn) و app.get('/api', fn) چیست؟

متد app.use با هر متد HTTP تطابق دارد و بر اساس پیشوند مسیر مطابقت می‌دهد (/api، /api/users، /api/v1/health)، و پیشوند /api را داخل تابع fn از مقدار req.url حذف می‌کند.

متد app.get صرفاً با درخواست‌های GET مطابقت دارد و به تطابق دقیق مسیر نیاز دارد (فقط مسیر /api).

app.use('/api', fn)

تمامی متدها · تطابق پیشوندی (/api/*) · حذف پیشوند /api از req.url

app.get('/api', fn)

صرفاً متد GET · تطابق دقیق مسیر (فقط /api)

پاسخ مصاحبه · پرسش ۳

۳. اکسپرس چگونه متوجه می‌شود که یک میان‌افزار، هندلر خطاست؟

با بررسی مقدار fn.length === 4 در تعریف تابع ((err, req, res, next)). چنانچه پارامتر چهارم next را حذف کنید، اکسپرس آن را یک میان‌افزار ۳ آرگومانی معمولی قلمداد کرده و هنگام بروز خطا هرگز آن را صدا نخواهد زد.

پاسخ مصاحبه · پرسش ۴

۴. اگر پس از شروع استریم پاسخ با res.write() خطایی رخ دهد، چه پیش می‌آید؟

به محض اینکه هدرهای HTTP و نخستین بایت‌های بدنه روی سوکت TCP فلاش (ارسال) شوند، دیگر نمی‌توانید کد وضعیت HTTP را به 500 تغییر دهید. در این حالت، مدیریت پیش‌فرض اکسپرس مقدار res.headersSent را بررسی کرده و سوکت را می‌بندد تا کلاینت متوجه ناقص ماندن انتقال داده شود.

پاسخ مصاحبه · پرسش ۵

۵. مفهوم فشار معکوس (Backpressure) در سرورهای HTTP مبتنی بر Node.js چیست؟

گاهی یک سرور پرسرعت فایل حجیم یا کرسر دیتابیس را سریع‌تر از توانایی دانلود یک کلاینت موبایل با سرعت اینترنت پایین می‌خواند. در این سناریو، بافرهای حافظه سرور انباشته شده و می‌توانند به کرش سرور منجر شوند. متدهای stream.pipe() یا pipeline() وقتی بافر نوشتن سوکت پر شود (زمانی که متد write() مقدار false بازگرداند)، خواندن داده را موقتاً متوقف می‌کنند و پس از رخداد رویداد 'drain' به صورت خودکار خواندن را از سر می‌گیرند.

خواندن سریع از منبع ← بازگشت false از write() ← توقف خواندن ← رویداد 'drain' ← از سرگیری استریم

امنیت و احراز هویت (پرسش‌های ۶ تا ۹)

پاسخ مصاحبه · پرسش ۶

۶. چرا برای Refresh Token به جای PBKDF2 یا bcrypt از هش SHA-256 استفاده می‌شود؟

گذرواژه‌ها آنتروپی پایینی دارند: انسان‌ها معمولاً رمزهای ساده و قابل حدس انتخاب می‌کنند، بنابراین نیازمند یک الگوریتم هش کند (مانند PBKDF2 یا Argon2) هستند تا جلوی حملات حدس آفلاین (Brute-force) گرفته شود.

توکن‌های تجدید آنتروپی بسیار بالایی دارند: این توکن‌ها شامل ۳۲ بایت (۲۵۶ بیت) داده تصادفی رمزنگاری‌شده قوی (crypto.getRandomValues) هستند. با داشتن 2^256 حالت ممکن، حدس زدن آن‌ها از نظر ریاضی غیرممکن است. یک تابع هش سریع رمزنگاری مثل SHA-256 توکن را در صورت نشت احتمالی دیتابیس کاملاً ایمن نگه می‌دارد، بدون اینکه در هر بار تمدید توکن منابع باارزش پردازنده را هدر دهد.

رمز عبور کاربر · آنتروپی پایین

آسیب‌پذیر در برابر حملات دیکشنری ← نیازمند الگوریتم کند PBKDF2 (با ۵۰,۰۰۰ دور تکرار) یا Argon2.

توکن ۳۲ بایتی · ۲ به توان ۲۵۶ حالت

غیرقابل حدس زدن ← هش سریع SHA-256 از دیتابیس محافظت می‌کند بدون اینکه ذره‌ای CPU هدر رود.

پاسخ مصاحبه · پرسش ۷

۷. اگر نشست‌ها را روی سرور ذخیره نکنیم، چگونه می‌توان از سرقت Refresh Token جلوگیری کرد؟

هیچ راهی وجود ندارد؛ به همین دلیل است که پیاده‌سازی رفرش‌توکن‌های کاملاً بدون‌وضعیت (Stateless) یک ضدالگو محسوب می‌شود. شما ملزم به ذخیره فراداده‌های نشست (auth_sessions) و ثبت تاریخچه چرخش توکن (auth_refresh_token_history) در پایگاه داده هستید. اگر توکنی که قبلاً در چرخه باطل شده مجدداً ارائه شود، کل خانواده توکن‌های آن نشست بی‌درنگ باطل می‌شوند.

پاسخ مصاحبه · پرسش ۸

۸. چگونه جلوی حملات کانال جانبی زمان‌بندی (Timing Attacks) را هنگام لاگین می‌گیرید؟

ابتدا هش رمز عبور را با حلقه‌ای که بر پایه زمان ثابت عمل می‌کند مقایسه کنید (timingSafeEqual). ثانیاً اگر ایمیل کاربر در دیتابیس یافت نشد، رمز واردشده را در برابر یک هش ساختگی DUMMY_PASSWORD_HASH اعتبارسنجی کنید. بدین ترتیب، وضعیت «کاربر پیدا نشد» دقیقاً همان حدود ۴۰ میلی‌ثانیه پردازش CPU توسط PBKDF2 را صرف می‌کند که وضعیت «رمز عبور اشتباه است» صرف می‌نماید و مهاجم نمی‌تواند از روی زمان پاسخ به وجود کاربر پی ببرد.

پاسخ مصاحبه · پرسش ۹

۹. توکن‌ها در فرانت‌اند کجا باید ذخیره شوند؟

رویکرد اول استفاده از کوکی‌های دارای فلگ‌های HttpOnly; Secure; SameSite=Lax است که در برابر حملات XSS کاملاً ایمن هستند اما برای متدهای تغییردهنده نیاز به محافظت در برابر CSRF دارند. رویکرد دوم، نگهداری Access Token در حافظه موقت جاوااسکریپت همراه با Refresh Token در حال چرخش، تعریف سیاست امنیتی سفت‌وسخت محتوا (CSP)، حذف کامل روزنه‌های XSS و تشخیص استفاده مجدد در سمت سرور است.

پایگاه داده و تراکنش‌ها (پرسش‌های ۱۰ تا ۱۲)

پاسخ مصاحبه · پرسش ۱۰

۱۰. خطای N+1 Query چیست و در Drizzle چگونه از آن پیشگیری می‌کنید؟

حالتی است که ابتدا ۲۰ جلسه تمرینی را دریافت می‌کنید (1 کوئری) و سپس در یک حلقه for به ازای هر جلسه یک کوئری SELECT جداگانه می‌زنید (20 کوئری). راهکار جلوگیری از این مشکل، دریافت یک‌باره تمامی تمرینات مربوطه در یک کوئری واحد با inArray(exerciseLogs.workoutSessionId, sessionIds) یا ایجاد JOIN در SQL است؛ سپس ردیف‌ها را در حافظه سرور با یک شیء Map گروه‌بندی می‌کنید.

۱۱. چگونه جلوی بروز شرایط رقابتی (Race Condition) را هنگام ویرایش هم‌زمان یک رکورد می‌گیرید؟

از سازوکار کنترل هم‌زمانی خوش‌بینانه (Optimistic Concurrency Control / Compare-And-Swap) در یک کوئری اتمیک مانند UPDATE ... WHERE id = $1 AND refresh_token_hash = $2 RETURNING id استفاده کنید. روش جایگزین، به‌کارگیری قفل‌گذاری بدبینانه (Pessimistic Locking) با دستور SELECT ... FOR UPDATE درون یک تراکنش دیتابیس است.

۱۲. چرا هنگام استفاده از PgBouncer یا Cloudflare Hyperdrive در حالت تراکنش، تنظیم prepare: false الزامی است؟

استخرهای اتصال در حالت تراکنش، پس از پایان هر تراکنش، اتصال فیزیکی بک‌اند در پستگرس را مجدداً به درخواست دیگری تخصیص می‌دهند. عبارات آماده نام‌دار (Named Prepared Statements) به یک اتصال خاص وابسته هستند؛ بنابراین کوئری بعدی ممکن است به بک‌اندی هدایت شود که اصلاً آن عبارت آماده را در حافظه خود ندارد و منجر به بروز خطای سیستمی شود.

۱۳. خاموش‌سازی اصولی (Graceful Shutdown) در یک کانتینر Express چگونه پیاده می‌شود؟

به سیگنال SIGTERM ارسال‌شده از سوی Kubernetes یا Docker گوش فرا دهید و سپس این ۴ مرحله ترتیبی را اجرا کنید:

۱. توقف ترافیک تازه

فراخوانی متد server.close() برای عدم پذیرش اتصالات جدید.

۲. تخلیه درخواست‌های فعال

مهلت دادن به درخواست‌های در حال اجرا برای اتمام کار (با سقف زمانی مثلاً ۱۵ ثانیه).

۳. بستن استخر دیتابیس

قطع ارتباط استخر اتصالات پایگاه داده (await sql.end()).

۴. خروج تمیز پروسس

خروج از برنامه با فراخوانی دستور process.exit(0).

۱۴. مفهوم برابری توان (Idempotency) چیست و چرا در POST /workout-plans/generate از inputHash استفاده می‌شود؟

یک عملیات زمانی برابرتوان یا Idempotent است که تکرار چندباره آن دقیقاً همان اثری را داشته باشد که یک‌بار فراخوانی آن دارد. با هش کردن مشخصات و ارزیابی‌های کاربر (buildPlanInputHash)، می‌توانیم درخواست‌های تکراری را شناسایی کرده، کانتکست اعتبارسنجی‌شده را مجدداً استفاده کنیم و لاگ‌های حسابرسی را همبسته سازیم.

۱۵. تفاوت کدهای وضعیت 401 Unauthorized، 403 Forbidden، 409 Conflict و 422 Unprocessable Entity چیست؟

401

شما چه کسی هستید؟

توکن احراز هویت وجود ندارد یا منقضی شده است.

403

عدم دسترسی مجاز

هویت شما مشخص است، اما اجازه دسترسی به مسیر /api/v1/admin را ندارید.

409

تعارض وضعیت یا نقض ایمنی

ثبت‌نام با ایمیل تکراری یا رد برنامه ناامن توسط گیت بالینی.

422 / 400

داده ورودی نامعتبر

سینتکس بدنه یا اسکیمای اعتبارسنجی داده نامعتبر است.

وقتی کاربری در یک سیستم توزیع‌شده گزارش خطا می‌دهد، شناسه traceId مانند نخی تمام گره‌ها را به یکدیگر وصل می‌کند. شما می‌توانید با استفاده از دستور grep در لاگ‌ها و کوئری در جدول ai_audit_logs، مسیر دقیق همان یک درخواست را در تمامی سرویس‌ها ردیابی کنید.

۱۸. چرا اندپوینت /api/v1/health باید کوئری SELECT 1 را روی پایگاه داده اجرا کند؟

یک بررسی سلامت سطحی که صرفاً شیء { ok: true } بازمی‌گرداند تنها زنده بودن پروسس را اثبات می‌کند؛ این بررسی حتی در صورت خرابی رمز عبور دیتابیس یا بن‌بست (Deadlock) استخر اتصالات سبز باقی می‌ماند! اجرای دستور SELECT 1 و سنجش پارامتر responseTimeMs، سلامت و آمادگی واقعی سامانه را تضمین می‌کند (200 OK در برابر 503 Service Unavailable).

۱۹. مفهوم Prototype Pollution در Express چیست و چگونه از آن جلوگیری می‌کنیم؟

اگر مهاجم شیء جیسونی مانند {"__proto__": {"isAdmin": true}} ارسال کند و کدهای شما بدون بررسی کلیدها اقدام به ادغام عمیق (Deep Merge) اشیاء نمایند، مهاجم می‌تواند آبجکت والد Object.prototype را آلوده سازد. اعتبارسنجی تمامی ورودی‌ها با اسکیماهای سخت‌گیرانه Zod (z.object({...}).strict()) کلیدهای __proto__ و constructor را بلافاصله حذف یا رد می‌کند.

پاسخ مثل یک مهندس ارشد · پرسش ۲۰ · معرفی ۶۰ ثانیه‌ای معماری

۲۰. معماری بک‌اند PhysioCoach AI را چگونه در ۶۰ ثانیه در ابتدای یک جلسه مصاحبه شرح می‌دهید؟

«بک‌اند سامانه PhysioCoach AI یک API مبتنی بر Express 5 است که با تایپ‌اسکریپت سخت‌گیرانه روی Cloudflare Workers پیاده شده است. این سرویس از طریق استخر اتصال Cloudflare Hyperdrive و به‌کارگیری Drizzle ORM به پایگاه داده Neon PostgreSQL متصل می‌شود. هر درخواست ورودی از یک خط لوله میان‌افزاری مقاوم با رویکرد Fail-closed می‌گذرد: بررسی هدرهای CORS، پارس امن بدنه JSON، الصاق شناسه توزیع‌شده UUID برای ردیابی، و اعتبارسنجی توکن‌های بدون‌وضعیت JWT بر پایه استاندارد Web Crypto. برای احراز هویت، ما از الگوریتم PBKDF2-SHA256 به همراه مقایسه در زمان ثابت و هش ساختگی برای جلوگیری از حملات زمان‌بندی استفاده کرده‌ایم. همچنین سیستم توکن‌های تجدید چرخان هش‌شده با SHA-256 را همراه با قابلیت شناسایی استفاده مجدد پیاده کرده است. برای ساخت برنامه‌های تمرینی با هوش مصنوعی، بک‌اند ابتدا کاتالوگ حرکات بالینی را در پستگرس فیلتر کرده و مدل‌های OpenRouter را با مکانیزم‌های تایم‌اوت و فال‌بک هدایت می‌کند. خروجی مدل با Zod و قوانین قطعی بیومکانیکی سنجیده شده و در نهایت، گزارش کامل در جدول حسابرسی ثبت می‌شود و هرگونه شکست در قالب ساختار استاندارد RFC 7807 بازگردانده می‌شود.»
