1.1 Node.js HTTP · Express · Edge Adapters

Under the hood

Calling express() returns a plain JavaScript function with the signature (req, res) => void. Node's HTTP server calls that function on every request. Express also attaches methods such as app.use() and app.get() to configure that function.

Real-world picture

Node's http.Server is an office building that opens the front door. Express app(req, res) is the one receptionist who greets every visitor and directs them inside.

How Cloudflare Workers runs Express

PhysioCoach AI runs inside Cloudflare Workers using the Web Standard fetch(request, env, ctx) API. A tiny bridge turns the Web Request into a Node socket call for Express.

import { httpServerHandler } from 'cloudflare:node';
import { createServer } from 'node:http';
import { createApp } from './app';
import type { WorkerBindings } from './env';

const app = createApp();
const server = createServer(app);
const nodeHandler = httpServerHandler(server as unknown as Parameters<typeof httpServerHandler>[0]);

export default {
  async fetch(request: Request, env: WorkerBindings, ctx: ExecutionContext): Promise<Response> {
    // Inject Cloudflare per-request environment bindings (Hyperdrive DB, secrets) into Express
    app.locals.workerEnv = env;
    return (nodeHandler as { fetch: (req: Request, env: unknown, ctx: unknown) => Promise<Response> }).fetch(
      request,
      env,
      ctx,
    );
  },
};
  • 1createServer(app) passes the Express function directly to Node's HTTP server.
  • 2httpServerHandler bridges Cloudflare's fetch event to that Node server.
  • 3app.locals.workerEnv = env hands Cloudflare secrets and Hyperdrive DB bindings to Express.

Why app.ts and index.ts are separate

src/app.ts builds the Express instance via createApp(). src/index.ts attaches it to the network runtime.

Each parallel test calls createApp() without binding port 8787.

Edge runtime ready

Docker & Node portability

The exact same app runs on a Linux container via app.listen(8787).

What happens to a POST body stream

When a client sends a POST request with JSON, the body is not ready right away.

  1. 1

    Raw bytes arrive in chunks over a TCP stream

    Node wraps this readable stream in an http.IncomingMessage object (req).

  2. 2

    req.body does not exist yet

    Reading a network stream is asynchronous and takes time until a body parser reads the chunks.

  3. 3

    Express upgrades the JavaScript prototypes

    Express uses Object.setPrototypeOf to attach express.request and express.response, adding req.header(), res.status(), and res.json().

Interview answer

What is the difference between app.locals, res.locals, and attaching properties to req?

app.locals lives for the whole process or isolate lifetime. Use it for global configuration or environment bindings.

Race-condition warning: In a concurrent multi-request Node server, mutating app.locals per request causes race conditions across overlapping requests. Always put per-request state on req or res.locals.

req and res.locals live for one HTTP request only. When the response finishes, they are garbage-collected. Putting req.user or req.traceId on req guarantees User A's data never leaks into User B's concurrent request.

Three allowed moves — and what breaks

Every middleware receives (req, res, next) and must do exactly one of three things.

1. Call next()

Pass control to the next middleware function in line.

2. Send a response

Call res.json(), res.send(), or res.end() to finish the request.

3. Call next(error)

Or throw inside an async function in Express 5 to jump straight to errorHandler.

Trap

Forget next() and send no response

The client hangs forever until the load balancer times out with 504 Gateway Timeout.

Trap

Call next() after res.json()

The next middleware sends a second response. Node crashes with Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client. Always return res.json(...)!

Pipeline assembly in code

export function createApp(): TestableExpressApp {
  const app = express();

  app.use(cors());          // 1. Fast OPTIONS preflight
  app.use(express.json());  // 2. Parse JSON stream into req.body

  // 3. Distributed Trace ID (before auth so 401s still get a traceId!)
  app.use((req, res, next) => {
    req.traceId = req.header('x-request-id') || crypto.randomUUID();
    res.setHeader('x-request-id', req.traceId);
    next();
  });

  // 4. Global Authentication gate
  app.use(authMiddleware);

  // 5. Backward-compatible URL aliasing middleware
  app.use('/api/v1', (req, _res, next) => {
    const aliases: Record<string, string> = {
      '/profiles': '/profile',
      '/workout-plans/active': '/workout-plans/current',
      '/auth/google/exchange': '/auth/oauth/exchange',
      '/exercises': '/exercise-catalog/exercises',
    };
    const queryIndex = req.url.indexOf('?');
    const path = queryIndex >= 0 ? req.url.slice(0, queryIndex) : req.url;
    const query = queryIndex >= 0 ? req.url.slice(queryIndex) : '';
    const target = aliases[path];
    if (target) req.url = `${target}${query}`;
    next();
  });

  app.use('/api/v1', healthRouter);
  app.use('/api/v1', authRouter);
  // ... profilesRouter, assessmentsRouter, workoutPlansRouter, workoutSessionsRouter

  // 7. Central Error Funnel (MUST BE LAST)
  app.use(errorHandler);
  return testableApp;
}

Why use a global authMiddleware with a public-path allowlist instead of adding authMiddleware to individual routes?

1.3 Express 5 · Async Errors · Routing

Express 4 vs 5

PhysioCoach AI runs on "express": "^5.0.0". Express 5 checks if a handler returns a Promise and automatically forwards rejections to next(err).

Real-world picture

Express 5 stretches a safety net under a trapeze artist. In Express 4, an async handler that threw without its own net fell straight to the floor.

What happens when an await throws

Express 4 was built before async/await existed in JavaScript. Express 5 natively understands Promises ("thenables").

Express 4

Calls handlers synchronously. If an await rejects and you forgot try / catch or express-async-errors, nobody catches the rejected Promise.

→ unhandled rejection crashes Node or hangs the request

Express 5

Router internals check if the handler returns a Promise. When the Promise rejects, Express catches it and calls next(err) for you.

→ 4-argument errorHandler returns clean JSON

Guaranteed DB cleanup with finally

PhysioCoach AI pairs Express 5 with a custom router adapter so database connections always close, even when a route throws.

register(path, async (req, res, next) => {
  const context = createRouteContext(req, res);
  try {
    const response = await handler(context);
    await sendWebResponse(res, response);
  } catch (error) {
    next(error); // Forward any thrown error or rejected promise to errorHandler
  } finally {
    await context.closeDb?.();
  }
});
  • 1catch (error) passes any sync or async failure straight to next(error).
  • 2finally runs await context.closeDb?.() after both success and error paths.

Three breaking changes in Express 5

Auto-forwarded Promises

Any async (req, res) function that throws or rejects automatically triggers the 4-argument error handler.

Named wildcards & ReDoS safety

Wildcards must be named, like /*splat instead of bare *. Tighter path rules also block ReDoS (a regex that takes forever on evil input).

req.query is a read-only getter

Uses a simpler query parser by default. It blocks deep prototype-polluting nested objects unless configured.

Interview answer

Why is upgrading from Express 4 to Express 5 a major architectural milestone?

1. Native async error propagation: Express 4 ignored Promises from async handlers. Without try / catch or express-async-errors, rejections crashed Node or hung the request. Express 5 catches returned Promises ("thenables") and calls next(err) automatically.

2. Hardened route matching: Bare * wildcards must now be named (such as /*splat). Path regex patterns were also tightened to prevent Regular Expression Denial of Service (ReDoS) attacks.

3. Safer req.query getter: req.query is read-only by default and uses a flat parser that blocks prototype-polluting nested objects.

1.4 TypeScript · Declaration Merging · Context Adapter

Type-safe request context

Never write (req as any).user. Use TypeScript declaration merging and a context adapter that forces every route to return a Web Response.

Real-world picture

Lazy database creation works like a motion-sensor room light. The light switches on only when the first person walks in, and stays on for everyone else in that visit.

Solution 1: Declaration merging instead of any

By default, TypeScript complains: Property 'user' does not exist on type 'Request'. Declaration merging fixes this cleanly across the entire project.

Casting (req as any).user

Silences the compiler by turning off type checking. Typos and missing checks slip into production.

→ destroys type safety across the codebase

declare global merging

Extends Express.Request in one place. Every route gets strict types and IDE autocomplete.

→ req.user, req.traceId, req.authSessionId are 100% typed

declare global {
  namespace Express {
    interface Request {
      user?: AuthenticatedUser;
      authSessionId?: string;
      traceId?: string;
      auditLogId?: string;
    }
  }
}
  • 1TypeScript merges this Request interface with @types/express automatically.
  • 2Properties are marked optional (?) because they are attached by middleware along the pipeline.

Solution 2: The context adapter pattern (createExpressRouter)

Instead of passing raw (req, res, next) into every route, src/routes/express-adapter.ts passes an ExpressRouteContext (c). The adapter builds standard Web responses with Response.json(body, { status }).

Raw res.json(body)

res.json() returns res, not a control-flow exit. Forgetting return lets code below it run and send headers twice.

→ accidental double-send at runtime

return c.json({ ok: true }, 200)

Handlers must return a Web Response object. TypeScript checks at compile time that every branch returns a response.

→ impossible to forget return or double-send

Lazy per-request database creation with ??=

Nullish coalescing assignment (db ??= getDb(bindings)) creates a DB client only when a route queries the database. Later calls in the same request reuse that single instance.

if (key === 'db') {
  db ??= getDb(bindings);
  return db;
}
  • 1??= assigns getDb(bindings) only when db is null or undefined.
  • 2Every later call in the same request gets the existing db instance immediately.

Interview answer

How do you pass per-request state in Express with TypeScript without using any, and why wrap Router() in an adapter?

1. TypeScript Declaration Merging: In src/middleware/auth.ts, declare global extends Express.Request with user, authSessionId, traceId, and auditLogId.

2. Compile-time return enforcement: Raw res.json() does not exit the function, making double-send bugs easy. Our ExpressRouteContext adapter requires every branch to return c.json(...) (a Web Response).

3. Lazy per-request DI: c.get('db') runs db ??= getDb(bindings). It creates one DB client only when needed, reuses it across the request, and closes it in finally.

1.5 Zero-Trust · Zod · Mass Assignment

Zero-trust validation

TypeScript types disappear at compile time. Incoming req.body, req.query, and req.params are unknown until a runtime Zod schema validates them.

Real-world picture

Zod at the HTTP boundary is passport control at a border. Writing as RegisterPayload is waving everyone through without checking their bags.

The HTTP border gate

Never write const body = req.body as RegisterPayload. A client can send objects or arrays instead of strings, plus "isAdmin": true, and runtime code will trust it.

export const workoutSessionCreateSchema = z
  .object({
    workoutPlanId: z.string().min(1),
    dayIndex: z.number().int().min(0),
    scheduledDate: z.string().min(1),
  })
  .strict(); // <-- Notice .strict()!
  • 1Every field enforces exact types and bounds (.min(1), .int().min(0)).
  • 2.strict() rejects the whole request if any extra key is present.

Why .strict() blocks Mass Assignment

Mass Assignment (Over-posting) happens when an attacker guesses internal database column names like role: "admin" or verified: true and sneaks them into a JSON payload.

Default z.object({ ... })

Silently strips unknown keys like role: "admin" and lets the request proceed without warning.

→ silent stripping hides over-posting attempts

z.object({ ... }).strict()

If the client sends role: "admin" or verified: true, Zod rejects the entire payload right at the door.

→ immediate 400 Bad Request

.parse() vs .safeParse() in parseJsonPayload

User input mistakes are routine, not unexpected crashes. PhysioCoach AI uses a discriminated union helper instead of throwing exceptions.

Control flow Jumps to catch block via stack unwind Fast, explicit if (!parsed.success) branch

if (!parsed.success) return parsed.response;
// Below this line, TypeScript knows `parsed.data` matches `loginSchema`!
  • 1parseJsonPayload handles malformed JSON or empty bodies without throwing.
  • 2Checking if (!parsed.success) narrows parsed.data to the exact Zod schema type.

Interview answer

Why is req.body as Payload unsafe, and why combine Zod .strict() with .safeParse()?

1. Zero-Trust boundary: TypeScript types vanish at compile time. An attacker can send {"email": {"$gt": ""}, "password": ["array_instead_of_string"], "isAdmin": true}. Treat req.body, req.query, and req.params as unknown until verified at runtime.

2. Preventing Mass Assignment with .strict(): Default Zod strips extra keys silently. .strict() rejects any request containing unknown fields like role: "admin" or verified: true with 400 Bad Request.

3. Explicit control flow with .safeParse(): Wrapped in parseJsonPayload(c, schema), .safeParse() returns a discriminated union instead of throwing exceptions on expected user validation errors.

1.6 Web Crypto · Dual Tokens · Reuse Detection

Senior-grade authentication

Anyone can say "I use JWT and bcrypt." Senior authentication closes four real attack vectors: timing side-channels, user enumeration, database leaks, and refresh token theft.

Real-world picture

Refresh tokens work like hotel key cards. The front desk gives you a new card each day and cancels yesterday's card. If someone swipes yesterday's card again, security locks the room right away.

The 4 security pillars in src/auth/ and src/routes/auth.ts

Pillar 1 · Web Crypto PBKDF2 & Constant-Time XOR

crypto.subtle PBKDF2-SHA256 (50,000 iterations) + timingSafeEqual byte XOR.

Pillar 2 · Anti-Enumeration Dummy Hash

Runs PBKDF2 against DUMMY_PASSWORD_HASH when an email does not exist so login always takes ~45 ms.

Pillar 3 · Dual-Token Architecture

15-minute stateless HS256 JWT + 32-byte refresh token stored only as a SHA-256 hash in auth_sessions.

Pillar 4 · Rotation, CAS & Reuse Detection

Every refresh rotates the token via atomic SQL Compare-And-Swap; reusing an old token revokes the session.

function timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean {
  if (a.length !== b.length) {
    return false;
  }

  let diff = 0;
  for (let i = 0; i < a.length; i += 1) {
    diff |= a[i]! ^ b[i]!; // Bitwise XOR every single byte without short-circuiting!
  }

  return diff === 0;
}
  • 1a[i]! ^ b[i]! evaluates to 0 only when both bytes match.
  • 2diff |= ... accumulates any mismatch across the full array before returning diff === 0.

Pillar 2: Stopping user enumeration with DUMMY_PASSWORD_HASH

50,000 PBKDF2 iterations take ~30–50 ms of CPU time. If login returns 401 in 2 ms when user is null, attackers can test 100,000 emails. They can spot registered accounts by response time alone.

Stateless JWTs cannot be revoked before expiry without hitting a database on every request. PhysioCoach AI pairs a short-lived JWT access token with a hashed refresh token in PostgreSQL. If a database backup leaks, attackers get only SHA-256 hashes and cannot impersonate users.

Pillar 4: Refresh token rotation, reuse detection & atomic CAS

Following RFC 6819 / OAuth 2.0 Security Best Current Practice, every refresh invalidates the old token and issues a new one. Reusing a rotated token revokes the entire session.

Refresh Token Rotation & Theft Detection (src/auth/sessions.ts)

  1. 1

    Login issues Refresh Token R1

    Its SHA-256 hash is saved in auth_sessions and auth_refresh_token_history.

  2. 2

    Client refreshes with R1 → Server issues R2

    Server invalidates R1 (moves it to previousRefreshTokenHash) and sets R2 as active.

  3. 3

    Attacker (or client after theft) tries to use R1 again

    Server sees R1 is not the active token and checks auth_refresh_token_history.

  4. 4

    Server finds R1 belongs to Session S and revokes Session S

    Sets revokedAt = now immediately so neither thief nor old session can refresh again.

// Optimistic Concurrency Control (CAS - Compare-And-Swap in SQL)
const updated = await db
  .update(authSessions)
  .set({
    refreshTokenHash: nextHash,
    previousRefreshTokenHash: presentedHash,
    previousRefreshRotatedAt: nowIso,
    idleExpiresAt: nextIdle.toISOString(),
  })
  .where(
    and(
      eq(authSessions.id, session.id),
      eq(authSessions.refreshTokenHash, presentedHash), // MUST still hold the current hash!
      isNull(authSessions.revokedAt),
    ),
  )
  .returning({ id: authSessions.id });

if (updated.length === 0) {
  // Another concurrent request already rotated this token! Revoke the session.
  await revokeSession(db, session.id, nowIso);
  throw new AuthError('token_invalid', 'Refresh token is not valid.');
}
  • 1The WHERE clause requires refreshTokenHash === presentedHash and revokedAt IS NULL in one atomic SQL statement.
  • 2If updated.length === 0, another request already rotated the token, so the session is revoked immediately.

Trap · Concurrent Refresh Race

Two refreshes in the exact same millisecond

The SQL WHERE clause requires eq(authSessions.refreshTokenHash, presentedHash). The second request sees updated.length === 0, calls revokeSession(db, session.id, nowIso), and throws token_invalid.

Dual Expiry Windows

Interview answer

Why avoid native bcrypt and === on password hashes, and why verify against DUMMY_PASSWORD_HASH when a user is missing?

1. Edge compatibility: Native C++ bcrypt addons cannot run in Cloudflare Workers isolates and can block Node's thread pool. We use Web Crypto (crypto.subtle) PBKDF2-SHA256 with 50,000 iterations and a 16-byte salt (pbkdf2$50000$<base64-salt>$<base64-hash>).

2. Constant-time XOR (timingSafeEqual): Standard === exits at the first wrong byte, enabling Timing Attacks. timingSafeEqual XORs every byte (diff |= a[i]! ^ b[i]!) in constant CPU time.

3. Stopping User Enumeration: PBKDF2 takes ~30–50 ms, while an early 401 takes 2 ms. Running verifyPassword against DUMMY_PASSWORD_HASH (~45 ms) and returning Invalid email or password. hides whether an email exists.

Interview answer

Why not issue a 30-day JWT, and how do Refresh Token Rotation and Reuse Detection stop token theft?

1. Dual tokens & hashed storage: Stateless JWTs cannot be revoked before expiry. We pair a 15-minute HS256 JWT (<1 ms check) with a 32-byte refresh token stored only as a SHA-256 hash (refreshTokenHash) in auth_sessions. If a database backup leaks, attackers get only SHA-256 hashes and cannot impersonate users.

2. Rotation & Reuse Detection (RFC 6819): Refreshing with R1 invalidates R1 and issues R2. If anyone uses R1 again, the server spots R1 in auth_refresh_token_history and revokes the session (revokedAt = now).

3. Atomic CAS & Dual Expiry: SQL Compare-And-Swap (eq(authSessions.refreshTokenHash, presentedHash)) revokes the session on concurrent refreshes. Every session also enforces both sliding idleExpiresAt and a hard absoluteExpiresAt cap.

Interview answer

Why are prepare: false and fetch_types: false set in src/db/client.ts?

1. prepare: false (Disabling Named Prepared Statements): Connection poolers like Cloudflare Hyperdrive and PgBouncer run in Transaction Pooling Mode. Transaction 1 might run on Postgres backend connection #42, while Transaction 2 runs on Postgres backend connection #19. Named prepared statements in Postgres are scoped to a specific backend TCP connection. Suppose postgres.js prepares statement s1 on connection #42 and later executes s1 on connection #19. Postgres crashes with ERROR: prepared statement "s1" does not exist. Setting prepare: false uses simple/unnamed protocol execution so transaction pooling works seamlessly.

Node.js & Express core (1–5)

Interview answer · Q1

1. Is Node.js single-threaded?

Your JavaScript code runs on a single thread (the V8 Event Loop). A heavy synchronous for loop or JSON.parse blocks all concurrent users.

The C++ runtime (libuv) and OS kernel are multi-threaded and async. libuv uses a background thread pool (default 4 threads) for file I/O, DNS, and crypto (PBKDF2). It delegates network sockets (http, PostgreSQL TCP) to OS kernel async APIs (epoll on Linux, kqueue on macOS).

V8 Event Loop (1 thread)

Runs JS callbacks. Blocked by sync loops or huge JSON.parse.

libuv Pool (4 threads)

Offloads file I/O, DNS lookups, and PBKDF2 crypto.

OS Kernel Async

epoll (Linux) & kqueue (macOS) multiplex HTTP & Postgres TCP sockets.

Interview answer · Q2

2. What is the difference between app.use('/api', fn) and app.get('/api', fn)?

app.use matches any HTTP method and matches by path prefix (/api, /api/users, /api/v1/health), stripping /api from req.url inside fn.

app.get matches only GET requests and requires an exact path match (/api only).

Interview answer · Q3

3. How does Express know a middleware is an error handler?

By inspecting fn.length === 4 ((err, req, res, next)). If you omit the 4th parameter next, Express treats it as a regular 3-argument middleware and will never call it on error.

Interview answer · Q4

4. What happens if an error is thrown after res.write() has already started streaming a response?

Once HTTP headers and initial body bytes are flushed to the TCP socket, you cannot change the HTTP status code to 500. Express's default fallback checks res.headersSent and closes the socket connection so the client detects an incomplete transfer.

Interview answer · Q5

5. What is backpressure in Node.js HTTP servers?

Sometimes a fast server reads a large file or DB cursor faster than a slow mobile client can download it. Memory buffers then fill up and crash the server. Using stream.pipe() or pipeline() pauses reading when the socket write buffer is full (write() returns false). It resumes automatically on the 'drain' event.

Fast source read → write() returns false → Pause reading → 'drain' event → Resume stream

Security & authentication (6–9)

Interview answer · Q6

6. Why store a SHA-256 hash of a Refresh Token instead of PBKDF2/bcrypt?

Passwords have low entropy: Humans pick weak passwords, so they need a slow hash (PBKDF2/Argon2) to stop offline brute-forcing.

Refresh tokens have high entropy: They are 32 bytes (256 bits) of cryptographic random data (crypto.getRandomValues). With 2^256 possibilities, they are mathematically impossible to brute-force. A fast cryptographic hash like SHA-256 protects the token against database leaks without wasting CPU time on every token refresh.

Human Password · Low Entropy

Vulnerable to dictionary attacks → requires slow PBKDF2 (50,000 iterations) or Argon2.

32-Byte Token · 2^256 Possibilities

Impossible to brute-force → fast SHA-256 hash protects DB leaks with zero CPU waste.

Interview answer · Q7

7. How do you defend against Refresh Token theft if you don't store sessions on the server?

You can't—which is why pure stateless refresh tokens are an anti-pattern. You must store session metadata (auth_sessions) and track token rotation (auth_refresh_token_history). If a previously rotated refresh token is presented again, you immediately revoke the entire session family.

Interview answer · Q8

8. How do you prevent timing attacks during login?

First, compare password hashes using a constant-time XOR loop (timingSafeEqual). Second, if the email does not exist in the database, verify the incoming password against DUMMY_PASSWORD_HASH. That way, "user not found" takes the same ~40 ms of PBKDF2 CPU work as "wrong password".

Interview answer · Q9

9. Where should tokens be stored on the client?

Option 1 is HttpOnly; Secure; SameSite=Lax cookies, which are immune to XSS but require CSRF protection on mutations. Option 2 is in-memory access tokens paired with rotated refresh tokens, strict Content Security Policy, zero XSS vectors, and server-side reuse detection.

Databases & transactions (10–12)

Interview answer · Q10

10. What is the N+1 query problem and how do you avoid it in Drizzle?

You fetch 20 workout sessions (1 query) and then run a SELECT in a for loop for each session (20 queries). Fix it by fetching all related exercises in one query with inArray(exerciseLogs.workoutSessionId, sessionIds) or a SQL JOIN. Then group the rows in memory with a Map.

Interview answer · Q11

11. How do you prevent race conditions when two requests try to update the same row at the same time?

Use Optimistic Concurrency Control (Compare-And-Swap) in a single atomic UPDATE ... WHERE id = $1 AND refresh_token_hash = $2 RETURNING id. Alternatively, use Pessimistic Locking with SELECT ... FOR UPDATE inside a transaction.

Interview answer · Q12

12. Why must prepare: false be set when using PgBouncer or Cloudflare Hyperdrive in transaction mode?

Transaction-mode poolers reassign Postgres backend connections after every transaction. Named prepared statements live on one specific backend connection. The next query can hit a different backend that does not have that prepared statement.

1. IQueryable<T> vs. IEnumerable<T>

IQueryable<T> builds an Expression Tree (Expression<Func<T, bool>>) that EF Core translates into SQL to run on the database server.

IEnumerable<T> runs delegates (Func<T, bool>) in C# memory. Converting to IEnumerable before filtering pulls the entire table over the network into RAM first.

Interview answer · 2 of 8

2. async / await under the hood

async does not spin up a new thread. The C# compiler rewrites your method into a state machine (IAsyncStateMachine).

While waiting for network or disk I/O (like Postgres or OpenRouter), the thread returns to the .NET Thread Pool to serve other HTTP requests. Always return Task or Task<T>.

  1. 1

    Start I/O and reach await

    IAsyncStateMachine records current local variables and registers a continuation.

  2. 2

    Thread returns to the .NET Thread Pool

    Zero thread blocked while Postgres or OpenRouter processes the request.

  3. 3

    I/O completes → state machine resumes

    A pool thread picks up the next state and completes the returned Task<T>.

Trap 1: .Result or .Wait()

Thread-pool starvation & deadlocks

Blocking a thread synchronously while waiting for an async task causes sync-over-async deadlocks and starves the thread pool.

Trap 2: async void

Exceptions crash the whole process

Callers cannot await async void or catch its exceptions. Always return Task or Task<T>.

Interview answer · 3 of 8

3. ValueTask<T> vs. Task<T>

Task<T> is a reference type that allocates on the heap unless cached. ValueTask<T> is a struct.

Use ValueTask<T> on hot paths where the result is usually available synchronously (such as hitting an in-memory cache 99% of the time). Never await a ValueTask<T> more than once.

C# type Reference type (class) Value type (struct)

4. Garbage Collection (GC) & memory generations

.NET divides the managed heap into Gen 0, Gen 1, Gen 2, and the Large Object Heap (LOH). Gen 0 holds short-lived HTTP request DTOs, Gen 1 acts as a buffer, and Gen 2 holds long-lived Singletons. The LOH stores objects >= 85,000 bytes, such as huge arrays or giant strings.

Gen 0 collections are sub-millisecond, while LOH and Gen 2 collections are expensive. Avoid allocating huge strings or arrays repeatedly in loops; use ArrayPool<T>, Span<T>, or streaming instead.

Gen 1 · Buffer between Gen 0 and Gen 2
Gen 2 · Long-lived Singletons · Expensive collection
Large Object Heap (LOH) · Objects >= 85,000 bytes · Expensive collection
Zero-LOH tools: ArrayPool<T> Span<T> Streaming I/O

3.1 Functions · Snapshots · Pure Render · Keys

Rendering and state

A React component is not a living class instance. It is a pure function call that turns current props and state into UI.

The core formula

UI = f(props, state)

Every time state changes, React calls your function again from top to bottom.

Real-world picture

A React component is a photo booth. It prints a brand-new photo on each change instead of taking a pen to edit the old photo.

A function call, not a class instance

Local variables declared with const or let are created fresh on every render. Event handlers close over (capture) the props and state from that specific render.

Angular habit: Class instance

Angular calls new MyComponent() once, mutates this.someProperty over time, and checks the template when signals or zone events fire.

→ one mutable object lives for the whole lifetime

React way: Function snapshot

React runs your function again on every state change. Local variables are fresh and disappear when the function returns.

→ handlers capture that render's exact values

State is immutable and compared with Object.is

React checks whether state changed by comparing the old and new references with Object.is(oldState, newState).

Trap · Angular habit that breaks

toasts.push(newItem); setToasts(toasts)

The array reference did not change, so Object.is(oldArray, newArray) === true. React thinks nothing changed and skips re-rendering.

const [toasts, setToasts] = useState<ToastItem[]>([]);

const toast = useCallback<ShowToast>((message, tone = "success") => {
  const id = nextId.current++;
  setToasts((current) => [...current, { id, message, tone }]);
}, []);
  • 1[...current, { id, message, tone }] allocates a new array so Object.is sees a new reference.
  • 2current => ... reads the latest queued array instead of a stale closure.

Key idea

When two events fire in the same tick, setToasts(current => ...) guarantees the second update appends to the first update's array.

Derived values: compute during render

When a value comes from props or state, calculate it right inside the function body. Do not put it in useState or useEffect.

// Derived value: computed while rendering, from props. Not state, not an Effect.
const hasFilters = Boolean(search.q || search.status || search.assignee);
  • 1hasFilters runs on every render and can never go out of sync with search.

Angular habit: computed()

In Angular, the class instance runs once, so you wrap derived state in computed(() => ...) to track signal changes.

React way: Plain const

Your component function already runs on every render. A plain const variable is fast and needs no wrapper.

Key idea · React Compiler

Next Issue Tracker enables reactCompiler: true in next.config.ts (docs/adr/0003-react-compiler.md). At build time, the compiler caches derived values and JSX nodes automatically, without manual useMemo, useCallback, or React.memo.

The pure render rule

React and the React Compiler can call your component multiple times or cache its output. Rendering must stay pure.

Don't mutate outside

Never change variables outside the component function while rendering.

Don't call impure APIs in render

Never call Date.now(), new Date(), or Math.random() during render or inside a state reducer.

Do impure work in handlers

Event handlers like submit are not render—they can call new Date() and pass the value in.

export function useHotkey(
  key: string,
  handler: (event: KeyboardEvent) => void,

The latest-ref pattern for timers

When a setTimeout starts inside an event handler instead of inside useEffect, store the latest callback in a useRef box.

export function useDebouncedCallback<Args extends unknown[]>(
  fn: (...args: Args) => void,
  delayMs: number,
) {
  const latest = useRef(fn);
  const timer = useRef<ReturnType<typeof setTimeout> | undefined>(undefined);

  useEffect(() => {
    latest.current = fn;
  });

  useEffect(() => () => clearTimeout(timer.current), []);

  return useCallback(
    (...args: Args) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => latest.current(...args), delayMs);
    },
    [delayMs],
  );
}
  • 1latest.current = fn updates inside an Effect after each commit.
  • 2When the timer fires after delayMs (for example 300 ms), it calls latest.current(...args) with fresh props and state.

Why useRef?

{ current: value } is a mutable box that persists across renders without triggering a re-render when .current changes.

Why not useEffectEvent?

Effect Events can only be called from inside useEffect. Here, the timer starts inside a caller event handler (onChange).

Why not write latest.current in render?

Concurrent React can start a render, abandon it, or render out of order. Mutating a ref during render breaks purity.

export async function updateIssueAction(
  issueId: string,
  _prev: FormState,
  formData: FormData,
): Promise<FormState> {
  // 1. Authenticate the caller (never trust that the button was hidden in UI)
  const user = await requireUser();

  // 2. Validate form data with Zod
  const values = formValues(formData);
  const parsed = EditIssueInput.safeParse(values);
  if (!parsed.success) return invalid(values, parsed.error);

  // 3. Authorize & mutate inside the DAL (checks can.editIssue)
  let issue;
  try {
    issue = await updateIssue(user, issueId, parsed.data);
  } catch (error) {
    return failed(values, error);
  }

  // 4. Expire affected cache tags
  invalidate.issueChanged(issue);

  // 5. Redirect OUTSIDE try/catch!
  redirect(`/projects/${issue.projectKey}/issues/${issue.number}` as Route);
}
  • 1requireUser(), EditIssueInput.safeParse(), and updateIssue() enforce authentication, schema validation, and can.editIssue authorization on the server.
  • 2The marked line places redirect() outside the try/catch block so catch cannot swallow the redirect exception.

Three traps every senior candidate must know

Bound arguments, redirect() exceptions, and validation errors behave differently from client-side routers.

Trap 1 · Bound arguments are untrusted input

updateIssueAction.bind(null, issue.id) is serialized into hidden HTML form fields

An attacker can edit that hidden field in browser DevTools and submit the form. Always validate bound arguments with Zod (Id.safeParse(projectId)) and check permissions inside the database mutation.

Trap 2 · redirect() throws NEXT_REDIRECT

Putting redirect() inside try { ... } catch (err) { return failed(...) } swallows the redirect

redirect() and notFound() throw an internal control-flow exception so React stops rendering immediately. A surrounding catch block intercepts it and turns a successful save into an error message.

Angular habit · Inside try / catch

In Angular, this.router.navigate(...) returns a normal Promise. In Next.js, calling redirect() inside try/catch catches NEXT_REDIRECT and runs return failed(values, error).

→ save succeeds, but UI shows an error

Next.js way · After try / catch

Call redirect() after the try/catch block (or call unstable_rethrow(err) inside catch) so Next.js catches NEXT_REDIRECT at the framework level.

→ sends 303 redirect / client navigation

Trap 3 · Expected validation errors must be returned as FormState values

Throwing a validation error triggers error.tsx and destroys what the user typed

Return { values, fieldErrors, message } into useActionState instead. IssueForm then preserves typed values (const v = { ...defaults, ...state.values }) and displays inline field errors.

Wrong: Throw validation error

Throwing from a Server Action jumps to the nearest error.tsx boundary and unmounts IssueForm.

→ error.tsx replaces form; typed values lost

Right: Return FormState value

Return invalid(values, parsed.error) as { values, fieldErrors, message } into useActionState.

→ form stays mounted with inline fieldErrors

Interview answer · Q1

Why does redirect() fail when placed inside a try/catch block in a Server Action?

redirect() throws NEXT_REDIRECT: In Next.js, redirect() does not return a value. It throws a special internal error (NEXT_REDIRECT). Next.js catches that error higher up to send a 303 redirect header or stream a client router navigation.

How to fix it: Putting redirect() inside try/catch intercepts that exception. Either place redirect() after the try/catch block or call unstable_rethrow(err) inside catch.

Interview answer · Q2

Does myAction.bind(null, secretId) keep secretId secret on the server?

No. Next.js sends bound arguments to the client in hidden form fields so the browser can send them back when the form is submitted.

Never pass secrets to .bind(), and always validate and authorize bound IDs on the server just like FormData fields.

3.8 Defense-in-Depth · proxy.ts · Session Cache · PGlite · Playwright

Auth defense-in-depth and testing

Layouts never gate authentication. Next Issue Tracker enforces three security layers and verifies them with a four-layer test pyramid using zero database mocks.

Real-world picture

A bank has a door guard, a counter clerk who checks your ID, and a vault with its own key.

Why layouts never gate authentication

Putting authentication checks only inside layout.tsx is a critical security vulnerability in Next.js App Router (docs/adr/0012-session-strategy.md).

Angular habit: Parent canActivate

In Angular, putting canActivate: [authGuard] on a parent route protects every child route. Trying to do the same in Next.js layout.tsx leaves child pages and actions exposed.

→ layout auth check is bypassed

Next.js way: 3-layer defense-in-depth

Check cookie existence in proxy.ts, validate the DB session with requireUser() in every page and action, and enforce can.* rules in the DAL.

→ every page and action verifies auth

Defense-in-depth across 3 layers

Authentication and authorization run at three concentric layers on the server.

1. src/proxy.ts · Cookie exists check (no DB)
2. Page & Action · requireUser / requireAdmin (React.cache DB session)
3. DAL · queries.ts / mutations.ts + permissions.ts (can.editIssue before SQL)

1. src/proxy.ts

Called middleware.ts prior to Next 16. Fast, optimistic check that verifies a session cookie exists (getSessionCookie(request)) and redirects anonymous visitors. No DB call here.

2. Page & Action (session.ts)

requireUser and requireAdmin validate the session token against the PostgreSQL sessions table, deduplicated per request via React.cache.

3. DAL (permissions.ts)

queries.ts and mutations.ts check role and ownership (can.editIssue(actor, row)) right before reading or writing SQL.

Instead of mocking SQL queries, integration tests run real Drizzle migrations on in-memory PGlite (Postgres compiled to WASM; docs/adr/0010-integration-tests-pglite.md). Playwright E2E tests run against a production build (docs/adr/0006-testing-strategy.md).

Interview answer · Q1

An Angular architect moving to Next.js suggests checking the user's session in src/app/(app)/layout.tsx so individual pages don't have to. How do you respond in a design review?

Reject that design. In Next.js App Router, layouts do not re-execute on client-side navigations between child routes. Pages also stream independently of layouts, and Server Actions bypass layouts completely.

Where auth belongs: Layout checks are only for displaying user UI (like the navbar avatar). Real authentication and authorization must happen in every page's data access calls and inside every Server Action.

Interview answer · Q2

Why can't you unit-test an async Server Component that uses <Suspense> and "use cache" in Vitest + Testing Library?

Missing server runtime in JSDOM: Testing Library's render() runs in a client-like JSDOM environment. It lacks Next.js's RSC stream serializer, "use cache" runtime, and server request context (headers(), cookies()).

Cleanest test split: Test data queries and Server Actions directly in fast integration tests with in-memory PGlite. Then test async Server Component pages end-to-end with Playwright against a production build.
